### Upload Success UI Flicker (Stale State Override) Bug

通过对“点击按钮 -> 开始上传 -> 上传成功 -> UI变化”链路的精准溯源，发现了一个导致上传成功后 UI 出现回退闪烁（Flicker）的严重状态覆盖漏洞。该问题源于本地临时状态计算与全局 Canonical Sync 状态机的分离。

#### 具体链路与问题点：

1. **上传完成瞬间 (Local Transient Update)**：
   在 `RecordingUploadCoordinator.uploadAndWaitWithActiveTrace` 中，上传请求成功返回后，调用了 `setActiveStatus(nil, for: latestMetadata, job: completedJob)`。
   - `setActiveStatus` 会调用 `updateDisplaySnapshot(metadata:activeStatus:job:)`。
   - 此时，它根据 `job` 的完成状态提取出 `provenUploadHash` 和 `byteSize`，并传入 `LegacySyncStatusToCanonicalEffectiveStatusAdapter.iPhoneUploadSnapshot`。
   - `iPhoneUploadSnapshot` 发现 `provenUploadHash` 存在，会**临时硬编码**生成一个 `CanonicalTransferFinalizeProof` (且 `verified: true`)。
   - 适配器在 `facts()` 中将这个 `finalizeProof` 作为一个 Fact 追加，并在随后的 `reconcile()` 中被评估为 `hasAcceptedFinalizeProof == true`，从而产出 `phase = .completed`。
   - 最终，`updateDisplaySnapshot` 直接将 `displaySyncStateByObjectID` 覆写为 `.completed`，UI 瞬间变为“上传完成”的状态。

2. **状态机的盲区 (State Machine Blindspot)**：
   **致命缺陷在于：** 这个由成功上传计算出的 `finalizeProof` Fact 仅仅是 `updateDisplaySnapshot` 里的**临时数据 (Transient)**，**从未被提交 (produce)** 给作为全局唯一的真理源 `canonicalStatusTruthRuntime`！
   `canonicalStatusTruthRuntime` 对刚才的上传成功一无所知，它内部缓存的关于该文件的 Fact 依旧停留在上传前（例如 `.localOnly`）。

3. **心跳同步的“降维打击” (Stale Sync Override)**：
   几秒后（或者上传途中刚好触发），`StudyLibrarySyncCoordinator.performTick()` 开始执行，它向 Mac 抓取最新的 `/sync/inventory`。
   - 如果此时 Mac 还未完全处理完 `/finalize` 落地，或者网络请求存在时间差，Mac 的 inventory 中该文件的 `audioAvailable` 仍为 `false`。
   - 同步协调器根据这个 Inventory 生成了一个无音频的 Fact (如 `.localOnly` 或 `.peerUnknown`)，并将其 `produce` 给 `canonicalStatusTruthRuntime`。
   - `canonicalStatusTruthRuntime` 综合现有 Facts (并没有 `finalizeProof`) 计算出一个落后的快照 (比如 `.localOnly`)。
   - 随后触发 `uploadCoordinator?.applyCanonicalStatusProjection(snapshot)`。
   - `applyCanonicalStatusProjection` 会**无条件覆写** `displaySyncStateByObjectID` 为这个落后的状态 (`.localOnly`)。
   
4. **UI 表现 (Visual Glitch)**：
   用户会看到 UI 从“正在上传” -> 瞬间变成“上传成功” -> 突然闪退回“本地/需要上传” -> 直到下一次 Tick 抓取到 Mac 最终的 inventory 后，才再次变回“上传成功”。

#### 核心原因：
`RecordingUploadCoordinator` 在上传成功时“走后门”直接绕过 `canonicalStatusTruthRuntime` 更新了 UI 投影 (`displaySyncStateByObjectID`)，而没有将成功的凭证 (Proof/Fact) 注入到状态机中。导致状态机在下一次被触发时，用其落后的认知覆写了前台正确的状态。
