### 1. 现象描述：短录音（<64MB）在 Canonical Sync 开启时上传状态丢失
当 `canonicalKernelMode == .canonicalFullSync`（新内核开启），但 iPhone 端由于 `CanonicalProductionPortInjectionPolicy` 中极其严苛的安全校验（如 `manualOwnerApproval`, `!releaseDefaultBuild` 等）被拦截时，iPhone 会**降级（Fallback）**误用旧内核，即调用 `RecordingUploadClient.uploadRecording` 发起传统的 Legacy 接口上传。
而在旧内核上传逻辑中，文件大小决定了使用的路由：
- **>64MB**：走断点续传（`/upload-recording-audio-session/*`）。
- **<64MB**：走单文件直传（`/upload-recording-audio`）。

由于大多数普通录音小于 64MB，会使用 `/upload-recording-audio` 路由发送。

### 2. 网络上传行为审计（Network Upload Request）：上传本身是成功的
当 Mac 端 `SecureLocalHTTPSServer` 收到 `/upload-recording-audio` 请求时，会进入 `handleRecordingAudioUploadRequest`：
```swift
private func handleRecordingAudioUploadRequest(_ request: HTTPRequest, on connection: NWConnection) async {
    let response = await recordingUploadRouteHandler.audioUploadResponse(...)
    sendRouteResponse(response, on: connection)
}
```
此时文件数据被成功存入 `recordingFileStore.saveAudio`，Mac 会通过 `onRecordingAccepted` 将旧的本地状态 `receiveStatus` 更新为已接收，并给 iPhone 返回 `200 OK`。
从网络请求本身和物理文件传输来看，上传是**完全成功**的。

### 3. UI与状态机同步行为审计（UI & Status Machine）：Canonical Fact 缺失导致状态回滚
在收到 Mac 的成功响应后，iPhone 端的 `RecordingUploadCoordinator` 会：
1. 更新其本地旧版 SQLite 数据库（`jobStore.markUploadSucceeded`）。
2. 调用 `setActiveStatus(nil, for: latestMetadata, job: completedJob)`，**人为制造一个 UI 状态缓存**，使得页面上立刻显示为“上传完成”。

**漏洞爆发点：**
因为 `canonicalKernelMode == .canonicalFullSync` 已经开启，此时 UI 的真实状态来源是 `CanonicalStatusTruthRuntime`（通过事实账本 Fact Ledger  reconciliation 获得）。
- 对于 **>64MB** 的文件，旧内核刚好命中了 `/upload-recording-audio-session/finalize` 路由，Mac 在 `handleResumableAudioFinalizeRequest` 中有这样一段代码：
  ```swift
  Task { await self?.produceMacTransferFinalizeProofFactIfPresent(...) }
  ```
  这会阴差阳错地在 Mac 端生成 `macTransferFinalizeProof` Fact，并通过状态交换同步回 iPhone，从而使最终状态正确。
- 但对于 **<64MB** 的单文件上传（`/upload-recording-audio`），Mac 的 Handler **完全没有**调用 `produceMacTransferFinalizeProofFactIfPresent`！
  这意味着 iPhone 和 Mac 双方都**没有任何人**向 `CanonicalStatusTruthRuntime` 提交过上传成功的 Fact。

**最终结果：**
当下次界面的 Heartbeat 刷新或重新获取状态时，由于缺乏 Canonical Fact，`displaySyncStateByObjectID` 的缓存被清除。`CanonicalStatusTruthRuntime.reconcileDisplayState` 会认为该文件从未上传过（状态仍为 `.local`）。
于是，UI 发生了**永久性的 Flicker 回滚**，即显示为“本地（未上传）”，而实际上物理文件早就已经躺在 Mac 的硬盘里了。这也是导致“上传失败”错觉的根本原因。
