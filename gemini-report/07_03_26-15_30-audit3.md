### 潜在的断链风险与失败点分析（漏洞审计）

尽管在“正常环境”下一切看似闭环，但深入源码和参数后，我发现以下几处强依赖时序和状态匹配的**潜在断链点**：

1. **`receive.json` 强依赖（Mac 存储层）**：
   - 在 `MacRecordingFileStore.updateTranscriptionStatus` 中：
     ```swift
     let receiveURL = recordingDirectoryURL.appendingPathComponent("receive.json")
     guard fileManager.fileExists(atPath: receiveURL.path) else { throw metadataMissing }
     ```
     如果用户在 iPhone 触发了上传，但 Mac 端由于历史残留或并发写入导致 `receive.json` 文件瞬态不可读或被其他进程锁定，转写状态将无法更新，后续的同步信号也就无法发出。这会导致 iPhone 永远收不到转写结果。

2. **Probe 信号覆盖与消费（同步信号竞态）**：
   - Mac 端 `consumePendingSyncStartSignal` 是一次性消费操作（Pop）。如果 iPhone 发送了一个 Probe，拿到了 `syncRequested = true`，但随后 iPhone 端由于网络抖动（如切后台、休眠）没能成功启动 `performSync`，这个信号就丢失了。Mac 不会重发，导致 iPhone 的转写结果被卡在 Mac 上，除非用户再次手动强制同步。

3. **生成的工件 ID (Artifact ID) 匹配**：
   - 在 `StudyLibrarySyncCoordinator` 执行下载时：
     ```swift
     guard let artifact = artifactsByID[action.entityID], artifact.kind.isAutoDownloadAllowed else { continue }
     ```
     如果 Mac 端 `MacRecordingFileStore` 写回的 `receive.json` 中的相对路径（`transcriptRelativePath`）未正确格式化，导致构建 Inventory 时无法被正确识别为 `generatedArtifact`（如被错误识别为普通文件或未知类型），iPhone 在这里会直接 `continue` 跳过下载。

4. **长耗时转写与 Heartbeat 周期**：
   - 如果是一段长录音（如数小时），转写（`LongAudioTranscriptionPlanner` 执行 Chunk 计划）可能需要很久。如果在这期间，iPhone 进入深度休眠（Deep Sleep），虽然 Mac 端会在转写完毕后注入 `syncStartSignal`，但 iPhone 长时间不发 Probe 心跳，就无法取回文本。此时只能依赖 Apple 的 Background Tasks 或 Live Activity 唤醒。

5. **大文件下载分片 (Chunking) 阈值**：
   - `downloadPeerArtifact` 逻辑中：
     ```swift
     if expectedSize > Self.maxSmallArtifactUploadBytes { // 4MB
         try await downloadPeerArtifactInChunks(...)
     }
     ```
     对于极大的转写结果文件（尽管文本一般不会超 4MB，但这依赖于具体的 Provider 和是否携带大量时间戳/置信度元数据），如果触发了 Chunk 下载逻辑，任何一个 `offset` 和 `length` 校验失败（如 Mac 端的 `syncArtifactChunkBytes` 与 iPhone 预期的不一致），都会导致抛出 `sync_artifact_offset_mismatch` 错误。
