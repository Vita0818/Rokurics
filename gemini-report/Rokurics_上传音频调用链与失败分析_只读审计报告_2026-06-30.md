## 1. iPhone 成功上传音频到 Mac 的完整调用链

在假设“iPhone 与 Mac 已通过局域网配对并成功连接”的前提下，从 iPhone 触发上传到 Mac 接收成功的完整代码调用和协议链条如下：

### 1.1 iPhone 客户端侧的调用与发送流
1. **触发层 (UI)**:
   * 用户在 UI 界面点击上传，触发 `RecordingLibraryView.uploadRecording` 或详情页的 `RecordingStudyDetailPage.uploadCurrentRecording`。
2. **调度与决策层 (Coordinator)**:
   * 调用 [RecordingUploadCoordinator.swift:upload(...)](file:///Users/vita/Vitemis/Vela/Rokurics/Rokurics/RecordingUploadCoordinator.swift#L619)，在后台异步 Task 中调度 `uploadAndWait`。
   * 调用 `RecordingAudioUploadDecisionEvaluator.evaluateRecordingAudioUploadDecision` 评估是否允许上传（检查本地录音是否存在、大小限制、以及对等端音频状态）。
3. **内核分发层**:
   * **情况 A：新内核 (canonicalFullSync 模式)**:
     - 进入 `uploadViaCanonicalTransferRuntimeIfEnabled`，根据 `IPhoneCanonicalProductionPortFactory` 获取 `IPhoneCanonicalTransferFileSource`，传入 `CanonicalTransferRuntime`。
     - 执行新版传输状态机 `runtime.transfer(source:requestedAt:)`。
   * **情况 B：旧内核 (oldKernel 默认/退避模式)**:
     - 调用 `jobStore.ensureJob` 在 SQLite 中注册或激活该上传 Job。
     - 将 UI/业务状态置为 `.uploading`。
     - 调用网络传输接口 `uploadClient.uploadRecording`（位于 [RecordingUploadClient.swift](file:///Users/vita/Vitemis/Vela/Rokurics/Rokurics/RecordingUploadClient.swift#L255)）。
4. **网络与分块传输层 (Client)**:
   * **上传 Metadata**：先调用 `uploadMetadataIfNeeded` 将元数据以 HTTP POST 发送到 Mac。
   * **断点与分块调度 (Resumable Upload)**：若音频大小超过阈值（如 5MB），触发分块上传流程 `uploadResumableAudio`：
     - **Session 恢复**：若已有 sessionID，则向 Mac 发送 `/upload-recording-audio-session/status` 请求，拉取 Mac 端已确认的 confirmedBytes 及下一次分块的 offset。
     - **Session 开始**：若无，调用 `secureClient.startResumableAudioUpload` (发送请求至 Mac 的 `/upload-recording-audio-session/start` 路由) 建立新的传输 Session，获取 Session ID。
     - **Chunk 循环传输**：打开本地音频的 FileHandle，按分块大小（如 1MB）循环读取，通过 `secureClient.uploadResumableAudioChunk` (调用 Mac `/upload-recording-audio-session/chunk`) 发送数据并更新进度。
     - **Finalize 提交**：发送完毕后，调用 `secureClient.finalizeResumableAudioUpload` (发送请求至 Mac `/upload-recording-audio-session/finalize`)，通知服务端进行整轨哈希校验及原子移动。

### 1.2 Mac 服务端侧的接收与状态保存流
1. **网络拦截与验签层 (Server)**:
   * 局域网入站请求到达 [SecureLocalHTTPSServer.swift](file:///Users/vita/Vitemis/Vela/Rokurics/RokuricsMac/SecureLocalHTTPSServer.swift)，根据路由匹配派发到对应的 handler：
     - `/upload-recording-audio-session/start` -> `handleResumableAudioStartRequest`
     - `/upload-recording-audio-session/status` -> `handleResumableAudioStatusRequest`
     - `/upload-recording-audio-session/chunk` -> `handleResumableAudioChunkRequest`
     - `/upload-recording-audio-session/finalize` -> `handleResumableAudioFinalizeRequest`
   * 每个请求均前置通过 `requestVerifier.verify`。此模块利用 Keychain 中的 pairing secret 校验 HTTPS 握手、HMAC 签名、时间戳 nonce 等，非信任或非配对设备直接拒绝。
2. **逻辑写入与事实合并层 (Route Handler & Store)**:
   * 请求校验通过后，由内嵌的 `RecordingUploadRouteHandler` 转发给 [MacRecordingFileStore](file:///Users/vita/Vitemis/Vela/Rokurics/RokuricsMac/MacRecordingFileStore.swift) 处理。
   * **Start/Status**：在临时目录为该录音初始化分块占位文件，保存 session 进度。
   * **Append Chunk**：校验当前的偏移量是否与写入进度吻合，在后台使用 `fileHandle` 追加文件，并校验局部 Chunk SHA256。
   * **Finalize**：校验整轨的大小与最终全量 SHA256 哈希，一致后将音频文件原子性 rename 移入 Inbox 播放和 AI 转写目录。
   * **Proof 事实合并**：若运行在新内核，在 Finalize 完毕后，Mac 端会生成对等端确认凭证 `CanonicalTransferFinalizeProof` 并合并回 Mac 本地 `CanonicalStatusTruthRuntime` 以更新同步状态。

## 2. 失败原因深入分析

即使“iPhone 与 Mac 已连接成功”，在传输的大文件长耗时场景下，依然可能在以下几个脆弱边界处触发失败：

### 2.1 安全验签失败 (RequestVerifier Rejected)
- **时钟偏移 (Clock Drift)**：局域网连接成功但由于两端设备系统时钟不一致（通常时差相差超过 5 分钟限制），导致带有时间戳的 Signature HMAC 校验失败，Mac 直接拒绝 start/chunk 请求，返回 400。
- **配对关系失效 (Pairing Loss)**：传输期间 Keychain 数据或配对存储区被清理，导致双方用于算 HMAC 的 pairing secret 不一致，导致所有后续分块写入在 verifier 层即被拦截。

### 2.2 重试风暴与网络抖动 (Retry Storms)
- **抖动崩溃**：在分块上传过程中，由于局域网弱网、丢包，某个 Chunk 发送超时。
- **风暴卡顿**：iPhone 侧若无合理的指数退避重试限制（Backoff），可能会以高频进行 status 路由重试，消耗局域网带宽，最终被 iOS 系统的内存或 CPU 限制杀掉。

### 2.3 存储与一致性冲突 (Storage & Conflict Blockers)
- **哈希冲突 (Different Audio Hash)**：iPhone 侧检测到同一个 recordingID 但本地音频内容有更新（SHA256 与 Mac 已存在的不匹配），为保护 Mac 已有的原始录音数据不被损坏或清空，Mac 判定为 conflict 并拒绝写入。
- **Mac 磁盘溢出**：Mac 设备的临时目录/归档分区存储空间被写满，`appendResumableAudioChunk` 触发写入 IO 失败，返回 500。

### 2.4 主线程耗时卡死 (MainActor Freezes)
- **同步大哈希计算**：对几十 MB 甚至上 GB 的长录音进行 SHA256 计算时，如果在 oldKernel 路径上未被完全移入后台 actor 线程，会霸占 UI 主线程（MainActor）。这会导致应用被 iOS 系统的 Watchdog 杀掉，导致传输中断。
- **同步日志阻塞**：大量的 Diagnostics 日志写入直接调用了老式的 atomic 全文件写操作，霸占主线程 IO。

### 2.5 权限沙盒异常 (Sandbox & Security-Scoped Bookmark)
- **书签过期**：iPhone 端由于 sandbox 权限限制或安全书签（Security-Scoped Bookmark）在应用重新激活后失效，导致 `audioURL` 虽然存在，但 FileHandle 打开失败直接抛出 `audioFileMissing`。
