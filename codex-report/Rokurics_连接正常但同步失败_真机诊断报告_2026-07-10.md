## 1. 结论摘要

当前失败不在连接层，也不在网络、端口、TLS、签名或 Mac inventory 服务。

本次同步的直接失败链是：

1. iPhone 成功连接到 Mac 当前监听的 `8788` 端口。
2. 心跳、配对身份、TLS 与签名请求全部正常。
3. iPhone 成功请求 `/sync/inventory`，Mac 约 252 ms 完成构建并返回 inventory。
4. iPhone 在本地生成差异计划时得到 53 个 `object_signature_conflict`：
   - 52 个 `studyItem`；
   - 1 个 metadata-only `recording`。
5. iPhone 同步引擎的全局冲突门禁检测到 `conflictActions` 非空，立即抛出 `sync_unresolved_conflicts:53`。
6. 整轮同步在 iPhone 本地终止，未向 Mac 发送 `/sync/apply-metadata`，也未开始 artifact 或文件内容传输。
7. iPhone 控制面状态写为 `failed`；Mac 因收不到后续 apply/completed，只能继续显示在 `inventoryExchanging` 附近。

这些冲突主要不是真实的用户双端同时编辑冲突，而是两端使用了不稳定、包含设备本地字段的对象签名。

## 3. P0：StudyItem 使用了不稳定的跨设备哈希

### 3.1 当前实现

iPhone 与 Mac 都直接对完整的 `StudyItemMetadata` 编码结果计算哈希：

- iPhone：`Rokurics/StudyLibrarySyncCoordinator.swift:2693`
- Mac：`RokuricsMac/SecureLocalHTTPSServer.swift:5576`

也就是说，`revisionHash` 不仅包含业务元数据，还包含路径、接收信息、设备状态与本地 custom properties。

### 3.2 两端会必然生成不同对象

iPhone 在构建当前 study item 时会合并本机录音模型：

- `createdAt = recording.createdAt`；
- `audioRelativePath = recording.relativeAudioPath`；
- 附加 iPhone 本地上传/传输进度字段。

对应源码：`Rokurics/StudyFilingModels.swift:768`。

Mac 在构建同一 study item 时会合并 Mac inbox 模型：

- `createdAt = item.receivedAt`；
- `audioRelativePath` 使用 Mac inbox 路径；
- `receiveRelativePath`、处理状态和部分 custom properties 使用 Mac 本地值。

对应源码：`RokuricsMac/StudyLibraryModels.swift:398`。

录制时间和 Mac 接收时间语义不同，iPhone 路径和 Mac inbox 路径也必然不同。这些字段一旦参与完整对象哈希，即使标题、归档、标签等业务内容完全一致，两端签名仍然不同。

### 3.3 为什么最终被判为冲突

共享 planner 的判断顺序位于 `RokuricsShared/SyncCore.swift:223`：

1. content signature 相同则 no-op；
2. 一端更新时间更晚则选择 upload/download；
3. 两端 `updatedAt` 相同、完整度相同但 signature 不同，则生成 `object_signature_conflict`。

当前真实数据恰好进入第三种情况。因此这 52 个 study item 冲突是结构性、可重复产生的，无法通过重试或改善网络解决。

## 4. P0：Recording metadata-only 记录也存在签名不一致

本轮剩余 1 个冲突来自 metadata-only recording。

当前 recording fallback signature 虽然已经排除一部分传输字段和路径，但仍包含：

- `createdAt`；
- `updatedAt`；
- transcription/note 状态；
- deleted 状态。

对应源码：`Rokurics/StudyLibrarySyncModels.swift:3153`。

与此同时：

- iPhone 普通 recording inventory 使用录制时间构建对象时钟；
- Mac inbox recording 使用接收时间构建对象时钟；
- metadata-only existence ledger 还可能保留旧版本的 metadata hash。

本轮实际冲突的 metadata-only 记录，其 Mac existence ledger hash 与 iPhone 当前生成的 recording metadata hash 不一致，最终同样成为 `object_signature_conflict`。

这说明仅修复 study item 哈希还不够，recording metadata 与 metadata-only existence 记录也必须统一签名版本和时间语义。

## 5. P0 放大器：任意冲突都会终止整轮同步

`Rokurics/StudyLibrarySyncCoordinator.swift:4590` 当前逻辑为：

```swift
guard plan.conflictActions.isEmpty else {
    throw LocalNetworkSyncExecutionError.unresolvedConflicts(plan.conflictActions.count)
}
```

因此只要存在一个 conflict：

- 已确认安全的 metadata upload/download 不会继续；
- audio/artifact 传输不会开始；
- Mac 不会收到 apply；
- 整轮同步直接失败。

这个门禁本身能够避免覆盖真实冲突数据，但当前签名算法会稳定地产生假冲突，于是门禁把签名问题放大成了“正常数据也永远无法同步”。

不建议只删除这个 guard。正确顺序应是先修复跨设备签名与时间语义，再决定真实冲突是否按对象隔离处理，避免单个对象阻断所有互不相关的安全动作。

## 6. P1：`syncedMetadataOnly` 是持久化的 Mac 本地污染字段

当前 Mac 真实库共有 53 个 study item，其中 28 个携带：

```text
customProperties.syncedMetadataOnly = true
```

该字段的用途是表示 metadata 已到达但 Mac 尚无录音内容。然而当前实现存在两个问题：

1. 它被包含在完整 `StudyItemMetadata` 哈希中，保证 Mac hash 与 iPhone hash 不同；
2. 音频到达后没有可靠清除此标记。

相关源码：

- 写入标记：`RokuricsMac/StudyLibraryStore.swift:1731`
- 转换 inbox 状态时依赖标记：`RokuricsMac/StudyLibraryModels.swift:431`

这不仅会制造同步签名分叉，还可能让已经具备音频路径的条目继续被判断为 metadata-only。

## 7. P1：修复假冲突后仍可能遇到 Tombstone HTTP 409

Mac 当前 Debug 持久配置仍为 `canonicalFullSync`，并非干净的 old-kernel 状态；当前真实 inventory 还包含 1 个 tombstone。

手动同步会通过 `forceSend` 强制发送本地 manifest：

- `Rokurics/StudyLibrarySyncCoordinator.swift:4603`
- `Rokurics/StudyLibrarySyncCoordinator.swift:9332`

Mac recording existence bridge 当前把 deleted/tombstone recording 返回为 `.blocked`：

- `RokuricsMac/SecureLocalHTTPSServer.swift:8941`

之后 `.blocked` 会被计入 `failedChanges`：

- `RokuricsMac/SecureLocalHTTPSServer.swift:4013`

只要 `failedChanges > 0`，`/sync/apply-metadata` 就返回 HTTP 409：

- `RokuricsMac/SecureLocalHTTPSServer.swift:5141`

因此，即使先消除本轮 53 个假冲突，当前 canonicalFullSync 配置下的 tombstone 仍可能成为下一层稳定失败原因。Tombstone 应由 tombstone 域负责，不能在 recording existence bridge 中被当成一般 apply 失败。

## 8. P1：Canonical peer manifest 当前无法通过校验

iPhone 真机日志还记录了：

```text
canonicalSyncRuntimeAuthorityGateBlocked: invalidPeerManifest
canonicalApplyRuntimeLegacyFallbackUsed: canonicalManifestValidationFailed:peer
```

当前实现因此回退到 legacy plan，本次并未直接在这里终止。但这表示：

- 当前 Debug canonicalFullSync 配置与真实 peer manifest 并未达到生产可用的一致状态；
- canonical plan/apply 路径不能作为当前同步成功的可靠基础；
- 修复时应先切回 oldKernel 做 A/B，或完成 manifest schema/modifiedAt 数据的统一后再开启 full sync。

## 9. P2：Mac 的 51 组 `existingInboxAudioDiverged` 是假阳性诊断

Mac 本轮 inventory 构建产生了 51 组：

```text
canonicalExistenceAudioConflict
canonicalRecordingExistenceInventoryConflict
detail=existingInboxAudioDiverged
```

这些日志不是 iPhone 差异计划中的 53 个 fatal conflict。

直接原因是：metadata-only existence ledger 的 `declaredAudioHash`/`declaredAudioByteSize` 为空，Mac merger 仍将其与真实 inbox audio 的 hash/size 比较；nil 与真实值自然被判断为不同。

对应源码：`RokuricsMac/SecureLocalHTTPSServer.swift:9342`。

该 merger 随后保留已有 inbox audio，没有把假冲突写成 peer inventory 冲突动作，所以它不是本次直接失败原因。但它有两个实际危害：

- 产生误导性冲突信号；
- 单次 inventory 写入大量低层日志，挤掉真正的 `syncTickFailed`/`syncRunFailed` 关键事件。

正确逻辑应把“ledger 未声明 hash/size”视为 unknown/not-comparable，而不是 diverged。

## 10. P2：控制面和诊断状态会掩盖真实失败位置

Mac 首轮 run 进入 active 后，短时间内可能拒绝后续不同 run ID 的状态更新；iPhone 快速重试时，Mac 状态文件仍可能保持早先 run 的 `inventoryExchanging`。

同时，inventory 产生的大量逐文件、逐对象日志会超过持久诊断窗口，导致最终错误事件没有可靠保留下来。

因此当前 UI/状态可能表现为“Mac 一直卡在 inventoryExchanging”，而真实情况是 iPhone 已经在本地 planning 阶段失败并启动了新一轮请求。

建议：

- 关键失败和 completed 事件使用保留优先级，不能被普通 hash/cache 事件挤掉；
- 对同一阶段的逐对象诊断做聚合和采样；
- 控制面应明确记录旧 run 被新 run 替代、超时或失败，而不是长期保留模糊的 inventory 状态。

## 11. 修复建议与优先级

### P0：先恢复基本同步收敛

1. 为 recording、study item、folder 定义真正跨设备稳定的业务签名。
2. 从签名中排除：
   - iPhone/Mac 文件路径；
   - Mac 接收时间与接收路径；
   - 上传、下载、transfer progress 和 ledger 状态；
   - `syncedMetadataOnly`、`localNetworkTransfer*`；
   - 本地预览缓存、处理状态和纯设备诊断字段；
   - 不参与业务冲突判断的 `modifiedByDeviceID`、本地 conflict 标记。
3. 明确并统一业务 `createdAt`/`updatedAt`：
   - recording 的业务创建时间应是原始录制时间；
   - Mac `receivedAt` 只能作为本地接收事实，不能替代业务更新时间；
   - `SyncObject.updatedAt` 与签名中的业务时间必须使用同一语义。
4. 为旧 metadata-only existence ledger 增加签名版本迁移或重建，避免旧 hash 与新 hash 永久冲突。
5. 将真实冲突按对象隔离；在保证安全的前提下，不让一个对象阻断所有无冲突动作。

### P1：处理下一层稳定失败

1. 音频落盘后清除 `syncedMetadataOnly`，并迁移现有错误标记。
2. Tombstone 交给 tombstone 域处理；existence bridge 对 tombstone 应返回合法 no-op/not-applicable，而不是 `.blocked` apply failure。
3. 当前真机验证先使用 oldKernel 做 A/B；canonicalFullSync 仅在 peer manifest 校验和 convergence 测试通过后重新开启。

### P2：修复可观测性

1. nil hash/size 不应产生 `existingInboxAudioDiverged`。
2. 保留失败、完成、HTTP 状态和最终 exception；普通逐对象日志聚合采样。
3. 让 Mac 和 iPhone 的 run 状态能明确表达 superseded、failed、timedOut。

至少补充以下测试：

1. **真实双端两轮收敛**
   - 第一轮允许产生必要 upload/download；
   - 应用结果后重新由 Mac/iPhone 各自真实 inventory builder 构建第二轮；
   - 第二轮必须 `conflicts = 0`、`pending upload = 0`、`pending download = 0`。

   - 同一录音分别使用 iPhone `Recordings/...` 与 Mac `audio/inbox/...`；
   - 业务签名必须相同。
3. **录制时间与接收时间不同**
   - Mac `receivedAt` 晚于 iPhone `createdAt`；
   - 不得生成 `object_signature_conflict` 或 `both_changed_after_last_sync`。
4. **metadata-only 到 audio available 迁移**
   - 文件到达后清除 `syncedMetadataOnly`；
   - 下一轮 inventory 必须收敛。
5. **Tombstone 手动同步**
   - manifest 含 tombstone 时 `/sync/apply-metadata` 不得因 existence bridge 返回 409。
6. **诊断保留**
   - 即使单轮产生数百条 hash/cache 事件，最终 `syncRunFailed` 或 `syncRunCompleted` 仍必须存在。

| `invalidPeerManifest` / hash round-trip 漂移 | 代码闭环 | canonical timestamp 在 wire/hash 前统一到整秒；ISO8601 encode/decode 后 manifest hash 保持一致；scoped manifest 覆盖检查锁定 authority 输入 | 原始真机日志中该错误实际消失 |
| 新 run 被旧 run、watchdog 或迟到终态污染 | 已闭环 | 新 run 可 supersede；旧 run 的 phase/terminal 被拒绝；同一 run first-terminal-wins；metadata apply lease 暂停 watchdog，apply 完成后再恢复监督 | 前后台切换、断网和快速重复点击 |
| sync-start 信号丢失或过早 ACK | 已闭环 | iPhone 两个消费者使用独立的原子持久化 FIFO；pending/in-flight/completed 与生命周期去重持久保存；写失败回滚且不可 ACK；重启保守重放；先成功入队再 ACK | 真实进程被系统杀死后的重放 |
| 普通诊断挤掉最终错误 | 已闭环 | normal/critical 有界队列、关键事件优先保留、串行落盘；`flush` 等待正在执行的 sink 写入完成 | 长时间运行和极端日志风暴 |
| 配对、端口与上传状态机的连带阻碍 | 已闭环 | 仅 `EADDRINUSE` 时 8787→8788→8789 逐次迁移并更新复制文本；两阶段 pairing 在 confirm/proof 成功后才持久保存；内容合同变化时续传重建 session；损坏 upload ledger 可恢复；Mac 收件箱通知同步刷新 | Bonjour/防火墙、首次权限和真实大文件 |

### 15.1 必须保持的协议边界

- V2 签名只表达业务等价，业务时间仍是 planner 的独立输入；custom property 默认白名单为空。
- receiver-local 路径、处理状态、`syncedMetadataOnly`、传输 ledger 和 UI 状态不得通过 peer merge 传播成跨设备业务事实。
- action-scoped manifest 缺少自身对象、必要关系或 deletion tombstone 时必须拒绝，不能 silent continue。
- 冲突隔离不是忽略冲突：无关动作可以完成，但只要仍有真实 unresolved conflict，该 run 就不能写成功。
- tombstone 不删除真实 inbox audio；peer proof 不完整也不能制造假冲突或抑制本机应有的上传。
- heartbeat 只能传递经过 runID、代际和阶段校验的状态，在线 presence 本身不能代表同步成功。

## 16. 现在再次同步和上传还可能有什么阻碍

在相同修复版本下，**目前没有已知的正常路径代码级硬阻碍**。连接完成后，metadata 同步应能进入 planning/apply/terminal，随后双向文件传输应按 hash、size、session 和 final ACK 收敛。仍可能阻碍真实设备的条件都属于必须保留或必须现场验证的边界：

1. **双端版本不一致。** 旧端没有 V2 签名、scoped manifest 和新 run/queue 语义，不能用混合版本做最终结论。
2. **系统与网络条件。** 首次本地网络权限、macOS 防火墙、Bonjour/`.local` 解析、Wi-Fi 客户端隔离、App 退后台/锁屏都可能阻断真实请求；这些不是代码单测能证明的。
3. **真实数据冲突。** 同一业务对象在两端确实被不同编辑时，系统会有意让该对象保持 unresolved，而不是覆盖数据；无关对象仍可继续。
4. **历史状态首次迁移。** 首轮可能清理旧 signature、metadata-only/existence/upload ledger 并产生一次性动作；应以紧接着的第二轮是否零冲突、零 pending 来判断是否稳定。
5. **资源和文件事实。** 原文件被移走、权限失效、磁盘空间不足、文件传输中再次变化或真实 hash/size 不同，都会被正确拒绝或重建，不应被当成网络层失败。
6. **尚未做真机压力验证。** 超长文件、弱网续传、进程被杀、前后台切换和长时间 soak 仍可能暴露只在 Apple 真实网络栈/生命周期下出现的问题。

端口占用本身不再应卡死配对：只有确认是 `EADDRINUSE` 时才把候选端口加一，下一次点击使用新端口，ready 后复制文本也包含该实际端口；iPhone 使用粘贴文本中的动态端口，不再写死 8787。
