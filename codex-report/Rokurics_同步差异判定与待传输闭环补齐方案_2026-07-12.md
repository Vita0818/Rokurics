# Rokurics 同步差异判定与待传输闭环补齐方案

- 日期：2026-07-12
- 范围：iPhone / Mac 学习库同步发现、Last-Write-Wins 决策、逐对象待传输标记以及上传层交接
- 文档性质：当前源码缺口说明与后续实现要求；本报告本身不表示这些缺口已经修复
- 前置边界：同步层不交换文件内容；上传层只有在用户明确操作后才传输文件 bytes

## 1. 最终产品定义

同步层必须完整完成以下五件事：

1. 两端分别构建一次学习库 inventory snapshot。
2. 使用稳定业务 ID 对齐同一个文件或同一组文件。
3. 比较两个版本，并按业务修改时间执行 Last-Write-Wins（LWW）。
4. 确定最新版本来自哪台设备、缺少最新版本的是哪台设备。
5. 在目标端持久化逐对象“待传输”标记，并把该标记提供给上传层。

同步层到此结束。它不得读取或发送实际文件内容，不得自动创建上传任务，不得执行文件覆盖、移动、删除、metadata apply、placeholder、retry 或 finalize。

上传层负责：用户点击学习库上传按钮后，消费同步层产生的待传输标记，校验来源版本仍然有效，传输文件内容，在目标端校验 checksum/size，并通过完成证明推进或清除标记。

## 2. 身份与版本必须分开

### 2.1 稳定业务 ID 是身份证号

每个文件或文件组必须拥有跨设备稳定的业务身份，例如：

```text
recordingMetadata:<recordingID>
recordingAudio:<recordingID>
studyFolder:<folderID>
studyItem:<itemID>
artifact:<artifactID>
```

稳定 ID 不得因以下变化而改变：

- 文件名或显示标题改变；
- 内容改变；
- 修改日期改变；
- iPhone/Mac 本地路径不同；
- 上传、接收、转写或笔记处理状态改变。

只要稳定 ID 相同，就必须视为同一业务对象的两个版本，而不是两个新增对象。

### 2.2 文件名、hash 和修改时间是版本属性

版本描述至少包含：

```text
objectID
objectKind
businessName / fileName
contentHash
byteSize
businessModifiedAt
tombstone
contentVersion/schemaVersion
```

其中：

- `objectID` 决定“是不是同一个对象”；
- `contentHash + byteSize` 决定内容是否相同；
- `businessName/fileName` 用于发现改名或 metadata 差异；
- `businessModifiedAt` 决定两个不同版本中哪一个更新；
- `tombstone + businessModifiedAt` 表示带版本的删除事实。

`inventory generatedAt`、扫描时间、接收时间、上传时间和诊断时间不得冒充业务修改时间。

## 3. 当前源码能做到什么

| 闭环环节 | 当前状态 | 说明 |
| --- | --- | --- |
| 单轮 inventory exchange | 已完成 | active path 每端以单次 snapshot 为目标，不在同步中传输文件内容 |
| 按稳定 ID 配对 | 基本完成 | recording、audio、folder、study item、artifact 已有稳定 object ID |
| 比较 hash/size/tombstone | 基本完成 | `SyncDiffPlanner` 使用对象签名判断相同或不同 |
| 按 `updatedAt` 给出方向 | 部分完成 | 普通差异可产生 upload/download 方向，但双方都在上次同步后修改时会提前判 conflict |
| 逐对象结果 | 仅内存存在 | `LocalNetworkSyncDiffPlan` 包含 action，但没有完整、长期的目标端记录 |
| 持久化 | 未完成 | `LocalNetworkSyncState` 只保存数量、摘要和 conflict count |
| 双端一致落标记 | 未完成 | iPhone 主要负责计算 diff；Mac inventory handler 没有持久化同一 reconciliation 结果 |
| 上传层消费标记 | 未完成 | 当前上传按钮直接按选中的录音创建任务，不读取同步标记 |
| 完成后收敛/清除 | 未完成 | 没有统一逐对象标记，因此也没有完成证明后的状态推进和下一轮清除 |

结论：当前同步已完成“只读发现且不越界传文件”的架构边界，但尚未完成业务要求的“最新版决策 -> 目标端待传输标记 -> 上传层消费 -> 完成后收敛”闭环。

## 4. 当前必须修正的判断问题

### 4.1 `both_changed_after_last_sync` 不符合本产品的 LWW 规则

当前 planner 在发现两端都晚于 `lastSuccessfulSyncAt` 时，会先返回 conflict，即使两端修改时间能够明确分出先后。

例如：

```text
iPhone modifiedAt: 10:10
Mac modifiedAt:    10:30
hash:              不同
```

产品要求：

```text
winner: Mac
source: Mac
target: iPhone
status: pendingTransfer
```

不得仅因为两端都改过就返回 unresolved conflict。只有以下情况才应 defer/conflict：

- 两端 hash 不同且 `businessModifiedAt` 完全相同；
- 缺少可信业务修改时间；
- 修改时间或版本 schema 不可比较；
- 删除与更新使用同一逻辑时间且无法确定顺序。

### 4.2 文件名差异尚未成为独立 reconciliation 事实

当前主要内容签名由 hash、size 和 active/deleted 构成。业务标题可通过部分 metadata hash 被发现，但物理文件名或独立业务名称尚未统一进入逐对象版本比较。

需要区分：

- hash 相同、名称不同：`renameOnly`，通常不需要传输文件内容；
- hash 不同、名称也不同：最新版来源端的内容和名称共同胜出；
- 稳定 ID 不同：才是两个不同对象，不能用名称相似强行合并。

### 4.3 缺少 hash 时不能用“空 hash + 相同 size”判定相同

当前底层签名会把缺失 hash 归一为空字符串。如果双方 hash 都缺失且 size 相同，存在误判为相同的风险。

正确结果应为：

```text
differenceKind: informationInsufficient
resolutionStatus: deferred
reason: missingContentProof
```

只有双方都具备可信 hash 和 size，或者有被协议认可的等价内容证明，才可以判定内容相同。

### 4.4 两端 tombstone 不能只因“都是删除”就无条件相同

tombstone 也有版本。双方均为删除状态时，仍应比较稳定 ID、tombstone version/hash 和业务修改时间，避免旧删除标记覆盖更新的恢复或新版本事实。

## 5. 需要新增的逐对象持久模型

建议新增独立于 inventory、upload job 和 UI display state 的模型：

```swift
struct SyncReconciliationRecord: Codable, Equatable, Identifiable {
    let recordID: String
    let objectID: String
    let objectKind: String

    let sourceDeviceID: String
    let targetDeviceID: String

    let sourceBusinessName: String?
    let targetBusinessName: String?
    let sourceHash: String?
    let targetHash: String?
    let sourceByteSize: Int64?
    let targetByteSize: Int64?
    let sourceModifiedAt: Date
    let targetModifiedAt: Date?

    let differenceKind: SyncDifferenceKind
    let resolutionReason: String
    let requiresContentTransfer: Bool
    let requiresMetadataUpdate: Bool

    var status: SyncReconciliationStatus
    var discoveredAt: Date
    var syncRunID: String
    var transferID: String?
    var completedProof: SyncReconciliationCompletionProof?
}
```

建议的差异类型：

```text
onlyOnSource
contentModified
renameOnly
metadataModified
deleted
same
timestampTie
informationInsufficient
```

建议的状态：

```text
pendingTransfer
pendingMetadataUpdate
queued
transferring
transferredAwaitingVerification
resolved
staleSourceVersion
deferred
```

该 record 必须有有界存储、schema version、原子写入、去重键和过期/替换策略。不得把完整文件内容、完整 transcript/note、绝对路径、secret 或证书信息写入其中。

## 6. LWW 决策算法

对每个稳定 `objectID` 执行以下顺序：

### 6.1 只有一端存在

```text
本端有 active version，对端不存在
→ source = 本端
→ target = 对端
→ difference = onlyOnSource
→ requiresContentTransfer = 是否存在文件内容
```

仅有 tombstone 而另一端从未出现对象时，不应创建内容传输；应保存删除事实或安全 skip，不能把 absence 直接执行为删除。

### 6.2 两端内容证明相同

```text
hash 相同 + size 相同 + tombstone 状态相同
→ content same
```

随后单独比较名称和业务 metadata：

- 全部相同：`same`，清除旧待传输记录；
- 只有名称/metadata 不同：按 `businessModifiedAt` 产生 `pendingMetadataUpdate`；不传文件内容。

### 6.3 两端版本不同

```text
local.businessModifiedAt > peer.businessModifiedAt
→ local is source
→ peer is target

peer.businessModifiedAt > local.businessModifiedAt
→ peer is source
→ local is target
```

不再因为“两端都晚于上次同步”而跳过时间比较。

### 6.4 时间完全相同但版本不同

不得静默选择某一设备覆盖另一端：

```text
difference = timestampTie
status = deferred
requiresUserResolution = true
```

如未来产品决定采用设备优先级，必须写成显式、稳定、双端一致的协议规则，不能依赖本地枚举顺序或请求方向。

### 6.5 删除与修改

- 较新的 tombstone 胜过旧 live version，生成目标端待删除 metadata 标记；同步本身不物理删除。
- 较新的 live version 胜过旧 tombstone，生成恢复/更新候选；必须保留 anti-resurrection 保护。
- 同一时间的 delete-vs-modify 进入 `timestampTie/deferred`。

## 7. 如何让两端得到一致标记

推荐方案：双端使用完全相同的 shared pure planner，各自对同一对 inventory 独立计算确定性 reconciliation records。

### iPhone

```text
构建 iPhone inventory
→ 发送给 Mac
→ 收到 Mac inventory
→ shared planner
→ 只持久化 targetDeviceID == iPhone 的待处理记录
→ 可选保存 sourceDeviceID == iPhone 的“待上传到 Mac”视图
```

### Mac

```text
收到 iPhone inventory
→ 构建一次 Mac inventory
→ 在 response 前或独立后台使用同一 shared planner
→ 只持久化 targetDeviceID == Mac 的待处理记录
→ 可选保存 sourceDeviceID == Mac 的“待上传到 iPhone”视图
→ 返回 Mac inventory
```

双方必须使用相同：

- stable ID schema；
- business hash schema；
- businessModifiedAt 语义；
- LWW/tie/tombstone 规则；
- 排序与 record ID 生成规则。

这样不需要把完整 diff plan 再额外来回发送；同步 wire payload 仍然只是两份短 inventory。若需要 ACK，只发送 run ID、inventory hash 和 reconciliation summary，不发送文件 bytes。

## 8. 上传层交接合同

上传按钮不应再凭 UI 当前选中对象自行猜测方向，而应读取有效的 reconciliation record。

创建任务前必须验证：

1. 当前设备等于 `sourceDeviceID`；
2. 目标设备等于 `targetDeviceID`；
3. 当前来源文件仍存在；
4. 当前来源 hash、size、modifiedAt 与 record 中的 source version 相同；
5. record 仍为 `pendingTransfer`，没有被新一轮同步替换；
6. 不存在同 object/source-version/target 的 active job。

若来源版本已变化：

```text
status = staleSourceVersion
不上传旧版本
请求重新同步
```

上传任务必须保存 `reconciliationRecordID` 和 expected source version，确保用户点击后传输的是同步层选定的版本，而不是随后被修改的另一个版本。

## 9. 上传完成后的收敛

推荐状态流：

```text
pendingTransfer
→ queued
→ transferring
→ transferredAwaitingVerification
→ resolved
```

只有满足以下条件才可进入 `resolved`：

- 目标端完整文件已落盘；
- byte size 匹配；
- 完整 checksum 匹配 record 的 source hash；
- no-overwrite 策略通过；
- finalize/ACK proof 被接受。

完成后：

- 上传层写入完成 proof 并停止显示 active transfer；
- 下一轮同步看到两端 hash/size 相同后，删除或归档 reconciliation record；
- 上传失败只更新 upload job/record 状态，不回写 `sync failed`；
- 同步失败也不得抹掉已有可验证 upload completion proof。

## 10. UI 表现

同一 reconciliation record 在两端显示不同文案：

### 来源端

```text
待上传到 Mac
待上传到 iPhone
```

来源端学习库按钮可创建内容传输任务。

### 目标端

```text
等待从 iPhone 传入
等待从 Mac 传入
```

目标端不得创建方向相反的新任务，也不得把旧本地版本显示为最新。

### metadata-only 差异

```text
名称待更新
归档信息待更新
```

不得显示文件上传进度，因为无需传输内容。

### tie/deferred

```text
版本时间相同，需选择保留版本
缺少内容校验信息，等待重新同步
```

不得用普通“同步失败”覆盖这些业务状态。

## 11. 实现优先级

### P0：补齐同步决策语义

1. 把 stable identity 与 mutable business name/fileName 明确分离。
2. 修改 shared planner：hash 不同后始终先比较可信 `businessModifiedAt`。
3. 删除普通路径中 `both_changed_after_last_sync` 对 LWW 的提前阻断。
4. 增加 rename-only、metadata-only、timestamp tie 和 missing proof 分类。
5. 缺 hash 时不得以相同 size 判定相同。

### P1：持久化目标端逐对象标记

1. 新增 versioned `SyncReconciliationRecordStore`。
2. iPhone 和 Mac 使用同一 pure planner 生成确定性 records。
3. 每端原子替换本轮针对自己的 target records。
4. 保留未完成 upload 所需的旧 record，直到新版本明确 supersede 或 proof resolved。
5. 记录有界摘要，但不能再只保存 count。

### P2：上传层消费

1. 学习库上传按钮读取 source-side reconciliation record。
2. job 保存 record ID 和 expected source version。
3. stale source fail closed，并请求重新同步。
4. iPhone -> Mac 与 Mac -> iPhone 使用相同交接合同。
5. upload completion proof 推进 record，下一轮 sync 清理。

### P3：UI 与诊断

1. 来源端和目标端分别显示方向明确的状态。
2. diagnostics 按 run 汇总 added/modified/renamed/deleted/pending/tie/deferred。
3. 对象级错误只保存脱敏 object ID/token、状态和 reason，不保存完整内容或绝对路径。

## 12. 必须新增的测试

### Planner

- 稳定 ID 相同、名称和内容都变：仍是同一对象的两个版本。
- 双方都在上次同步后修改，但 Mac 时间较新：Mac 胜出，不是 conflict。
- 双方都修改但 iPhone 时间较新：iPhone 胜出。
- hash 相同、名称不同：rename-only，不要求内容传输。
- hash 相同、只有时间不同：same content，不重复传输。
- hash 不同、时间相同：timestamp tie/deferred。
- 双方 hash 缺失且 size 相同：information insufficient，不是 same。
- newer tombstone、older tombstone、delete-vs-modify 和 anti-resurrection。

### Persistence

- 每个目标端 record 跨 app restart 保留。
- 新同步对同 object/version 幂等，不重复建 record。
- 新来源版本 supersede 旧 pending record。
- 无关对象不被清除。
- 存储有界、损坏 fail closed、schema migration 可回退。

### 双端一致性

- iPhone/Mac 对同一对 inventory 得到完全一致的 winner、source、target 和 reason。
- Mac 是目标端时，Mac 本地确实存在 pending record。
- iPhone 是目标端时，iPhone 本地确实存在 pending record。
- 同步 wire bytes 不包含文件内容。

### 上传交接

- 没有 reconciliation record 时，按钮不能把普通同步差异猜成上传方向。
- record source/target 正确时创建相应方向 job。
- 来源 hash 在点击前变化：不上传旧版本，标记 stale 并重新同步。
- matching checksum/size/finalize proof 后 resolved。
- upload failure 不改 sync completed。
- 下一轮两端 hash/size 相同后清理 record。

## 13. 验收标准

完整闭环必须同时满足：

- 同步仍然只交换短 inventory，不交换文件 bytes；
- 每个稳定 ID 只生成一个确定性 reconciliation 结果；
- 两端版本不同且修改时间可比较时，最新时间端必然成为 source；
- 没有最新版本的 target 端存在可跨重启的逐对象待传输标记；
- 标记包含 source、target、expected hash/size/modifiedAt 和明确 reason；
- 上传层只在用户点击后消费标记；
- 上传前阻止 stale source version；
- 完成 proof 后推进 resolved，下一轮一致性同步后清理；
- rename-only 不上传内容；
- 缺 hash、时间相同或不可比较时不静默覆盖；
- connection、sync、upload 的状态和错误仍彼此独立；
- 不降低 TLS pinning、HMAC、timestamp、nonce、body hash、`RequestVerifier`、checksum/size、no-overwrite、Keychain 或 root containment。

- `RokuricsShared/SyncCore.swift`：当前 `SyncDiffPlanner`、content signature 和 `both_changed_after_last_sync` 规则。
- 双端 `StudyLibrarySyncModels.swift`：inventory/object projection、compatibility plan 和差异 action。
- `Rokurics/StudyLibrarySyncCoordinator.swift`：iPhone inventory exchange、diff owner 和 sync completion。
- `RokuricsMac/SecureLocalHTTPSServer.swift`：Mac inventory request/response；后续需要在不重复扫描的前提下运行同一 shared planner。

- `Rokurics/RecordingUploadCoordinator.swift`：iPhone -> Mac 上传层消费点。
- `RokuricsMac/MacToIPhoneUploadStore.swift`、`Rokurics/MacToIPhoneUploadReceiver.swift`：Mac -> iPhone 上传层消费与完成 proof 点。
- 双端学习库 UI：展示 source/target 方向和用户上传入口。

## 15. 最终判断

当前实现不是完整闭环。它已经解决了“同步越权传文件、apply、创建 placeholder、重复扫描和错误终态耦合”，但仍缺少本产品真正需要的 reconciliation 层：

```text
发现差异
→ 按稳定 ID 认定同一对象
→ 按业务修改时间选择最新版本
→ 确定 source/target
→ 在 target 端持久化逐对象待传输标记
→ 交给用户触发的上传层
→ checksum/finalize proof 后收敛
```

上述链路全部完成并通过测试后，才能声明 Rokurics 同步差异处理与上传交接形成完整闭环。

## 16. 2026-07-12 实施结果

本报告要求的代码级闭环现已落地：

- 共享 planner 按稳定 `objectID` 与业务 `modifiedAt` LWW 得到确定性 source/target；rename-only、缺 hash/size、时间并列和 tombstone/anti-resurrection 均有明确结果。
- iPhone 与 Mac 在同一轮交换完整短 inventory，并各自持久化 `Sync/Reconciliation/records.json`；ledger 具备 schema v1、原子写入、默认 4096 条上限、幂等 supersede、无关对象保留和损坏 fail-closed。
- iPhone -> Mac 与 Mac -> iPhone 的学习库按钮只允许来源端消费有效 record；来源版本 stale 时不建 job，目标端安装前校验 expected target version，传输完成后记录 checksum/size proof。
- UI 区分“待上传到对端”和“等待从对端接收”；rename-only/deferred 不创建内容传输。
- 下一轮 inventory 收敛时清除对应 record；同步、连接和上传的失败/成功状态保持独立。

本地验证已通过 `SyncReconciliationClosedLoopTests` 13 项及双端构建。尚未完成的是 paired iPhone/Mac 真机同 Wi-Fi 往返、大文件第二轮 cache-hit 时延/流量和真实 TLS 网络链路证据；这些属于真机验证，不是已知代码缺口。在取得真机证据前，不得把本报告状态表述为“真机已验证”。
