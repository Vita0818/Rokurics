## 2. 一句话结论

结论：不建议继续 fullSync 真机长测，建议先修 blocker。当前源码已足以解释 9000ms+ 卡顿的高风险来源：`LocalNetworkSyncEngine` 仍是 `@MainActor` 且 fullSync tick 后半段串行执行大量 canonical seam/plan/apply/status/diagnostics，Mac event queue 也在 MainActor 上 `studyLibraryStore.refresh()`，同时 diagnostics/status store 以高频同步 JSON/JSONL 读写运行在 MainActor。v8.69-v8.72 的主要修复代码大多真实存在并有 app path 接线，但 v8.73 final gate 只是 pure scorecard/test/runbook，不是运行时阻断 gate；状态收敛仍受 foreground/offline/debounce/pending hint 超时、Mac 不能反向主动连接、双 coordinator/service 并存和 diagnostics 缺口影响。

## 7. diagnostics 可观测性审计

1. 是否能定位 read cache rebuild：部分能。`canonicalReadEffectiveCacheRebuilt`、`TreeRebuilt`、`RebuildDurationMs` 存在，但没有 UI body 访问频率与 MainActor long-task 关联。
2. 是否能定位 Mac inventory build duration：能定位 `/sync/inventory`。`macInventoryRouteCompleted` 包含 route/manifest/canonical duration。
3. 是否能定位 canonical build duplicate：部分能。Mac inventory 和 iPhone sync tick 有 duplicate/reuse diagnostics。
4. 是否能定位 heartbeat hint：能。`syncRequestedHintReceived`、`heartbeatSyncRequestedTickQueued/Started/Completed/Deferred/Debounced` 存在。
5. 是否能定位 event-to-sync latency：部分能。iPhone event tick context 记录 start/complete latency；Mac `eventToSyncStartLatencyMs` 只记录 hint queued，不证明 peer consumed/completed。
6. 是否能定位 status convergence：部分能。有 refresh/finalize-proof/peer-proof-unavailable；缺 peer inventory consume -> local UI convergence 的闭环指标。
7. 是否能定位 upload proof truth：部分能。Canonical upload truth diagnostics 存在；但需要真机 jsonl 串起 upload finalize、Mac inventory、iPhone read status。
8. 是否能定位 9000ms 卡顿来源：不能完整定位。缺少 MainActor long-task/signpost、diagnostics write duration、non-inventory route duration、store refresh/cache rebuild call-site、SwiftUI read path frequency。

诊断结论：diagnostics 对 v8.69-v8.72 的局部修复足够，但对用户报告的 9000ms+ 卡死仍不足，属于 blocker。

## 9. 是否可继续 fullSync 真机实测

选择：`STOP_AND_FIX_BLOCKERS`

理由：当前源码虽然已落地 v8.69-v8.72 的主要修复，但仍存在代码级 blocker，且这些 blocker 足以解释用户已观察到的 9000ms+ 卡顿和状态不收敛。继续 fullSync 长测会把真机时间消耗在已知主线程重活与诊断盲区上，不能高效收敛。

Blockers:

* `LocalNetworkSyncEngine.performTick` 主体仍在 `@MainActor`。
* Mac event/status convergence drain 仍 MainActor `studyLibraryStore.refresh()`。
* cache key 使用 `generatedAt`，无内容变化 refresh 仍可能 rebuild。
* diagnostics/status store 高信誉号路径同步文件 IO。
* v8.73 final gate 未接入 runtime fullSync switch。
* 9000ms 定位所需 MainActor/route/diagnostics write duration 不足。

## 10. 下一轮最小修复建议

### 1. 立即修复项

* 文件: `Rokurics/StudyLibrarySyncCoordinator.swift`
  函数/属性: `LocalNetworkSyncEngine.performTick`
  为什么: fullSync tick 后半段 MainActor 串行执行 canonical seam/plan/apply/diagnostics/status，是 9000ms 最大代码级根因。
  预期验收: 真机 jsonl 显示 sync tick 分段 duration；MainActor 分段只负责状态发布；UI 不出现 9000ms freeze。
  是否影响 route/security: 否，不能改 route、TLS/HMAC、RequestVerifier。

* 文件: `RokuricsMac/SecureReceiverService.swift`
  函数/属性: `drainMacSyncEventQueue`
  为什么: event drain 直接 `studyLibraryStore.refresh()`，转写/笔记/receive finalize 频繁触发。
  预期验收: status-only event 不 full tree rebuild；generated artifact event 后有 pending hint 与 projection update duration。
  是否影响 route/security: 否。

* 文件: `Rokurics/StudyLibraryStore.swift`, `RokuricsMac/StudyLibraryStore.swift`
  函数/属性: `canonicalReadSnapshotSignature`
  为什么: `generatedAt` 使 cache 对高频 refresh 过度失效。
  预期验收: 内容不变 refresh 后 cache hit，不增加 rebuild count；内容变化时仍 rebuild。
  是否影响 route/security: 否。

* 文件: `Rokurics/ConnectionSyncStateStores.swift`, `RokuricsMac/ConnectionSyncStateStores.swift`
  函数/属性: `ConnectionDiagnosticsStore.record`, status store `save`
  为什么: MainActor 同步 JSON/JSONL IO 高频发生。
  预期验收: buffered async writer；记录 diagnosticsWriteDurationMs；heartbeat/event 不阻塞 UI。
  是否影响 route/security: 否，但要保持 redaction。
