# Rokurics 连接、同步与双向文件传输全链路失败审查

生成日期：2026-07-10

初始审查方式：只读源码审查、调用图核对、现有测试断言核对、定向 Xcode 测试尝试

审查范围：Mac 与 iPhone 的连接、文件信息同步、iPhone→Mac 文件上传、Mac→iPhone 文件取得、状态交换、重试和持久化边界

修复状态更新：2026-07-10 已完成本文全部 P0/P1（含第 17 节的 P1/P2 项）源码修复和双端定向自动化验证。本文第 4～17 节保留的是修复前根因；最终状态以第 33 节为准。

## 1. 本报告采用的术语

- **连接**：Mac 与 iPhone 完成配对、TLS/HMAC 身份建立，并通过 heartbeat/probe 维持可通信关系。
- **同步**：Mac 与 iPhone 交换文件及学习库信息，包括对象 ID、metadata、路径 token、大小、hash、tombstone、状态和 revision，但不交换具体文件内容。
- **上传/文件传输**：连接和同步已完成后，一端向另一端发送实际文件内容。
- 当前拓扑中 iPhone 始终是网络请求发起方。所谓 Mac→iPhone 文件传输，实际是 iPhone 主动请求并从 Mac response 拉取文件，不是 Mac 主动反向拨号。

## 2. 初始审查总体结论（修复前）

修复前实现不能可靠完成“连接 → 文件信息同步 → 双向文件传输”。最严重的问题不是偶发网络抖动，而是生产同步执行器会主动跳过全部文件内容动作，然后仍把同步记录为成功。

| 阶段 | 当前真实状态 | 核心结论 |
| --- | --- | --- |
| 连接 | 单一稳定 IPv4、完整配对响应的 happy path 可用 | 配对事务、地址生命周期、控制 ACK 和持久化均存在正常操作可触发的失败 |
| metadata 同步 | inventory、hash、manifest、diff、apply 路径存在 | 冲突、部分应用失败和异步未完成可被记录成成功 |
| iPhone→Mac 内容 | 手动录音上传存在独立路径 | sync 自动补传音频和 artifact 当前不执行 |
| Mac→iPhone 内容 | 设计为 iPhone pull 少数 generated artifacts | 相关物理下载 helper 当前无调用点 |
| 状态展示 | 有 completed/online/progress 状态 | 多处状态会早于真实持久化或内容完成而进入成功 |

正常 loopback happy path 中，TLS leaf certificate fingerprint pinning、HMAC 字段、nonce/timestamp 和主要网络 entitlement 没有发现明显不一致。主要失败面集中在状态机的确认时机、地址生命周期、metadata 业务时钟、持久化事务和内容执行断点。

## 3. 严重度定义

- **P0**：阻断核心目标，正常流程必然无法得到承诺结果，或产生明确的假成功。
- **P1**：高严重度；常见用户操作、短暂丢包、重配、重启或普通数据变化即可触发持久失败或状态分叉。
- **P2**：条件性确定缺陷；达到特定规模、文件状态、系统权限或异常 I/O 条件时稳定触发。
- **风险项**：源码存在明确竞争或性能危险，但还需要真机、压力测试或 TSan 确认最终表现。

## 4. P0：同步规划文件传输后无条件跳过，并仍记录成功

### 4.1 触发条件

任一正常同步产生以下动作之一：

- Mac 缺少 iPhone 已有的录音音频。
- Mac 存在 iPhone 缺少的 transcript、note、summary 等 generated artifact。
- 一端存在另一端缺少的允许传输 artifact。

### 4.2 根因

`LocalNetworkSyncEngine.performTick` 先统计：

- `plan.uploadRecordingAudioActions`
- `plan.uploadArtifactActions`
- `plan.downloadArtifactActions`

随后把这些动作全部计入 `skippedContentActionCount`，记录 `contentTransferSkippedForStructureSync`。实际执行阶段只调用：

- `applyPeerRecordingStatuses`
- `applyPeerMetadataIfNeeded`
- `uploadLocalMetadataIfNeeded`

之后直接调用 `stateStore.recordSuccess`，把 `pendingUploadCount`、`pendingDownloadCount` 写成 0，清空 active transfers，并记录 `syncTickCompleted` / `syncRunCompleted`。

证据：

- `Rokurics/StudyLibrarySyncCoordinator.swift:4451-4487`
- `Rokurics/StudyLibrarySyncCoordinator.swift:4517-4526`
- `Rokurics/StudyLibrarySyncCoordinator.swift:4546-4563`

三个物理传输 helper 全仓只有定义，没有生产调用点：

- `downloadPeerArtifactsIfNeeded`：`Rokurics/StudyLibrarySyncCoordinator.swift:9239`
- `uploadLocalArtifactsIfNeeded`：`Rokurics/StudyLibrarySyncCoordinator.swift:9576`
- `uploadMissingRecordingAudioIfNeeded`：`Rokurics/StudyLibrarySyncCoordinator.swift:10263`

旧的 `StudyLibrarySyncCoordinator.performSync` 路径同样会把 pending recording upload 记录为 `contentTransferSkippedForStructureSync`，然后继续发送 metadata：

- `Rokurics/StudyLibrarySyncCoordinator.swift:1007-1026`

### 4.3 影响

- iPhone 已有、Mac 缺少的音频不会因同步自动上传。
- Mac generated transcript/note/summary 不会下载到 iPhone。
- artifact 上传/下载不会执行。
- UI 和状态存储仍显示同步完成。
- 下一轮会再次“规划 → 跳过 → 成功”，形成稳定假成功循环。
- 手动录音上传按钮走独立 `RecordingUploadCoordinator`，不受这个断点直接影响，但会受到后文 ledger/session 问题影响。

### 4.4 测试反证

现有测试仍明确要求这些动作真实执行：

- artifact 下载：`RokuricsTests/RokuricsTests.swift:4475`
- small artifact 上传：`RokuricsTests/RokuricsTests.swift:4496`
- large artifact 上传：`RokuricsTests/RokuricsTests.swift:4572`
- 缺失 audio 上传：`RokuricsTests/RokuricsTests.swift:4758-4853`

这些测试断言与当前生产调用图直接矛盾。

## 5. P1：同步冲突和部分应用失败会被记录为成功

### 5.1 触发条件

- 两端出现同时间戳、不同内容。
- 两端并发修改同一 metadata。
- 单条 apply 失败或被拒绝。
- Mac 返回 `conflictCount > 0`、`failedChanges > 0` 或 rejected changes。

### 5.2 根因

- diff plan 的 `conflictActions` 只写诊断，不中止同步：`Rokurics/StudyLibrarySyncCoordinator.swift:4502-4504`。
- iPhone 应用 peer metadata 后丢弃整个 `StudyLibrarySyncApplyResult`：`Rokurics/StudyLibrarySyncCoordinator.swift:9171-9197`。
- iPhone 上传 metadata 时只检查 `response.ok`，不检查 `applyResult`、`error`、`rejectedChanges` 或冲突：`Rokurics/StudyLibrarySyncCoordinator.swift:9200-9236`。
- Mac 对 manifest 的 partial failure/conflict 可继续构造 `ok: true` response：`RokuricsMac/SecureLocalHTTPSServer.swift:3940-4009`。
- 最终执行器无条件 `recordSuccess`，清零 pending 并推进 last successful state：`Rokurics/StudyLibrarySyncCoordinator.swift:4547-4563`、`Rokurics/ConnectionSyncStateStores.swift:1353-1383`。

### 5.3 影响

- 两端仍不一致，但 UI/state 显示成功。
- 未应用项不会保留为明确 pending。
- 错误 revision/hash 会成为下一轮判断基线。
- 用户看到“同步完成”却继续看到旧标题、旧删除状态或缺文件。

## 6. P1：iPhone 重命名录音不推进业务时间戳

### 6.1 触发条件

录音已经同步到 Mac，随后用户在 iPhone 正常重命名。

### 6.2 根因

- `RecordingManager.renameRecording` 更新 RecordingMetadata 后调用 `upsertRecordingMetadata`：`Rokurics/RecordingManager.swift:272-293`。
- `StudyItemMetadata.mergedWithCurrentRecording` 更新 title，却保留旧 `updatedAt`：`Rokurics/StudyFilingModels.swift:768-797`，尤其第 774、776 行。
- iPhone canonical library adapter 使用该旧时间作为 `businessModifiedAt`：`Rokurics/IPhoneCanonicalLibraryAdapter.swift:97`。
- iPhone recording adapter 对未删除录音使用 `createdAt` 作为 modified time，改名不会改变：`Rokurics/IPhoneCanonicalRecordingAdapter.swift:17`。
- 内容 hash 已变但业务时间相等时，canonical planner 生成 metadata tie conflict：`RokuricsShared/SyncCore/CanonicalLibraryObject.swift:469`、`RokuricsShared/SyncCore/CanonicalSyncPlanner.swift:320-340`。

### 6.3 影响

- iPhone 保留新标题，Mac 可能保留旧标题。
- 后续每轮仍是同时间戳冲突，无法自然收敛。
- 结合第 5 节，状态还会被记录为同步成功。

## 7. P1：恢复录音后 StudyItem tombstone 永久粘住

### 7.1 触发条件

用户正常删除录音，随后在 iPhone 执行恢复。

### 7.2 根因

- 恢复路径更新 RecordingMetadata 后重新 upsert StudyItem：`Rokurics/RecordingManager.swift:315-320`。
- 合并逻辑使用 `isTrashed || recording.isDeleted`：`Rokurics/StudyFilingModels.swift:793`。
- 原 StudyItem 一旦为 `isTrashed=true`，恢复后的 `recording.isDeleted=false` 无法把它清除；旧 `trashedAt` 也继续保留。
- manifest builder 因此仍会向 peer 输出 trash tombstone：`Rokurics/StudyLibrarySyncCoordinator.swift:2373-2385`。

### 7.3 影响

- 本地音频已经恢复，metadata sync 却继续宣告对象已删除。
- Mac 会保持删除状态。
- 后续同步还可能再次把本机状态拉回删除或持续制造 conflict。

## 8. P1：配对存在非事务性的半提交状态

### 8.1 触发条件

- 用户在配对请求进行中返回上一页。
- Mac 已处理配对但 HTTP 200/secret response 丢失。
- iPhone 收到 response 后 Keychain 写入失败。
- 配对 UI lifecycle 使 run ID 失效或 task 被取消。

### 8.2 根因

- Mac 在返回 secret 前已生成 deviceID/secret、upsert 设备、清除 challenge 并标记 paired：`RokuricsMac/PairingManager.swift:107-121`。
- HTTP 200 和 secret 在之后才发送：`RokuricsMac/SecureLocalHTTPSServer.swift:765-783`。
- iPhone 收到结果后先检查 view/run/task 仍有效，之后才写 Keychain：`Rokurics/MacConnectionView.swift:492-508`。
- 页面离开会取消 pairing task 并清 run ID：`Rokurics/MacConnectionView.swift:187-190`、`Rokurics/MacConnectionView.swift:762-778`。
- Mac UI 发现已有 device record 后会隐藏正常配对区域：`RokuricsMac/MacIPhoneConnectionView.swift:28-33`。

### 8.3 影响

Mac 已认为配对成功，iPhone 却没有 secret。原配对码已失效，用户通常只能两端人工清理后重新配对。

## 9. P1：Mac 地址发现和地址生命周期不适合正常网络变化

### 9.1 配对后地址永久冻结

- Mac 将配对时的数字 IP 写入 payload：`RokuricsMac/SecureReceiverService.swift:1626-1645`。
- iPhone 将 host 写入 UserDefaults：`Rokurics/SecureMacConnectionSettings.swift:309-345`、`Rokurics/SecureMacConnectionSettings.swift:424-435`。
- 后续请求直接使用该 host：`Rokurics/SecureMacUploadClient.swift:1586-1597`。
- 仓库不存在 Bonjour、`NWBrowser`、`NWPathMonitor` 或 paired host 更新协议。

正常 DHCP 续租、切换 Wi‑Fi/热点/以太网、Mac 网络接口改变后，heartbeat、同步和上传都会继续访问旧地址；普通 retry 不会修复，只能重配。

### 9.2 地址筛选实现错误

- 只枚举 `AF_INET`，不支持 IPv6：`RokuricsMac/MacLocalNetworkAddressProvider.swift:48-55`。
- 只选择所谓 private IPv4：`RokuricsMac/MacLocalNetworkAddressProvider.swift:17-28`。
- `is172PrivateIPv4` 没检查第一段必须为 `172`，任意 `x.16...31.y.z` 都可能被误判：`RokuricsMac/MacLocalNetworkAddressProvider.swift:113-119`。
- 只检查 `IFF_UP`，不检查 `IFF_RUNNING`、默认路由或 iPhone 可达性。
- iPhone host normalization 会按第一个冒号截断 IPv6：`Rokurics/SecureMacConnectionSettings.swift:458-466`、`Rokurics/MacConnectionView.swift:695-703`。

### 9.3 影响

- IPv6-only、IPv4 link-local、CGNAT、企业地址段可能无法生成配对 payload。
- VPN、多网卡、残留但不可达接口可能被错误选中。
- 即使未来传入 IPv6，iPhone 也会把 host 截断。

## 10. P1：Mac 手动同步 signal 在对端确认前就被删除

### 10.1 触发条件

Mac 点击“立即同步”，iPhone 收到 heartbeat response 前后发生一次正常短暂丢包，尤其是 `/sync/start-ack` 请求或响应失败。

### 10.2 根因

- Mac `consumePendingSyncStartSignal` 会立即从两个 pending 容器移除 signal：`RokuricsMac/ConnectionSyncStateStores.swift:340-351`。
- heartbeat handler 在构造 response 时就调用 consume：`RokuricsMac/SecureLocalHTTPSServer.swift:540-551`。
- iPhone 收到 response 后才发送 `/sync/start-ack`：`Rokurics/StudyLibrarySyncCoordinator.swift:1708-1729`。
- Mac timeout 逻辑只检查仍在 pending dictionary 的 signal：`RokuricsMac/ConnectionSyncStateStores.swift:651-667`；已 consume 但未 ACK 的 signal 不会超时或重发。
- pending signal 本身只在内存中，Mac 重启也会丢失。

### 10.3 连接状态误分类

iPhone 在 heartbeat 已成功并记录 online 后发送 sync ACK。ACK 失败会落入同一个 heartbeat catch，执行 `recordHeartbeatFailure`：

- heartbeat success：`Rokurics/StudyLibrarySyncCoordinator.swift:1641-1647`
- ACK：`Rokurics/StudyLibrarySyncCoordinator.swift:1708-1729`
- 错误归入 heartbeat failure：`Rokurics/StudyLibrarySyncCoordinator.swift:1750-1762`

### 10.4 影响

- Mac 的手动同步请求永久丢失。
- UI 可能停留在“iPhone 已收到同步请求”，但实际没有 sync tick。
- 同一次 ACK 失败还会增加 heartbeat miss，错误显示 interrupted/offline。

## 11. P1：上传 ledger 不按 pairing/目标 Mac 失效

### 11.1 触发条件

- iPhone 曾向 Mac A 上传过 metadata，之后改配 Mac B。
- Mac 接收库被清空，但 iPhone 仍保留 upload ledger。
- 重新配对产生新的 deviceID。

### 11.2 根因

- upload job 保存 `targetDeviceID` / `targetMacName`：`Rokurics/RecordingUploadCoordinator.swift:2777-2833`。
- `RecordingUploadJobStore.ensureJob` 只按 recordingID 返回旧 job，不比较当前 `settings.deviceID`：`Rokurics/RecordingUploadCoordinator.swift:2975-2987`。
- 只要旧 job 的 metadata stage 是 succeeded，客户端会直接伪造 metadata already uploaded，不发 metadata 请求：`Rokurics/RecordingUploadClient.swift:454-480`。
- Mac 接收 audio 前要求 recording directory、metadata.json 和 receive.json 已存在：`RokuricsMac/MacRecordingFileStore.swift:2156-2178`。
- failure classifier 只把 `recording_audio_conflict` 视作 fatal，`recording_metadata_missing`/一般 audio error 会继续 retry：`Rokurics/RecordingUploadCoordinator.swift:2854-2868`。

### 11.3 影响

新 Mac 永远收到 `recording_metadata_missing`，而 iPhone 永远认为 metadata 不需要重传，形成无上限重试循环。

## 12. P1：status envelope 在传输成功前就标记为已发送

### 12.1 根因

- `CanonicalStatusExchangeRuntime.makeOutgoingEnvelope` 把全部 unsent facts 放进单一 envelope，没有分页或字节预算：`RokuricsShared/SyncCore/CanonicalStatusExchangeRuntime.swift:127-149`。
- 在真实 HTTP 请求发送前就从队列 `removeFirst()` ack/request，并把 fact signature 加入 `sentFactSignatures`：同文件第 151-167 行。
- iPhone 随后才真正发送 heartbeat：`Rokurics/StudyLibrarySyncCoordinator.swift:1578-1628`。
- heartbeat request verifier 上限为 16 KiB：`RokuricsMac/RequestVerifier.swift:86-90`。

### 12.2 重启后的 sequence 问题

- `nextSequence`、`lastSequenceBySender` 只存在内存：`RokuricsShared/SyncCore/CanonicalStatusExchangeRuntime.swift:84-96`。
- 单侧重启后 sequence 从 1 开始，存活 peer 会把它判为 `olderSequence`：同文件第 251-269 行。
- 被拒绝的 envelope 在发送前已经标记 sent，不会自然补发。

### 12.3 影响

- 瞬时网络失败、413 或 peer reject 会永久丢失 status/hash proof、ACK 或 run-sync request。
- 超大 envelope 还能使本来健康的 heartbeat 被拒绝，继而把连接标成失败。

## 13. P1：Mac 在 HTTP 200 后才异步应用 recording-existence metadata

### 13.1 根因

- `/sync/apply-metadata` 先 apply 主 manifest，然后 schedule existence bridge：`RokuricsMac/SecureLocalHTTPSServer.swift:3940-3953`。
- server 随即构造成功 response：同文件第 3999-4010 行。
- 真正 existence apply 在无结构 `Task` 中执行：同文件第 4013-4049 行。
- Task 失败或 conflict 只能在 HTTP 200 之后写本地状态/诊断，无法反馈给 iPhone。

### 13.2 影响

- iPhone 已记录同步成功时，Mac existence ledger 可能尚未更新。
- Mac 进程退出、Task 未运行或 apply conflict 时，没有 durable retry/ack。
- response success 不再代表所有 metadata domain 已持久化。

## 14. P1：legacy/fallback recording metadata 两端 hash schema 不一致

### 14.1 根因

- iPhone 对完整 `RecordingMetadata` 求 hash：`Rokurics/StudyLibrarySyncCoordinator.swift:2424-2445`。
- Mac 对 `StudyItemMetadata` 求 hash：`RokuricsMac/SecureLocalHTTPSServer.swift:1128-1144`。
- legacy planner 把两个不同 schema 的 hash 当作同一 content signature 比较：`RokuricsShared/SyncCore.swift:215-244`。
- iPhone recording timestamp 常用 createdAt，Mac 又可能使用 receivedAt；普通上传后 Mac 往往看起来更新。

### 14.2 影响

canonical gate 只要因为 conflict、缺 manifest 或 unsupported object 回退 legacy，已经同步的录音也可能持续产生 metadata download/apply 或 conflict，无法得到稳定 no-op。

## 15. P1：当前源码强制 canonicalFullSync，忽略设置和 fail-closed 文档

### 15.1 根因

`CanonicalKernelSwitchConfiguration.debugStoredConfiguration` 和 `runtimeConfigurationFromStoredDefaults` 都忽略 UserDefaults，固定返回 `.runtimeCanonicalFullSync`：

- `RokuricsShared/SyncCore/CanonicalKernelSwitch.swift:697-709`

该模式接管：

- connection
- sync planning
- apply
- existence
- transfer
- audio upload
- read projection

证据：`RokuricsShared/SyncCore/CanonicalKernelSwitch.swift:910-919`。

真实 iPhone app service 和 Mac app 均读取该固定结果：

- `Rokurics/StudyLibrarySyncCoordinator.swift:11078-11114`
- `RokuricsMac/RokuricsMacApp.swift:20-67`

### 15.2 影响

- 用户或测试设置的 oldKernel/canonicalDecisionOnly 不生效。
- 运行态与文档、测试预期相反。
- 本报告中的 canonical status、apply、sequence 问题是当前真实 app path，而不只是试验代码。

## 16. P1（当前被 P0 遮蔽）：artifact 分块续传可假成功或永久卡死

### 16.1 artifact ID 和 temp 文件不绑定内容版本

- artifactID 只由 kind/owner/path 生成，不包含 checksum/version：`Rokurics/StudyLibrarySyncModels.swift:3045`。
- Mac status 只按 `<artifactID>.part` 大小返回 resume offset，无法证明 temp 属于当前 checksum/size：`RokuricsMac/SecureLocalHTTPSServer.swift:4272`。
- temp 名只由 artifactID 决定：`RokuricsMac/SecureLocalHTTPSServer.swift:4693`。
- final checksum 失败后不会清理 temp：`RokuricsMac/SecureLocalHTTPSServer.swift:4731`。

### 16.2 iPhone 可把未应用文件误标完成

- status 返回 `.resuming` 且 offset 等于 fileSize 时，上传循环不会执行：`Rokurics/StudyLibrarySyncCoordinator.swift:9784-9839`。
- 随后客户端只凭本地 offset 到达 fileSize 就记录 checksum verified、peer applied、complete，没有要求 Mac 返回 `.complete`：`Rokurics/StudyLibrarySyncCoordinator.swift:9888`。

### 16.3 下载方向同类问题

- iPhone 本地 temp 仅按 artifactID 恢复，不核对 checksum/version：`Rokurics/StudyLibrarySyncCoordinator.swift:9362-9377`。
- checksum 失败 catch 不删除 temp：`Rokurics/StudyLibrarySyncCoordinator.swift:9263-9289`。
- 下次继续验证同一错误 full-size temp，形成永久失败。

### 16.4 当前状态

由于第 4 节 P0，相关 helper 当前没有进入生产调用；一旦简单恢复调用，这些续传缺陷会立即成为真实文件损坏/假成功风险，必须一起修复。

## 17. P1/P2：stale resumable audio session 无清理途径且无限重试

### 17.1 根因

- Mac 发现相同 recording/source 已有参数不一致 session 时返回 `upload_session_conflict`：`RokuricsMac/MacRecordingFileStore.swift:991`。
- session 枚举会忽略 status 为 `expired` 的记录，但仓库没有正常逻辑把 session 标成 expired 或清理：`RokuricsMac/MacRecordingFileStore.swift:2355`。
- start/chunk/finalize server errors 被包装为 audio upload failed：`Rokurics/RecordingUploadClient.swift:687`、`:782`、`:819`。
- classifier 不把 `upload_session_conflict`、`upload_chunk_checksum_mismatch` 视作需要重建 session 的 fatal/recovery 状态：`Rokurics/RecordingUploadCoordinator.swift:2863-2868`。
- retry delay 只在 600 秒封顶，没有次数上限：`Rokurics/RecordingUploadCoordinator.swift:2898`。

### 17.2 触发条件和影响

上传中断后本地文件 hash/size 变化、chunk size 版本变化或两端 session ledger 不一致时，上传可能永远冲突并无限重试。

## 18. P2：首次本地网络权限可能让第一次配对先失败

- iPhone 已配置 Local Network 使用说明：`Rokurics/Info.plist:23-29`。
- 所有 pinned URLSession 明确设置 `waitsForConnectivity = false`：`Rokurics/SecureMacUploadClient.swift:1568-1572`。
- health check / pair 没有自动 retry：`Rokurics/SecureMacUploadClient.swift:153-260`。

首次访问本地网络时，系统权限弹窗尚未得到用户响应，请求可能立即失败。用户随后点“允许”也需要再次手动点击检查/配对。参考：[Apple TN3179](https://developer.apple.com/documentation/Technotes/tn3179-understanding-local-network-privacy)。

## 19. P2：过期配对码仍持续显示并允许复制

- pairing code 有效期 5 分钟：`RokuricsMac/PairingManager.swift:47-60`。
- 过期只在收到请求或显式 `refresh(now:)` 时处理：同文件第 94-98、124-131 行。
- `SecureReceiverService` 没有按 expiresAt 安排 timer，只在其他事件触发时 refresh：`RokuricsMac/SecureReceiverService.swift:1482-1495`。
- UI 只要旧 payload 仍在就继续显示/允许复制：`RokuricsMac/MacIPhoneConnectionView.swift:148-185`。

用户会复制一个 UI 看似有效、实际必然被 server 拒绝的 code。

## 20. P2：Mac 配对持久化失败仍返回成功

- `PairedDeviceStore.upsert` 先修改内存，再调用无返回值 `save()`：`RokuricsMac/PairedDeviceStore.swift:102-110`。
- `save()` 吞掉写盘错误，只更新 `lastError`，不抛出、不回滚：同文件第 174-185 行。
- `PairingManager.completePairing` 因此仍返回 secret，HTTP route 仍返回 200。

磁盘满、权限或 I/O 错误时，本进程内看似配对成功；Mac 重启后设备消失，iPhone 后续只会得到 `unknown_device`。

## 21. P2：离线执行 unpair 会留下双端状态分裂

- iPhone disconnect 路径会清理本地 credential，再尝试 remote unpair；失败后没有 durable retry：`Rokurics/MacConnectionView.swift:632-664`。
- Mac disconnect 会停止 server 并清除本地 device，无法通知离线 iPhone：`RokuricsMac/SecureReceiverService.swift:1060-1077`。

一端仍认为已配对、另一端已删除 secret 的状态无法自动修复，需要人工双端清理。

## 22. P2：整包 manifest 4 MiB 硬限制且没有分页

- manifest 包含全部 items、folders、tombstones、pendingUploads、recordings：`Rokurics/StudyLibrarySyncModels.swift:1263-1305`。
- request 只有一个完整 manifest，没有分页或增量 batch。
- `/sync/apply-metadata` verifier 上限为 4 MiB：`RokuricsMac/RequestVerifier.swift:121-124`。
- manual sync 还会通过 `forceSend` 发送完整 local manifest，即使没有 metadata diff：`Rokurics/StudyLibrarySyncCoordinator.swift:4520-4526`、`:9200-9209`。

库规模达到阈值后，manual/metadata sync 会稳定返回 413，且不存在缩小批次后的 retry。

## 23. P2/性能风险：首次 inventory 可能超过 iPhone 10 秒超时

- iPhone `/sync/inventory` request/resource timeout 约为 10/20 秒：`Rokurics/SecureMacUploadClient.swift:441-458`。
- Mac 在生成 response 前遍历 recording inventory，并 await checksum：`RokuricsMac/SecureLocalHTTPSServer.swift:5624-5704`。
- checksum cache miss 会读取完整文件、计算 SHA256 并持久化：`RokuricsShared/SyncCore/CanonicalInventoryRuntime.swift:637-674`。

大量或大体积录音、首次运行、缓存失效时，inventory 可能在正常磁盘和网络条件下超时。是否在目标设备稳定超过阈值需要真机 benchmark。

## 24. P2：inventory/manifest hash 不是内容稳定 hash

- `StudyLibrarySyncManifest.computedChecksum` 包含 `generatedAt`：`Rokurics/StudyLibrarySyncModels.swift:1308-1320`。
- `LocalNetworkSyncInventory.inventoryHash` 包含每轮变化的 `generatedAt`、`inventoryRevision`、`lastKnownPeerRevision`：同文件第 1814-1831 行。
- `inventoryRevision` 又来自包含 generatedAt 的 device section。

内容完全不变时 hash/revision 也会改变，并通过 `lastKnownPeerRevision` 双向回灌。当前 planner 主要比较 object hash，因此这更偏性能、缓存、delta/status churn 和诊断语义缺陷，但会放大 16 KiB status envelope 问题。

## 25. P2：空文件会确定性失败并产生无意义重试

### 25.1 空 generated artifact

Mac `/sync/artifact-request` 要求 `length > 0` 且 `offset < fileSize`：`RokuricsMac/SecureLocalHTTPSServer.swift:4154`。合法的 0-byte transcript/note 无法下载。

### 25.2 空 audio

- iPhone 只检查文件存在及不超过 max bytes，没有 `audioSize > 0` guard：`Rokurics/RecordingUploadClient.swift:297-325`。
- Mac small upload route 拒绝 content length 0：`RokuricsMac/SecureLocalHTTPSServer.swift:2115`。
- 错误会进入一般 retryable audio failure。

## 26. 高置信并发和运行时风险

以下风险有明确共享状态或队列证据，但仍需要 TSan、压力测试或真机交错执行确认最终表现。

### 26.1 app-global 与 UI 存在独立 sync/upload runtime owner

- app 入口创建 `LocalNetworkSyncAppService`：`Rokurics/RokuricsApp.swift:11-25`。
- app service 自己创建 AudioFileStore、RecordingManager、connection store、upload job store、upload coordinator、engine、scheduler：`Rokurics/StudyLibrarySyncCoordinator.swift:11045-11314`。
- UI 另外创建 RecordingManager/connection store/upload coordinator：`Rokurics/ContentView.swift:10-20`、`Rokurics/RokuricsHomeView.swift:10-35`。
- MacConnectionView 再创建独立 `StudyLibrarySyncCoordinator`，manual sync 每次新建 LocalNetworkSyncEngine：`Rokurics/MacConnectionView.swift:85-118`、`Rokurics/StudyLibrarySyncCoordinator.swift:554-609`。
- `isSyncing` 和 `uploadTasks` 都是实例内 gate，无法阻止另一个实例同时运行。
- `RecordingUploadJobStore` 使用无锁的 load-modify-write/replace：`Rokurics/RecordingUploadCoordinator.swift:2924-2995`、`:3280-3355`。

周期 tick、事件 tick、手动同步和手动上传重叠时，可能产生重复请求、一个 ledger write 覆盖另一个、错误恢复仍在运行的 job 或 UI 状态跳变。

### 26.2 `recoverStaleInProgressJobs` 没有 age/liveness 判定

- 新上传/重试会调用 stale recovery：`Rokurics/RecordingUploadCoordinator.swift:843`。
- recovery 会把所有 in-progress stage 当作 interrupted，没有判断它是否仍由另一 coordinator 实际执行：同文件第 3192 行起。

多录音并发或双 coordinator 重叠时，后启动任务可能破坏先启动任务的 ledger 状态。

### 26.3 Mac server activeConnections 跨队列无锁访问

- listener queue 的 connection handler/state callback 增删普通 Dictionary：`RokuricsMac/SecureLocalHTTPSServer.swift:1914-1943`。
- `stop()` 可从 MainActor/UI 直接遍历并 `removeAll`：同文件第 1777-1784 行。

用户在 heartbeat/upload 进行中断开、restart server 或 runtime switch 时，存在并发访问、崩溃或漏取消风险。

### 26.4 Debug/local 与 Release 共用固定端口并允许 reuse

- Debug/local 与 Release 使用不同 bundle/storage/TLS identity，但 receiver port 都是 8787：`RokuricsMac/MacAppStorageProfile.swift:10-47`。
- listener 设置 `allowLocalEndpointReuse = true`：`RokuricsMac/SecureLocalHTTPSServer.swift:1700-1704`。

Xcode Debug 与已安装 Release 同时运行时，请求可能命中另一实例的独立 identity/paired store，表现为间歇 fingerprint mismatch 或 `unknown_device`。现有 listener tests 使用 port 0，未覆盖此场景。

### 26.5 心跳时间余量偏小

- 默认 heartbeat interval 约 3 秒。
- request timeout 约 2 秒。
- 在线证据约 5 秒即进入 stale 判断。
- 每次请求都创建新的 ephemeral pinned URLSession，并伴随两端 JSON 状态持久化。

在 Mac 同时计算 inventory hash、处理上传或写大量状态时，正常负载可能造成 presence 抖动。需要真机延迟注入与长时间观测确认。

### 26.6 iPhone 后台不能持续上传

- 所有请求使用 ephemeral URLSession，普通 Swift Task，没有 background URLSession 或 background execution assertion：`Rokurics/SecureMacUploadClient.swift:1568-1583`。
- app scene 进入非 active 会 suspend app-global sync service：`Rokurics/RokuricsApp.swift:21-26`。

锁屏、切后台或进程终止会中断传输。audio ledger 可在回到前台后尝试恢复，但不会在后台持续执行。

### 26.7 canonical status node identity 在首次配对前固定

`LocalNetworkSyncAppService` init 时使用当时的 `connectionStore.snapshot.deviceID` 构造 `CanonicalStatusExchangeRuntime`：`Rokurics/StudyLibrarySyncCoordinator.swift:11078-11092`。首次安装未配对时 nodeID 会固定为 `iphone-`；pairing changed 只 refresh store/start services，不重建 runtime：同文件第 11389-11397 行。

当前部分 envelope 使用 destination nil，因此这不是已证实的连接阻断，但会造成 status fact producer identity 不反映真实 pairing，并可能在重配/多设备时发生身份碰撞或诊断污染。

## 27. 当前双向文件传输的产品边界

项目明确禁止 Mac 主动反向连接 iPhone：`docs/DO_NOT_BREAK.md:13`。因此当前不是通用双向文件发送系统。

设计边界是：

- **iPhone→Mac**：录音 metadata/audio 上传；部分 artifact put。
- **Mac→iPhone**：iPhone 主动 pull Mac 上的 receive/transcript/note/summary JSON/Markdown 等允许类型。
- **明确不支持**：Mac 主动拨号 iPhone、Mac 本地录音 audio 自动发送到 iPhone、任意附件/资源的通用双向发送。
- recording audio 的 Mac→iPhone 自动下载被明确禁用：`Rokurics/StudyLibrarySyncModels.swift:1730`、`:3092`。

即使按这个受限定义，当前 P0 仍使 sync 驱动的 iPhone→Mac 自动补传和 Mac→iPhone artifact pull 都不执行。

## 31. 修复优先级建议

### 第一批：恢复正确性

1. 恢复 `downloadPeerArtifactsIfNeeded`、`uploadLocalArtifactsIfNeeded`、`uploadMissingRecordingAudioIfNeeded` 的受控调用。
2. 成功条件改为：所有必需 metadata/content action 完成、无 unresolved conflict、无 partial failure；否则保留 pending/failed。
3. 同步状态中区分 metadata completed、content pending、conflict、partial failure 和 fully completed。

### 第二批：修复确定性分叉

1. iPhone rename 必须推进统一业务 `updatedAt`。

## 32. 初始审查结论（修复前）

当前最需要先修的不是 UI 或重试次数，而是“真实完成”的定义：

1. 连接必须在双方都持有可恢复身份并能找到当前 endpoint 后才成立。
2. 同步必须在 metadata apply 无 conflict/partial failure 后才可标记成功。
3. 文件传输必须在 peer 明确确认最终文件存在、大小/hash 正确且已持久化后才可标记完成。

修复前实现同时违反了第 2、3 点，并在配对半提交和地址冻结场景下违反第 1 点。只增加 retry 或调整 UI 文案不能解决这些根因。

## 33. 2026-07-10 P0/P1 修复结果

### 33.1 最终结论

本文识别的全部 P0/P1 已在源码层修复。当前自动化证据证明：同步执行器会真实执行已规划的 metadata、artifact 和缺失录音音频动作；只有在无未解决冲突、无 partial apply、所有必需内容均得到对端最终确认后，才会记录完整成功。

仍未取得的是两台真实设备在网络切换、首次本地网络授权、前后台切换和长时间运行下的现场证据。因此本轮可以确认“实现和自动化回归已闭环”，不能把它扩大表述为“真机环境稳定性已经验收”。

### 33.3 修复期间追加发现并修复的正常失败原因

- **fallback metadata 时钟漂移**：iPhone/Mac 在缺少持久 StudyItem 时曾用 `Date()` 重建 `updatedAt`，使同一内容每轮得到不同 hash 并触发假冲突。现在分别使用持久的 recording `endedAt` / inbox `receivedAt`。
- **完成状态被进度任务回写覆盖**：音频上传结束后，取消中的 progress task 仍可能把 transfer job 从 `.complete` 写回 `.transferring`。现在 cancellation 会终止任务，并在最终状态落盘前等待任务退出。
- **冲突诊断被脱敏器整条拒绝**：artifact ID 中的完整 hash 会使诊断变成 `redactionRejected`。现在只写 object/hash prefix，保留 winner/loser、双方 hash prefix 和业务时间。
- **同一 tick 被拆成两个 syncRunID**：post-transfer 验证 snapshot 现在复用原 syncRunID，保证端到端诊断关联。

## 34. 2026-07-10 端口占用后的逐次迁移

真机测试补充发现：Mac HTTPS listener 在默认 8787 被占用时，旧实现会在同一个 8787 上重试一次，因此第二次仍然确定失败，配对码无法生成。

现已修复为：

- 只在 Network framework 明确返回 `EADDRINUSE` / POSIX 48 时递增候选端口；TLS identity、证书或一般 listener 错误不会触发换端口。
- 第一次 8787 绑定失败后，`SecureReceiverService.port` 立即变为 8788，清除旧 pairing payload，并提示用户再次点击配对。
- 下一次点击使用 8788；若再次收到 `EADDRINUSE`，候选端口变为 8789，依次类推。到达 65535 后回到 8787。
- 递增后的候选端口写入当前 Mac app profile 的 UserDefaults；Mac 重启后仍监听已经复制给 iPhone 的端口，不会无故跳回 8787。
- 不再在同一个已占用端口上做无意义重试，也不会一次点击自动扫描一串端口。
- Mac 只有在新 listener 真实进入 ready 后才生成配对码；复制文本中的 `Port:` 来自 listener 的实际 active port。
- iPhone 粘贴解析读取复制文本中的动态 `Port:`，8787 仅作为没有粘贴信息时的初始默认值。

新增自动化证据：Mac 测试真实占用一个随机 TCP 端口，确认第一次配对把端口加一、第二次点击在新端口成功并发布 matching payload；独立测试确认 8788 可跨 service/app launch 持久读取；iPhone 测试确认 `Port: 8788` 被解析为 8788。
