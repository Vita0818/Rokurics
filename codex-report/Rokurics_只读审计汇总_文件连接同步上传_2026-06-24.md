## 1. 总体结论

Rokurics 当前不是单一旧链路，也不是纯 canonical 链路。真实形态是：

- 业务读写仍大量依赖旧 store 和旧文件格式。
- canonical core 已大面积接入，默认 runtime 配置固定走 `canonicalFullSync`，但多个域仍带 legacy fallback。
- UI 状态已经混入 canonical projection / effective status，但旧字段如 `RecordingMetadata.uploadStatus`、upload ledger、`activeStatuses` 仍直接影响按钮和展示。
- 连接层仍以 Mac 作为本地 HTTPS server，iPhone 主动请求 Mac。Mac 端“手动同步”不是 Mac 直接拨 iPhone，而是写入 pending signal，等待 iPhone 后续 heartbeat/status 请求取走。
- 上传链路默认先尝试 canonical transfer，再尝试 canonical audio upload runtime，再落回 legacy secure upload。失败后 fallback 并不保证只发生在“零副作用”阶段，这是当前上传重复尝试和状态分叉的核心风险。

最接近真机验证的链路：iPhone 上传录音到 Mac 的 resumable upload。  
最不可靠的链路：Mac 发起的手动同步 pending signal，以及 canonical side effect 后的 legacy fallback。

### 2.3 已证实薄弱点

- Mac resumable finalize 会先写 final file、`receive.json`、session completed，再发 HTTP response；canonical proof fact 在 response 后异步生成。文件事实与 canonical proof 不是同一个 durable 事件。
- `MacRecordingFileStore.appendResumableAudioChunk` 先 append partial file，再保存 session manifest；两步之间崩溃会留下 part file size 大于 manifest `receivedBytes` 的状态，后续重试可能变成 `sessionConflict`。
- Mac inbox 刷新依赖 `postInboxChanged()` → `AudioInboxStore.refreshRecordingInbox()`；resumable chunk/finalize 路径有通知，但其它 metadata/apply/artifact/rename/delete 入口需要逐项确认是否都触发同等刷新。
- UI 可能混读 legacy 与 canonical：`RecordingMetadata.uploadStatus` 可为 uploaded，但 canonical projection 缺失时，UI 仍可能显示 peer proof unavailable / waiting。

  - pairing / TLS / HMAC / nonce / certificate pinning 文件按冻结边界不要随意改。

### 3.2 三个 endpoint

- `/device/status`
  - iPhone `StudyLibrarySyncCoordinator.performHeartbeat()` 会构造 `DeviceStatusRequest` 并发给 Mac。
  - 成功后写入 connected 状态，并可能消费 response 中的 `syncStartSignal`。
- `/connection/heartbeat`
  - `LocalNetworkHeartbeatMonitor` 路径使用；携带 status exchange envelope。
- `/connection/probe`
  - 轻量探测路径。

Mac server route 分发中，`/device/status`、`/connection/heartbeat`、`/sync/inventory`、`/sync/apply-metadata` 已转到 `Task(priority: .utility)`，但 `/connection/probe`、`/sync/start`、`/sync/start-ack` 仍走 MainActor task。

### 3.3 状态语义

- `isPaired` 只表示保存了配对信息，不等价于 reachable、authenticated、online。
- `presenceState` / `DeviceConnectionStatus` 才是在线展示与 scheduler gate 的核心输入。
- `presenceSnapshot().isOnline` 是调度层应依赖的结果；上传按钮当前多处仍主要检查 `isPaired`。
- `monitoringMode` 用于表示 foreground/background 或等待前台响应等状态。
- `lastSyncStatus` 是用户可见状态文本，不等价于同步完成证明。

### 3.4 已证实薄弱点

- iPhone 心跳在已连接且 online 时不会再每次先 `markConnecting`，而是通过 `publishConnectionStatusIfChanged` 门控更新；这降低了每 3 秒 UI 发布抖动风险。
- 上传和部分 UI 操作仍主要 guard `isPaired`，paired=true 但 host/port 失效、pinning 失败、Mac server 未 ready 时，请求仍会失败。
- Mac 手动同步采用 pending signal：`recordPendingSyncRequest` 写入 `pendingSyncStartSignalsByDeviceID`；iPhone 后续 heartbeat/status 被 Mac 响应携带 signal；`consumePendingSyncStartSignal(deviceID:)` 读取时立即删除 pending。若 HTTP response 在网络中丢失，Mac 已认为 “iPhone 已收到同步请求”，iPhone 可能完全没有入队。
- pending signal 按 `deviceID` 分离，但重新配对产生新 deviceID、旧 deviceID 状态残留、UI 选中设备与 status store key 是否一致，仍是多设备风险点。

## 4. 手动同步 / 事件同步 / inventory / apply / canonical-legacy 切换

### 4.1 默认链路

默认 runtime 配置固定为 `canonicalFullSync`，不是纯 oldKernel。iPhone 端 `StudyLibrarySyncCoordinator` 初始化：

- `RecordingManager`
- `RecordingUploadCoordinator`
- `LocalNetworkSyncEngine`
- `CanonicalStatusTruthRuntime`
- `CanonicalStatusExchangeRuntime`
- `SecureMacUploadClient`

手动或事件同步最终进入 `LocalNetworkSyncEngine.performTick(...)`，使用 secure client 访问：

- `/sync/start`
- `/sync/inventory`
- `/sync/apply-metadata`
- `/sync/start-ack`

### 4.2 `/sync/start` 的含义

`/sync/start` 更接近 “server 收到同步启动信号 / 状态机记录请求”，不是业务数据已同步完成。真正业务差异和写盘发生在 inventory/diff/apply 后续阶段。若 `/sync/start` 成功但 `/sync/inventory` 或 `/sync/apply-metadata` 失败，UI 若只读 start ACK 或 `lastSyncStatus`，可能产生“看起来成功”的误导。

### 4.3 event / pending / upload-active defer

事件同步使用：

- `pendingSyncEventReasons`
- `pendingSyncEventRunID`
- debounce task
- `LocalNetworkSyncScheduler.requestTick`

`drainImmediateSyncEventQueue()` 中如果 `uploadCoordinator.hasActiveUploadInFlight()` 为 true，会记录 `syncDeferredBecauseUploadActive` 并重新 schedule drain。因此在进程存活且 active upload 最终清理的情况下，deferred event 有再次执行路径。

仍需注意：

- pending event 只在内存中，不是持久化 durable queue。
- app 终止后 pending reason 丢失。
- alreadyInFlight 使用合并/排队语义，不保存完整事件集合的全部顺序与 payload。
- manual peer sync 会走同一事件队列，受 debounce、offline、background、upload-active 影响。

### 4.4 objectID 分叉

同步与上传中 objectID 不统一：

- 录音音频 canonical projection / fact：`recordingAudio:<id>`
- legacy recording metadata / route：裸 `<id>`
- generated artifact：`generatedArtifact:<artifactID>` 或 artifact key
- upload route request `recordingID`：裸 `<id>`

转换应只存在 route adapter boundary，但目前业务层、UI 层、projection 层都有字符串拼接和 strip 行为。最早风险点出现在 UI 查询 canonical display state 与 upload coordinator active status 查表：前者用 `recordingAudio:<id>`，后者用裸 `<id>`。

## 5. iPhone 上传录音到 Mac

### 5.1 默认 Release 精确路径

默认 Release / DEBUG 在当前源码下同走：

1. `RecordingLibraryView` 或 `RecordingStudyDetailPage` 点击上传。
2. UI 调 `RecordingUploadCoordinator.upload(...)`。
3. coordinator 创建 `uploadTasks[metadata.id]`，使用裸 recording id 做 active key。
4. `uploadAndWait(...)` 先跑 `RecordingAudioUploadDecisionEvaluator`。
5. 先尝试 `uploadViaCanonicalTransferRuntimeIfEnabled(...)`：
   - `CanonicalTransferRuntime`
   - `IPhoneCanonicalTransferAdapter`
   - `SecureMacUploadClient`
   - `/upload-recording-audio-session/start`
   - `/upload-recording-audio-session/status`
   - `/upload-recording-audio-session/chunk`
   - `/upload-recording-audio-session/finalize`
6. 若 transfer runtime 返回 nil，再尝试 canonical audio upload runtime：
   - `IPhoneAudioUploadCutoverExecutor`
   - `CanonicalAudioUploadRuntimeExecutor`
   - `IPhoneCanonicalSecureAudioUploadPort`
   - 同一组 resumable secure endpoints
7. 若 canonical audio runtime 也返回 nil，再走 legacy：
   - `RecordingUploadClient.uploadRecording`
   - 先 `/upload-recording-metadata`
   - 小文件走 `/upload-recording-audio`
   - 大文件走 resumable start/status/chunk/finalize

### 5.2 按钮逻辑

- `RecordingLibraryView` 与 `RecordingStudyDetailPage` 读取 canonical display state：`recordingAudio:<id>`。
- 点击 guard 主要检查 `isPaired`，不检查 online、active upload、ledger、finalizing。
- presentation 对 `.completed` / `.peerVerified` 仍可 enabled，只要 paired 且不是 uploading/finalizing。
- `UploadableRecordingRow` 当前未发现调用点；若重新启用，它主要读 legacy `RecordingUploadStatus`，同样对 uploaded/completed 状态存在可点击风险。

### 5.3 no-op / retry / duplicate

`RecordingAudioUploadDecisionEvaluator` 的主要规则：

- peer already has same hash/size：no-op / uploaded。
- transfer or ledger queued/inFlight/finalizing：suppress。
- ledger retryPending：手动上传可重试，非显式触发 suppress。
- peer unknown：manual upload 可强制上传，周期/普通事件倾向 waiting。
- peer different：conflict，不覆盖。

薄弱点：canonical transfer 已经 start/chunk/finalize 后，runtime error 或 proof missing 会返回 nil 并继续 fallback。fallback 不保证只在零副作用阶段发生。

### 5.4 resumable 幂等性

Mac server 行为：

- same offset + same length/hash 且 manifest 已记录：`acceptedExisting`。
- same offset + different hash：conflict。
- offset 不等于 `receivedBytes`：offset mismatch，session error。
- final file 已存在且 hash/size 相同：completed / acceptedExisting。
- final file 已存在但 hash 不同：audio conflict。

不足：

- append partial file 先于保存 session manifest；崩溃窗口会让 retry 无法幂等恢复。
- `MacRecordingFileStore` 未体现 actor/per-session lock；并发 chunk 可能同时读取旧 manifest 并 append。
- iPhone 上传前会重新算 size/hash，但 chunk 读取期间未发现对 file identity / mtime 的持续验证；上传中途文件被替换时，最终靠 Mac checksum 拦截。

### 5.5 finalize proof 缺口

Mac finalize 成功后：

1. partial file move 到 final audio。
2. receive record 写 complete。
3. session manifest 写 completed。
4. `postInboxChanged()`。
5. HTTP response 返回 iPhone。
6. response 之后启动 async `Task` 生成 canonical transfer finalize proof fact。

`CanonicalStatusFactStore` 是内存 map，未发现持久化 outbox。因此：

- finalize response 已被 iPhone 收到，Mac 立刻退出：文件已到、receive complete，但 Mac-side finalize proof fact 可永久缺失。
- 重启后未发现自动扫描 completed receive/audio 并补发 finalize proof 的路径。
- 后续 inventory 可产生 peer inventory proof，但不是 finalize proof。

## 6. 风险优先级

1. canonical side effect 后 fallback legacy  
   - 现象：同一次上传可能先 canonical start/chunk/finalize，再 legacy 重进。
   - 风险：重复请求、metadata 重写、session conflict、状态震荡。

2. finalize response 与 proof fact 非同一 durable 事件  
   - 现象：文件已在 Mac，但 canonical proof 永远缺失。
   - 风险：iPhone UI 等 proof，Mac UI 显示已收到，两端状态分叉。

3. pending sync signal 非可靠投递  
   - 现象：Mac 点同步后 pending 被 heartbeat 消费并删除，但 response 丢失。
   - 风险：Mac 显示 iPhone 已收到，iPhone 实际没有入队。

4. paired 与 online 混用  
   - 现象：按钮可点，但请求必然失败。
   - 风险：用户感知“无反应”。

5. chunk append 与 manifest 保存非事务  
   - 现象：崩溃或写失败后 resume 变 conflict。
   - 风险：断点续传不是真正幂等。

6. UI completed/peerVerified 仍允许点击  
   - 现象：“已上传”仍能再次触发上传。
   - 风险：重复上传、状态回退、按钮误导。

7. objectID key 分叉  
   - 现象：`recordingAudio:<id>` 与裸 `<id>` 同时存在。
   - 风险：查不到 active upload、查不到 proof、重复 start session、UI 显示错误。

## 7. 下一轮最小修改方向

不要先动安全链路、配对、TLS、HMAC、nonce、证书、首页视觉动画。

建议优先级：

1. 上传 fallback：canonical 一旦发生 start/chunk/finalize 副作用，禁止直接 legacy 重开；只能 status/resume 同一 session，或明确返回 retry/conflict。
2. finalize proof：增加 durable outbox 与启动补偿扫描；completed receive/audio 存在但 proof 缺失时自动补发 fact。
3. chunk 原子性：为每个 session 加串行化；修复 append partial 与 manifest 保存之间的崩溃恢复。
4. UI guard：上传按钮除 paired 外增加 online、active upload、ledger finalizing/completed、canonical proof 状态；completed/peerVerified 点击改 no-op 或禁用。
5. pending sync：`consumePendingSyncStartSignal` 不应在 HTTP response 可靠送达前永久删除；增加 ack 或 syncRunID completion 闭环。
6. objectID 规范化：业务层统一 canonical key，route boundary 单点 strip 到 bare id。
7. event queue：需要持久化或至少 foreground 恢复扫描，避免 background/termination 丢失 deferred sync。
