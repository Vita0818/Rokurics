# Rokurics iPhone / Mac 同步卡顿与失败分层原因报告

- 报告日期：2026-07-12
- 审计范围：最近一次 iPhone / Mac 开发会话日志、同步状态快照及相关 Swift 实现
- 审计方式：本报告主体保留修复前只读诊断；2026-07-12 已按第 9、10 节完成源码拆层与本地验证
- 核心分类：同步层“做了不该做的事”与“本来该做，但多做了或做错了”

> 修复状态：active“立即同步”现已收敛为每端单次 inventory snapshot、单次 inventory exchange、单次 diff 和有界 run summary；metadata apply、placeholder、artifact/audio bytes、Store mutation、upload job/retry/finalize 均不再进入同步路径。conflict 返回 completed diff。scheduler 不再用 future-timer cancellation 取消 active run。内容传输只由学习库按钮创建独立 iPhone -> Mac 或 Mac -> iPhone job。下文问题描述保留为修复前证据与防回归依据。

## 1. 结论摘要

当前“立即同步”并不是轻量的文件清单交换。它实际串联了 inventory、diff、metadata apply、placeholder 创建、artifact 上传/下载、缺失录音音频上传、Store 保存、retry、内容证明和最终完成判断。因此，用户点击一次“立即同步”，系统事实上同时执行了同步层和上传层。

最近日志显示，卡顿的首要原因不是重复计算大文件 hash。最近一轮 iPhone 有 54 次 checksum cache hit，Mac 有 53 次 checksum cache hit，没有观察到 miss、stale 或 recompute。真正的主要耗时来自文件内容传输、约 70 次重复 inventory 构建、逐对象 Store 保存与发布风暴。

最近失败也不是普通 Wi-Fi 或 HTTPS 不通。系统已经成功交换 inventory，并实际传输了 69 个 artifact；这本身证明 TLS、请求签名和局域网传输至少在该阶段可以工作。失败发生在业务状态机内部：第一轮因 4 个 unresolved conflict 被错误判为整轮失败；后续重试在 metadata apply 阶段因 scheduler/presence 与当前 tick 的取消关系报 `cancelled`，同时 Mac 端仍继续完成了部分 apply。

必须先恢复产品层次：

1. 连接只做短握手、鉴权和在线状态。
2. “立即同步”只构建并交换 inventory，计算 added/deleted/modified/same/conflict/deferred。
3. 学习库内用户点击“上传”后，才执行 iPhone -> Mac 或 Mac -> iPhone 的实际文件内容传输。

## 2. 本报告采用的同步定义

同步是只读发现过程：

- 获取两端学习库文件的稳定标识或逻辑文件名。
- 获取或复用内容 hash、byte size、业务修改时间和版本。
- 交换 tombstone/删除标记等差异判断所需的短字段。
- 计算新增、删除、修改、相同、冲突和信息不足。
- 返回并持久化有界的差异结果。

同步不做以下事情：

- 不交换音频、转写、笔记、summary 或附件的文件 bytes。
- 不返回或接收 `dataBase64`。
- 不 apply metadata。
- 不创建 placeholder。
- 不 merge/save 学习库对象。
- 不物理删除文件。
- 不创建、恢复或执行内容上传任务。
- 不因发现 conflict 而判定同步失败。

## 4. 卡顿原因：同步层做了不该做的事

### 4.1 在“立即同步”中传输了 artifact 文件内容

当前执行顺序直接调用：

- `uploadLocalArtifactsIfNeeded(...)`
- `downloadPeerArtifactsIfNeeded(...)`

最近一轮因此串行传输了 69 个 artifact，耗时约 56 秒。Mac artifact response 还会读取文件并返回 `dataBase64`。

这不是同步慢，而是上传层工作被塞进了同步层。只要 artifact 或音频较大，“立即同步”的耗时就会自然接近真实文件上传/下载耗时，完全失去轻量清单交换的意义。

正确归属：这些动作只能由学习库内用户点击“上传”后启动，并拥有独立的 transfer job、进度和错误状态。

### 4.2 在同步中执行 metadata apply

当前 tick 在 diff 后调用：

- `applyPeerMetadataIfNeeded(...)`
- `uploadLocalMetadataIfNeeded(...)`

这使“发现对端不同”与“立即修改本端或对端”成为同一个动作。同步不再是只读观察，而是带副作用的 apply transaction。

直接影响：

- apply 时间被计入同步耗时。
- apply 失败被报告成同步失败。
- 两端可能在同一轮结束前出现部分更新。
- conflict 不再只是差异结果，而会与 apply 能否继续纠缠。

正确归属：同步只返回 modified/conflict；是否应用以及向哪个方向应用，应由后续用户动作决定。

### 4.3 在同步中创建 placeholder 并保存学习库

当前 tick 在执行内容动作前调用 `createPlaceholderTransfers(...)`。最近一轮创建了约 51 个 placeholder。

placeholder 创建会触发 Store 保存、刷新和 UI 发布。它既不是 inventory exchange，也不是 diff 计算，却被放在同步关键路径中。这会把一个本应只读的网络操作变成大量本地持久化操作。

正确归属：同步只输出“对端新增/本端缺少”的对象描述；不得为了预告未来传输而提前创建真实学习库记录。

### 4.4 在同步中自动补传缺失录音音频

当前 tick 调用 `uploadMissingRecordingAudioIfNeeded(...)`，并要求 remaining audio transfer 清零后才能继续成功判定。

这违反了“上传必须由用户在学习库明确点击”的产品边界。普通同步、周期 tick、heartbeat 或 app activation 都不应因为发现 peer missing 就创建新的文件传输。

正确归属：同步可以返回 `peerMissingContent` 或 `uploadSuggested`，但不能创建或执行 upload job。

### 4.5 把内容传输完成证明纳入同步成功条件

当前同步要求 artifact/audio transfer 完成、remaining transfer 清零，并取得内容级 proof 后才记录成功。这实际把同步完成定义成“全库内容已经复制并应用完成”。

正确语义应当是：两端 inventory 成功取得、校验并完成 diff，当前 sync run 就完成。文件是否随后上传属于另一状态机。

## 5. 卡顿原因：同步层本来该做，但多做了或做错了

### 5.1 同一轮重复构建全库 inventory

Mac artifact lookup 会调用 `makeLocalNetworkSyncInventory(sourceKind: .artifactLookup)`。最近一轮约 69 个 artifact 请求导致约 70 次全库 inventory 重建，累计约 19.4 秒。

inventory 是同步层应该做的事，但每端每轮只应构建一次一致性 snapshot。当前实现把“一轮一次”做成了“每个 artifact 一次”。

正确实现：

- 以 `syncRunID + nodeRole + inventoryRevision` 缓存本轮 snapshot。
- inventory response、diff planner、artifact lookup 描述和诊断全部引用同一 snapshot。
- 即使上传层之后需要查询文件，也只能读取已经选定对象的 descriptor，不能重扫全库。

### 5.2 逐对象 Store save、refresh 和 publish

placeholder 和 metadata apply 过程中，Store 被逐条保存和刷新。最近一次重试约 7 秒内产生 84 次 publish。

即使未来某个独立 apply 操作确实需要修改多个对象，也不应逐对象触发全 Store 刷新。当前实现放大了磁盘 I/O、JSON 读写、主线程通知、SwiftUI 重新计算和后续触发器。

正确实现：

- 同步层 Store mutation 必须为 0。
- 上传完成后的必要落库应批量提交。
- 一批变更最多发布一次一致性 revision。
- Store publish 不能重新创建 sync/upload trigger。

### 5.3 对同一批事实重复展开、遍历和诊断

约 55 条录音被展开为约 300 个逻辑对象和 126 个 artifact。多域投影本身可能有业务价值，但当前实现又在 inventory、planner、apply、artifact lookup、status projection 和 diagnostics 中反复遍历这些对象。

问题不是“对象数一定不能超过文件数”，而是没有把 immutable snapshot、diff result 和执行计划分开复用。对象展开的成本被重复支付。

正确实现：一次规范化、一次 diff；后续只引用稳定 object ID 和差异 action，不重新投影全库。

### 5.4 重复 trigger 产生额外运行和 `stale_sync_run`

foreground、periodic、manual signal、Store publish 和 retry 等触发源没有完全隔离。一轮未完成时又产生排队运行，后续被判为 `stale_sync_run`。

这类运行不仅无效，还会重复构建状态、写诊断、竞争 scheduler，并让 UI 看到难以解释的失败。

正确实现：同一 peer 在任意时刻最多一个 sync discovery run；新请求只合并为一次 `rerunRequested`，不得创建多个竞争性 run。

### 5.5 高频诊断进一步放大压力

Mac 最近会话包含两万级诊断事件。诊断不是首要根因，但在 inventory、Store publish 和 transfer 已经高频时，每个内部动作继续写多条日志会放大序列化、队列、磁盘和内存压力。

正确实现：按 run 汇总计数和耗时；对象级成功事件采样或聚合；错误和终态保留 critical 事件。

### 5.6 大文件 hash 假设：最近日志不支持

`CanonicalChecksumCacheKey` 当前包含 logical token、byte size、modified time、content version、hash algorithm、schema version、node role 和 store namespace。最近同步中 iPhone 54 次、Mac 53 次均为 cache hit。

因此：

- 持久 hash cache 确实工作了。
- 最近卡顿不是“每次同步都重新读取所有大文件计算 SHA256”。
- 仍需保留 cache miss 离主线程计算和单文件失效测试，但不应把当前主要精力放在重写 hash 算法。

## 6. 失败原因：同步层做了不该做的事

### 6.1 把 upload/apply 错误传播成 sync failed

当前一轮 sync 包含 metadata apply、artifact transfer 和 audio upload，因此这些阶段的 `cancelled`、checksum、finalize、remaining transfer 或 route 错误都会变成 `sync_tick_failed`。

这会掩盖真正状态：inventory 和 diff 可能早已成功，只是后续内容动作失败。

正确归属：

- inventory/diff 成功应记录 sync completed。
- apply/upload 失败只更新对应 upload job。
- UI 分别展示“同步差异已更新”和“文件上传失败”。

### 6.2 在发现 conflict 后仍先执行无关副作用

当前代码先 apply metadata、创建 placeholder、上传/下载 artifact、补传 audio，随后才检查原始 `plan.conflictActions` 并抛出 unresolved conflict。

这导致一次最终标记失败的同步，在失败前已经传输了文件并修改了状态。对用户而言既慢又不可预测。

正确归属：conflict 在 diff 阶段就是完整结果，不应触发任何 apply 或 transfer，也不应把 sync 变成失败。

### 6.3 同步失败前允许对端继续发生部分 apply

最近重试中，iPhone 约 20:02:22 报 `cancelled`，但 Mac 仍继续并在之后完成 metadata apply、更新 pulled 时间。结果是 iPhone 认为本轮失败，Mac 却已经产生部分副作用。

根因仍是同步层越界拥有 apply。只读同步没有部分写入，自然也不会出现“失败但已修改”的状态。

### 6.4 让 scheduler 同时拥有周期任务和当前同步任务生命周期

当前 periodic task 内直接 `await runTickIfPossible(...)`，`scheduler.stop()` 又会取消该 periodic task。于是连接 presence 短暂不满足 start gate 时，停止周期调度等同于取消正在执行的同步。

这不是 inventory/diff 的业务失败，而是调度控制面错误地拥有了当前 run 的 cancellation。

## 7. 失败原因：同步层本来该做，但做错了

### 7.1 把 conflict 定义成同步失败

第一次主要运行已经取得两端 inventory、生成 diff，并实际完成 69 个 artifact 下载，最后却因 `sync_unresolved_conflicts:4` 失败。

4 个 conflict 来源于两条 recording 在 recording/studyItem 两个投影上的业务差异。无论最终如何解决，它们都应该是同步成功发现的结果：

```text
sync: completed
added: ...
deleted: ...
modified: ...
conflicts: 4
```

而不是：

```text
sync: failed
error: sync_unresolved_conflicts:4
```

### 7.2 presence 短暂 stale 会取消当前 sync tick

最近重试中，正常 heartbeat 之间出现约 11 秒空档。同期 Store 发布风暴占用执行资源，start gate 随后认为当前不适合运行并调用 `scheduler.stop()`，最终取消承载当前 tick 的 task。

连接是否需要停止未来周期调度，与当前已经开始的 sync run 是否应取消，是两个不同问题。当前实现把它们合并了。

正确实现：

- `stopSchedulingFutureTicks()` 只停止未来 timer。
- 当前 run 由独立 task/token 持有。
- 只有用户显式取消、鉴权失效或当前请求真实断连时才取消当前 run。

### 7.3 多触发源与 run generation 处理产生 stale failure

一轮执行期间又排队了重复运行，后续以 `stale_sync_run` 被拒绝。stale run 本应是内部去重结果，不应成为用户看到的又一次同步失败。

正确实现：旧 run 的迟到事件可以记录为 ignored/superseded 诊断，但不得覆盖当前 run，也不得生成新的用户级失败。

### 7.4 两端终态没有按层次保持一致

iPhone 已经宣告 `cancelled` 时，Mac 仍完成 metadata apply。当前 `syncRunID` 同时承担 discovery、apply 和 transfer，导致两端对“本轮完成了什么”没有同一含义。

正确实现：

- sync run 只表示 inventory/diff，两端可以确定性收敛。
- upload job 使用独立 transfer ID。
- apply 如果保留，也应使用独立 operation ID。
- 任一层的终态不能覆盖另一层。

### 7.5 错误分类过粗，误导为网络问题

当前 UI 最终只看到同步失败，但没有清楚区分：

- connection/authentication failure；
- inventory build/protocol failure；
- conflict result；
- metadata apply failure；
- artifact/audio transfer failure；
- scheduler cancellation；
- stale/superseded internal run。

这让“网络明明正常却总失败”成为必然体验。实际上最近证据表明网络足以完成大量 HTTPS 内容传输，失败发生在更高层的业务和调度逻辑。

## 8. 两次最近失败的因果链

### 8.1 第一次运行

```text
连接与鉴权成功
  -> inventory exchange 成功
  -> diff 生成成功
  -> 自动执行 metadata/artifact/audio 内容动作
  -> 串行传输 69 个 artifact
  -> 保留 4 个 conflict
  -> conflict 被抛成 fatal error
  -> 整轮显示 sync failed
```

真正产品口径：同步在 diff 生成时已经成功，`conflicts: 4` 是结果；之后 69 个文件传输根本不应发生。

### 8.2 后续自动重试

```text
连接正常
  -> inventory/diff 再次完成
  -> 再次进入 metadata apply
  -> placeholder/Store publish 风暴
  -> heartbeat 观察出现空档
  -> start gate 不满足
  -> scheduler.stop() 取消承载当前 tick 的 task
  -> iPhone 报 cancelled / sync failed
  -> Mac 仍继续完成部分 metadata apply
```

真正产品口径：inventory/diff 与 apply 必须拆开；停止未来 scheduler 也不得取消当前 sync discovery run。

## 9. 修复优先级

### P0：先恢复产品边界

1. 从“立即同步”路径移除 metadata apply。
2. 移除 artifact request/put 和 `dataBase64` 内容传输。
3. 移除缺失 audio 自动上传。
4. 移除 placeholder 创建和 StudyLibraryStore 写入。
5. 移除 upload retry/finalize/remaining transfer 作为 sync success 条件。
6. conflict 改为 completed sync 的差异结果。

完成 P0 后，即使暂时没有进一步性能优化，“立即同步”也应从几十秒级内容传输回到短 metadata 交换。

### P1：修正同步层自身实现

1. 每端每个 `syncRunID` 只构建一个 inventory snapshot。
2. 所有 planner、response 和 diagnostics 复用该 snapshot。
3. 保留持久 checksum cache；只对 miss/stale 文件离主线程 rehash。
4. 合并 foreground/periodic/manual 触发；同一 peer 同时最多一个 run。
5. scheduler 停止未来 tick，不取消当前 run。
6. stale/superseded 只记内部诊断，不显示为用户级失败。
7. 对象级诊断聚合为 run summary。

### P2：建立独立双向上传层

1. 学习库“上传”按钮创建 selected-content transfer job。
2. 明确 source device、target device、object ID、content hash 和 size。
3. 分别实现 iPhone -> Mac 与 Mac -> iPhone。
4. 保留 TLS/HMAC/pinning/nonce/body hash、`RequestVerifier`、checksum/size、no-overwrite 和 finalize proof。
5. upload job 独立持久化进度、失败、取消和重试。
6. 上传失败不得回写 sync failed。

## 10. 验收标准

一次“立即同步”必须满足：

- 每端 inventory builder 调用次数为 1。
- `artifactBytesTransferred == 0`。
- `audioBytesTransferred == 0`。
- `metadataApplyCount == 0`。
- `placeholderCreatedCount == 0`。
- `studyLibraryMutationCount == 0`。
- `uploadJobsCreated == 0`。
- 大文件无变化时 checksum 全部 cache hit，不读取内容。
- wire bytes 只随文件数量和短 metadata 增长，不随文件体积增长。
- conflict 存在时 sync 仍为 completed，并返回 conflict list。
- peer absent 不直接删除；有效 tombstone 只形成 deleted diff。
- 短暂 heartbeat stale 不取消已开始的 sync discovery。

一次学习库“上传”必须满足：

- 只有用户点击后才创建新 job。
- 明确显示 iPhone -> Mac 或 Mac -> iPhone。
- 实际文件 bytes 只出现在该 upload job 中。
- 进度、失败、取消和重试不污染 sync run。
- 目标端 checksum/size/finalize 成功后才标记 upload completed。

## 12. 最终判断

当前问题不是“不到一百个文件也算不动 hash”，也不是“同一私人 Wi-Fi 下 HTTPS 天生不可靠”。

卡顿的本质是：同步层越权执行了文件传输和持久化副作用，同时又对本应单轮构建的 inventory、Store refresh 和对象投影进行了大量重复工作。

失败的本质是：同步、apply、上传和调度共享同一个 run/终态；conflict 被错误当成 fatal failure，presence/scheduler 又能取消当前 tick，最终产生“iPhone 报失败、Mac 已部分应用”的不一致结果。

修复顺序不能从微调 SHA256 或网络 timeout 开始。第一步必须是把“立即同步”恢复成纯 inventory exchange + diff；第二步才优化单轮 snapshot 和调度；实际文件内容必须留到学习库内用户明确点击“上传”后，通过独立的双向上传状态机完成。
