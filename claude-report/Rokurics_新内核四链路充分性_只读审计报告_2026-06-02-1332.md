## 1. 四链路充分性逐条评估（语义层 vs 运行时）

标尺：每条链路要"被新内核支撑"，需同时满足**①语义建模**（对象/字段/不变量齐备）和**②运行时归属**（由内核驱动，而非旧层）。

| 链路 | ①语义建模 | ②运行时归属 | 结论 |
| --- | --- | --- | --- |
| 同步链路 | ✅ 录音+文件夹+学习项+独立笔记+墓碑+冲突+LWW+apply 计划 | ⚠️ apply 仅"计划+桥接旧执行"（applyBridged），冲突只记录不解决 | **基本够用**（决策层完整，执行靠旧层） |
| 文件链路 | ✅ artifact（音频/转写/笔记/摘要）+内容哈希+字节数+**安全相对路径令牌**+生产者归属 | ❌ 物理读写仍属旧 store（`physicalStorage=.blocked`） | **建模够、运行时不够** |
| 连接链路 | ✅ node 身份+能力声明+schema 版本+清单完整性哈希；**鉴权正确地留在连接层** | ❌ 签名 HTTP 路由仍旧（`transport=.blocked`） | **建模够、运行时不够** |
| 上传链路 | ⚠️ 传输 job/阶段/方向/失败/重试**状态词汇**齐全，但只是**状态投影**，缺 resumable 会话/分块/offset/confirmedBytes/finalize 协议 | ❌ 实传仍 `RecordingUploadCoordinator`（`uploadRuntime=.blocked`） | **半建模、运行时不够** |

> 关键判断：**新内核现在足以做四链路的"共享语义契约/决策大脑"，但还不足以做"运行时执行体"**。同步链路最接近完成（决策+apply 计划已 canonical 驱动）；文件/连接/上传是"已被它描述、但还由旧层执行"。

### 1.1 同步链路（最完整）

- 库对象模型齐备：`CanonicalLibraryObject` 含 `folder/studyItem/standaloneNote`，`CanonicalObjectKind`（folder/standaloneStudyItem/standaloneNote/recordingAssociatedStudyItem/unknownUnsupported），`CanonicalLibraryTombstone`，冲突种类（`CanonicalLibraryObject.swift:18-320`）。
- 决策齐备：`CanonicalSyncPlanner`(录音) + `CanonicalLibrarySyncPlanner`(文件夹/学习项) + `CanonicalApplyPlanner`(apply 计划，含 send/apply/tombstone/conflict/deferredUnsupported，带 `preconditions` 与 `bridgeHint`，`CanonicalApplyPlan.swift:10-130`)。
- 已接线为真相源：`bridgedCanonicalPlan` 剥离旧的 recording/folder/studyItem/产物动作，改由 canonical 计划驱动（`StudyLibrarySyncCoordinator.swift:2352-2405`）。
- **缺口**：apply 是"计划+桥接"，真正写回仍走旧 diff 执行；**冲突仅记录、无解决策略**（`CanonicalApplyResult.conflictRecorded`、就绪评估里 `conflicts` 会被判 `.blocked`，`CanonicalRetirementReadiness.swift:91/109-111`）。

### 1.2 文件链路（建模够，运行时缺）

- artifact 抽象足以承载文件内核：`CanonicalArtifact`（kind/availability/contentHash/byteSize/logicalName/**logicalPathToken**/producedBy）。
- **安全相对路径**：`CanonicalProjectionContract.safeLogicalPathToken` 拒绝 `/` 开头、`://`、`\\`、`.`/`..` 组件（`CanonicalProjectionContract.swift:124-138`）——这是文件内核需要的防逃逸基础。
- **缺口**：内核不做物理 IO；`physicalStorage=.blocked`（"legacyStoresStillOwnFiles"，`:98/118`）。迁移文件链路时，**apply 执行体必须在 `safeLogicalPathToken` 之外再叠加 `isInsideRoot` 根目录绑定**（令牌只保证"相对、无穿越"，不保证"落在沙盒根内"）。

### 1.3 连接链路（建模够、且边界正确，运行时缺）

- 提供 `CanonicalNode`(nodeID/platform/capabilities) + `schemaVersion` + `manifestHash`(自校验)。
- **边界正确**：内核**不含** TLS/HMAC/nonce——鉴权留在连接层，这是对的设计；canonical 清单寄生在已签名的 `/sync/inventory` 响应体里（`SecureLocalHTTPSServer.swift:3170-3241`）。
- **缺口**：`transport=.blocked`（"signedHTTPRoutesStillLegacy"，`:96/116`）。迁移时内核可拥有"线格式/清单契约"，但**鉴权必须继续由连接层提供**（见第 2 节）。

### 1.4 上传链路（半建模，运行时缺）——这是最需要补的语义缺口

- 有 `CanonicalTransferKind/Phase/Direction/Failure/RetryPolicySnapshot/Job/LedgerProjection`（`CanonicalTransferStateMachine.swift:18-121`）。
- **但它本质是"状态投影"**：核心是 `phase(fromLegacyState:)` 把旧状态字符串映射成 canonical 阶段（`:124-151`），**没有** resumable 会话 ID、分块大小、offset、confirmedBytes、finalize、断点续传的**协议状态机**。
- **缺口**：因此内核**还不能驱动**上传，只能**统一描述**上传状态；`uploadRuntime=.blocked`（"RecordingUploadCoordinatorStillRuntime"，`:97/117`）。迁移上传链路前，必须把 resumable/chunk/retry **传输协议**纳入内核（目前只有"状态词汇"，没有"传输机制"）。

## 2. 安全边界评估

| 项 | 结论 | 证据 |
| --- | --- | --- |
| 路径防逃逸 | ✅ 投影层强制相对、无 `..`/`.`/`/`/`://`/`\\` | `CanonicalProjectionContract.swift:124-138` |
| 清单无密钥/绝对路径 | ✅ SyncCore 无 `sharedSecret/fingerprint/绝对路径`；只携带 objectID/标题/标签/哈希/字节数/**相对令牌** | 全量 grep；`.path` 仅出现在本地诊断日志写入 |
| `manifestHash` 性质 | ✅ **完整性、非鉴权**；仅在 planner `validate` 里用于拒绝损坏清单后回退，未作任何传输鉴权门 | `CanonicalCore` 自校验；app 层无 `hasValidManifestHash` 鉴权用法 |
| 鉴权归属 | ✅ canonical 清单走**已 HMAC 签名**的 `/sync/inventory` 通道；内核不自带鉴权 | `SecureLocalHTTPSServer.swift:3170-3241` + `RequestVerifier` |
| 信任假设 | ⚠️ 对端**能力声明/生产者归属/内容哈希均为自述**；内核隐含"对端已配对且已鉴权可信" | `isAuthoritativeProducer`、planner 信任 `peer.capabilities` |

**两条必须写进迁移红线的安全结论：**

1. **`manifestHash` 永远不能被当作鉴权**。它能发现"清单被改坏/损坏"，但**不能**发现"被攻击者伪造"（任何人都能重算）。当连接链路日后迁到 canonical，**TLS pinning + HMAC 必须保留**，canonical 只负责完整性与语义，不负责真伪。
2. **迁移文件链路时，apply 执行体必须在 `safeLogicalPathToken` 之上再加 `isInsideRoot`**。当前因为物理存储仍是旧 store（自带根校验），没有新攻击面；但一旦 canonical 自己落盘，相对令牌**不等于**"在沙盒根内"。

整体：**当前无新增攻击面**（运行时还是旧层在守边界），且 canonical 的边界设计（鉴权外置、路径相对化、清单无秘密）是正确的。

## 3. 是否可进入真机验证

**可以，而且这套东西恰好是为真机验证设计的。** 依据：

- **回退安全**：canonical 出错（schema 不符/清单哈希无效/能力缺失）即 `catch` 回退旧 plan（`CanonicalSyncPlanner.validate` + 协调器 `?? legacyPlan`），不会把同步搞挂。
- **每个 tick 输出机器可读的就绪/阻断诊断**：`CanonicalRetirementReadinessEvaluator` 给出 14 个域的状态 + 阻断项（`CanonicalRetirementReadiness.swift`），并在 `performTick` 落诊断（`StudyLibrarySyncCoordinator.swift:2156-2178`）。你在真机上能直接看到"哪些域已 semanticsComplete / applyBridged、哪些仍 blocked"。
- **影子对比仍在**：`canonical-shadow.jsonl` + apply/library/transfer/projection 诊断，能逐对象暴露 canonical 与 legacy 的分歧。
- **测试覆盖扩大**：本轮新增 `CanonicalApplyPlanTests / CanonicalLibraryObjectTests / CanonicalLibrarySyncPlannerTests / CanonicalObjectProjectionTests / CanonicalTransferStateTests / CanonicalInventoryCoverageTests`（双端）。

**真机验证应重点盯（验收口径）：**

1. `canonical-shadow.jsonl` 的 `canonicalMetadataHashMismatch` 趋零（投影一致性，尤其 `createdAt`/title/tags）。
2. 退役就绪报告里 `blocked` 最终只剩**已知三项**：`transport / uploadRuntime / physicalStorage`（其余 metadata/folders/studyItems/apply/transferState/inventory/objectProjection 应升到 applyBridged 或 semanticsComplete）。
3. `conflicts` 域是否频繁进 `.blocked`——若是，说明真机存在未解决冲突，需要先定义冲突解决策略。
4. `libraryPlan.fallbackRequiredObjectIDs` / `unsupportedLegacyObjectCount` 是否为 0——非 0 表示还有对象类型没纳入 canonical（仍走旧层）。

**结论**：进入真机验证的前置条件已满足（安全、可回退、可观测）。但请明确——**这轮真机验证是验证"语义层 + 决策/apply 计划"的正确性**，不是验证"四链路已迁移"；文件/连接/上传的**运行时**仍由旧层执行。

## 4. 要让新内核"足以承载四链路运行时"，还差什么（按优先级）

1. **上传链路：把 resumable 传输协议纳入内核**（当前只有状态词汇，缺会话/分块/offset/finalize/重试驱动）。这是四链路里语义缺口最大的一块。
2. **apply 执行体（executor）**：把 `CanonicalApplyPlan` 的 `bridgeHint` 从"提示旧层"升级为"canonical 自有执行"，并内建 `isInsideRoot` 等存储安全守卫——这同时解锁**文件链路**与**同步链路 apply**。
3. **冲突解决策略**：`conflictRecorded` 目前只记录；需定义胜负/合并/用户可见入口，否则 `conflicts` 域永远卡 `.blocked`。
4. **连接/传输线契约归内核**：内核定义线格式与端点契约，**鉴权仍由连接层提供**（红线见 2.1）。
5. **物理存储抽象**：共享 `FileStore` 协议核 + 双端适配器，替换旧 store 的文件 IO。
6. **UI 改读 canonical 投影**：`objectProjection` 目前 `uiStillReadsLegacyStatus`（`:115`）；UI 不切到 canonical，状态一致性无法最终收敛。

完成 1–2 后，文件与上传链路才谈得上"运行时可迁移"；完成 3–6 后，才到 `readyToRetireLegacy`。
