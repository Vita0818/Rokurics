## 2. 执行器接口：两阶段、最小、可实现

- **NoCommit（暂存）**：`CanonicalRecordingMetadataNoCommitExecutor.stageNoCommit(_:) -> StagingResult`（`CanonicalRecordingMetadataCutover.swift:1165-1169`）——单方法、同步、清晰。
- **Cutover（提交）**：`CanonicalRecordingMetadataCutoverExecutor`（`:412-421`）——`commitRecordingMetadata(_:) async -> CommitResult` + `rollbackRecordingMetadata(_:reason:) async -> RollbackResult`，提交与回滚成对出现。

两者**互补而非竞争**：先 `stageNoCommit`（写暂存+比对），过门后才 `commit`（写真实根）+ 失败 `rollback`。这正是安全阶梯的接口化，命名/签名都稳定。

## 3. 可用性：NoCommit 端到端已通，Commit 接口就绪待实现

- **NoCommit 完全可用**：
  - 双端**真实实现**：`Rokurics/IPhoneRecordingMetadataNoCommitExecutor.swift`、`RokuricsMac/MacRecordingMetadataNoCommitExecutor.swift`。
  - **已接进 app**：iPhone `StudyLibrarySyncCoordinator.swift:2500-2509`、Mac `SecureLocalHTTPSServer.swift:3449-3457` 调 `CanonicalRecordingMetadataNoCommitRunner().run(... executor: ...NoCommitExecutor())`。
  - **默认关**：seam 由 `canonicalV8CutoverAppSeamConfiguration` 守门，默认 `.disabled`（`StudyLibrarySyncCoordinator.swift:1798`；类型默认 `isEnabled=false`，`CanonicalRecordingMetadataCutover.swift:912/925`）。
  - **只写暂存根**：executor 写入 `temporaryDirectory/RokuricsCanonicalV8NoCommit/iphone-<UUID>/...`、`.atomic`、结果 `wroteOnlyStagingRoot=true`，仅报告"将 apply/send"（route `/sync/apply-metadata`），**不碰真实根、不发网络**（`IPhoneRecordingMetadataNoCommitExecutor.swift:13-60`）。
- **Commit 接口就绪、实现待写**：`CanonicalRecordingMetadataCutoverExecutor` 仅有测试 `FakeExecutor`（`RokuricsTests/CanonicalRecordingMetadataCutoverTests.swift:147`）演示用法，**尚无真实提交实现**。这是有意为之（最危险一环放最后）。

→ **可用性结论**：接口对集成方（v8.0）**好用**——NoCommit 有现成双端实现 + 接线 + 默认关样板可照抄；Commit 有清晰协议 + 测试用法示例，照着写真实实现即可。

## 5. 需要留意的接口/可用性小问题（非阻塞）

1. **暂存临时根的清理**：NoCommit executor 每次建 `RokuricsCanonicalV8NoCommit/<UUID>` 暂存目录。执行影子根上轮已加清理；**需确认 NoCommit 暂存根也有对应清理**，否则真机开启后会累积临时文件（仅磁盘、默认关，轻微）。
2. **配置旋钮开始增多**：现已有 `canonicalShadowMigrationConfiguration`、`canonicalSingleDomainShadowConfiguration`、`canonicalV8CutoverAppSeamConfiguration` 三个门。功能上清晰，但建议**统一文档化"每个旋钮管什么、默认值、互斥关系"**，避免操作者误开/漏配（可用性而非正确性问题）。
3. **Commit 协议的真实性待证**：`commit/rollback` 协议签名稳定，但只有等真实提交实现落地，才能验证 candidate/result 类型是否足以承载"原子替换 + receive.json 一致性 + 部分提交回滚"。当前看类型设计是够的（已有 `applyFailureAfterPartialCommit` 等失败态），但属"未被真实实现压过"。

## 6. 下一步方向

**先验证已就绪的 NoCommit，再实现 Commit，节奏不变（默认关 / 一次一个域 / 影子先于提交）。**

1. **真机跑 NoCommit（现在就能做，零风险）**：把 `canonicalV8CutoverAppSeamConfiguration` 打开为 NoCommit，在真实库上采集"canonical 暂存 payload vs legacy 动作"的等价/分歧（`evaluateEquivalence`，`CanonicalRecordingMetadataCutover.swift:1685`），要求**分歧持续为 0**；顺手确认暂存根被清理（第 5.1）。
2. **实现真实 Commit 执行器（录音 metadata 单域）**：新增 `IPhoneRecordingMetadataCutoverExecutor` / `MacRecordingMetadataCutoverExecutor` 实现 `CanonicalRecordingMetadataCutoverExecutor`，做真实根**原子替换 + 回滚检查点**；先在 `guardedExecuteNoCommit` 跑通，再升 `guardedExecuteCommit`，全程默认关。
3. **过门标准（全满足才允许该域 commit）**：NoCommit 等价=0 ＋ 执行影子在真实数据副本上字节等价 ＋ 故障注入回滚演练通过（写中断/部分提交/磁盘满/权限失败）＋ 重试幂等 ＋ 崩溃安全（metadata 原子替换与 receive.json 一致）。
4. **配置收敛**：把 3 个旋钮统一成一份"迁移阶段"配置（阶段枚举：off→shadow→executionShadow→noCommit→guardedCommit），降低误配面（第 5.2）。
5. **之后**：逐域扩展（音频上传最后）→ UI 读 `CanonicalObjectProjection`（先并行对照）→ 退役 legacy（`CanonicalRetirementReadiness` 达标后）。

**红线（沿用）**：`manifestHash` 永不当鉴权（保 TLS pinning + HMAC）；执行/提交永不指向生产根（`validatedShadowRootURL` 守卫保留）；提交必须原子 + 回滚 + 崩溃安全；默认关、一次一个域、影子先于提交。
