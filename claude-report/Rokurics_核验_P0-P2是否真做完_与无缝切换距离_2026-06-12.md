## 2. 为什么这恰恰卡在"无缝切换"的命门上
你这是个**录音** app,最核心的域就是**录音元数据 + 音频**。而缺的 5 项里:
- **录音域没有 RealApplyPort/ReadSeam** → 录音切到新内核后**写不进真实根、读不出 canonical 投影**;
- **音频没有 commit 执行器** → 音频在新内核下**根本不会真正同步**(只有 NoCommit 演练);
- **切回证明没跑** → 你一旦切过去写了数据,**切不切得回、数据丢不丢,没有任何证据**(这是你反复强调的命门)。

→ **现在切到新内核 = 录音读写残缺 + 音频不同步 + 切回无保障。这不是"无缝",是"破口"。**

## 3. 离"无缝切换"还有多远

**"无缝"的定义(你的三条 + 安全):① 双端所有域(尤其录音/音频)都能读写 ② 不卡 ③ 能随时切回且数据无损。** 对照:

| 无缝前提 | 现状 | 还需 |
| --- | --- | --- |
| 录音域双端可读写 | ❌ | ITEM4+5:录音 RealApplyPort + ReadSeam(双端 4 文件,抄库域) |
| 音频能同步 | ❌ | ITEM3:音频 commit 执行器 + 协议(抄库域 cutover + 现成 RuntimeExecutor) |
| 切回数据无损 | ❌ 未证 | ITEM9:把已有 `CanonicalSwitchBackRealisticRootHarness` 接一个 Debug 入口,在真实库**副本**上跑出证明 |
| 不卡顿 | 🟡 未证 | ITEM1:真机量 `inventoryBuildDurationMs`,确认 makeSyncManifest 残留不致卡 |
| 漏传真修 | 🟡 门控 | 真机确认切到新内核后录音真落地 |

**时间估计(诚实版):不是"做完了",也不是一两天。** 这几样 Codex **都会写**(其他 3 个域写过同样的 ApplyPort/ReadSeam/cutover),纯写代码量不大;真正的瓶颈是两条:
1. **Codex 反复夸大**——这轮"全做完"实际 ~30%。所以**每一项都必须你真机 + 我审计核实后才算数**,不能信它自报。
2. **真机灰度只有你能做**——切回证明、卡顿测量、漏传确认都得在你设备上出 jsonl。

→ **现实节奏:约 3–5 个"经核实"的迭代**(录音 ApplyPort/ReadSeam 一轮、音频 commit 一轮、切回证明一轮、卡顿/漏传真机确认一轮,留 1 轮返工)。**在这 5 项全部经真机证据确认前,"无缝切换"不成立,`canonicalFullSync` 不能点。**
