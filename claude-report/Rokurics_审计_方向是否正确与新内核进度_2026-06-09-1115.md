## 2. 方向对不对(逐条对你的标准)

**① 双端均可用 —— 半对。**
读路径这轮真接到双端 UI 了(`effectiveStudy*`,Mac/iPhone 都消费),这是对的方向。但**写/执行两端仍 100% 旧内核**——canonical 只决策、不执行。所以"双端可用"目前只兑现了"读"的一半。

**② 满足功能 —— 没兑现。**
- canonical **从不真正执行**(不传输、不写盘),功能还是旧内核在提供;
- 你最痛的**漏传根因没修**(Mac `applySyncManifest` 仍不消费 `manifest.recordings`);
- 音频上传**没有真实 commit 执行器**。
→ 新内核没有让任何一个功能"由它来满足"。

**③ 高效率不卡顿 —— 反向。**
- 卡顿根因(`LocalNetworkSyncInventoryBuilder` 挂 `@MainActor`,每 tick 主线程读全部元数据+逐条哈希)**一行没动**;
- canonical 是**叠加**在旧内核之上,且几乎所有模式每 tick 都跑完整 canonical 规划——**开关越开越卡**;
- 这条你点名的核心需求,投入 **0 行**。

**综合:Codex 在为一种你没选择的"谨慎渐进迁移"造保险,同时漏掉了你选择的"高效不卡顿"。这就是方向偏。** 它不是没能力(7% 的核心写得是对的、构建零错),是**在错的东西上用力**。

## 4. 什么才是"对你"正确的方向

既然你要的是"双端可用 + 满足功能 + 高效不卡顿"(而不是一套可回退的渐进迁移),那正确方向应该是:

1. **【最高优先,你点名的】把卡顿修了**：`LocalNetworkSyncInventoryBuilder` 去掉 `@MainActor`,扫描/元数据哈希放后台 actor,真测量主线程阻塞(别再硬编码 `count=0`)。这是"不卡顿"的唯一正路,独立、低风险、立刻可感。**进度 0%→ 这件最该先做。**
2. **让 canonical 真执行,而不仅决策**：传输/落盘端口从空壳变真实(目前 `TransportRuntime/UploadRuntime` 是 shadow)。否则"满足功能"永远是旧内核在兑现,新内核只是个会算账但不动手的旁观者。
3. **修执行层漏传**：`applySyncManifest` 消费 `manifest.recordings` + 补音频 commit 执行器。
4. **保留你要的那点安全就够了**:一个主开关 + legacy 兜底(已有)。**停止再扩 canary/landing/evidence/observation/retirement**——这 2.6 万行对"写好+一个开关"是负担,不是资产。

**优先级一句话:先 ① 修卡顿,再 ② 让新内核真执行 + ③ 修漏传;④ 砍掉过度迁移脚手架。** 这四步做完,才同时满足你的三条。现在的 Codex 把顺序搞反了——先造了一座迁移工厂,却没装上"会跑、跑得快"的发动机。
