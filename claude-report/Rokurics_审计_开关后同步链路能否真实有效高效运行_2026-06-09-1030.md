# Rokurics 审计 · 开关打开后,同步链路能否"真实 / 有效 / 高效"运行

- 时间：2026-06-09 10:30 (CST)
- 方式：**只读**审计,未修改任何代码。聚焦"假设把主开关推到 canonical 后,同步链路实际会怎么跑"。
- 一句话结论：**会跑,但不是你以为的那种跑法。新内核只是"出主意",活还是旧内核干的;4 个症状不会因此消失;而且开关开得越多,主线程越卡。**

| 维度 | 结论 | 实质 |
| --- | --- | --- |

## 一、真实:开关打开后,canonical 是"接管"还是"出主意"?

**是"出主意",不是"接管"。** 证据链:

1. **每个 tick 旧规划器无条件先跑**：`let legacyPlan = diffPlanner.plan(...)`（`StudyLibrarySyncCoordinator.swift:2470`,无任何开关判断）。
2. **canonical 把自己的决策"翻译"回旧计划**：`canonicalScopedPrimaryDecisionPlan`（`:5229`）做的是 `var plan = legacyPlan`，然后对**启用的 scope**把旧动作删掉、塞进 canonical 等价动作（`:5254-5318`）。产出仍是旧类型 `LocalNetworkSyncDiffPlan`。
3. **真正被执行的 plan 是一串"压制旧动作"的链**：`suppressCanonicalRecordingMetadata… → …GeneratedArtifact… → …LibraryMetadata… → …TombstoneConflict…`（`:2623-2647`），最后交给**旧的执行器/传输/落盘**。
4. **canonical 的"运行时主决策"只覆盖 3 个 scope**：`recordingMetadata / libraryMetadata / recordingExistence`（`CanonicalSyncRuntime.swift` 的 `DecisionScope` 只有这三个）。生成产物、tombstone/冲突走另一条 cutover 压制链;**音频上传仍纯旧内核**。

→ **本质：canonical 是"决策叠加层"。即便推到 `canonicalFullSync`,新内核也只是替旧计划改了 3 类决策,然后让旧内核去传、去写。所谓"新内核接管同步运行"——没有发生。** 这跟你"全部写好+一个开关切到新内核运行"的设想有实质差距:你以为切的是"内核",实际切的是"diff 决策来源"。

## 二、有效:开关打开后,你最初的 4 个症状会消失吗?

| 症状 | 开关后是否消除 | 原因 |
| --- | --- | --- |
| ① 卡顿 | ❌ 不消除,反而更重 | 见第三节(inventory 仍在主线程 + canonical 叠加)。 |
| ② 已有文件重传 | 🟡 决策层**可能**改善 | canonical 用两端一致的稳定字段哈希做 LWW,理论上能判对"没变";但哈希依赖"主线程拒算+缓存"机制(见三节),不稳。 |
| ③ 新文件不传(漏传) | ❌ 不消除 | 根因在**执行层**:Mac 的 `applySyncManifest` 仍只处理 `folders/items/tombstones`,**不消费 `manifest.recordings`**（`RokuricsMac/StudyLibraryStore.swift:642-671`）。canonical 决策"要传这条录音"也没用——干活的旧接收端有这个洞。 |
| ④ 双端状态不一致 | 🟡 部分改善 | **读切换这轮真接好了**(下条),若开启,两端 UI 都读 canonical 投影,可缓解显示不一致。 |

**唯一值得肯定的有效性进步——读切换真接进 UI 了**(我上轮说的 0/6,这轮变了)：
- 两端 `StudyLibraryStore` 都加了 `effectiveStudyItems / effectiveStudyFolders / effectiveStudyTree`,以 `canonicalReadServed` 为闸（默认 legacy）。
- UI **确实在消费**:Mac `MacStudyLibraryView.swift:148/259/581`、`MacAIChatView.swift:167`；iPhone `RecordingLibraryView / IPhoneAIChatView / RecordingSessionView / RecordingStudyDetailPage`。
- 默认走 legacy,`canonicalReadServed` 为真才读 canonical——**安全默认正确**。

→ **但合起来看:开关打开,4 症状里最多缓解 ②④,而 ①(卡顿)③(漏传)这两个"执行层"病根开关碰不到。** 你建新内核的初衷(修同步)仍未由开关兑现。

## 三、高效:开关打开后会更流畅,还是更卡?

**更卡。** 三条硬证据:

1. **inventory 构建仍在主线程**：`LocalNetworkSyncInventoryBuilder` 标了 `@MainActor`（`:1190`）。`buildRuntimeSnapshot` 每 tick 在主 actor 上同步做:`makeSyncManifest`（`:1242`）、`loadAllMetadata(includeDeleted:true)`（`:1243`,读全部录音元数据)、`loadJobs`（`:1244`)、对**每条**录音/文件夹/学习项算 `metadataHash`（`:1285/1321/1333`)、`makeArtifacts`（`:1339`)。**这才是卡顿主因,它没被移走。**
2. **只优化了"音频文件 SHA256"这一小块,而且手段是"主线程拒算"**：`sha256HexOffMainActor` 现在**在主线程直接 throw**（`:2117-2122`,原来的 `semaphore.wait()` 阻塞确实去掉了——这点是改善),改走 size+mtime 的落盘缓存。但**元数据哈希和磁盘扫描仍在主线程**,大库照卡。
3. **canonical 是"叠加"不是"替换",且几乎所有模式都在跑**：`evaluatesCanonicalCandidate` 对 `.disabled / .diagnosticsOnly / .canonicalPlanNoCommit / .canonicalPlanPrimaryWithLegacyFallback` **全为真**,只有 `.blocked` 不跑（`CanonicalSyncRuntime.swift:21-28`)。意味着**即使"关着",每 tick 也在做完整 canonical 规划**;开关往上推,还要叠加 apply/library 规划器 + 投影 + 退役评估 + 一堆 seam 记录——**全在 `@MainActor` 的引擎上**。开的 scope 越多,主线程活越多。

**附:有一处误导性遥测要小心**——构建一开始就硬编码发了两条 `canonicalInventoryRuntimeMainActorHashBlocked: count=0` / `…ScanBlocked: count=0`（`:1229-1240`),但 builder 本身就是 `@MainActor`。**这两个"主线程未阻塞=0"的事件是写死的,不能拿来证明"已移出主线程"。** 看诊断时别被这条骗了。

→ **结论:推开关 = 主线程每 tick 的工作量上升 = 更卡。你真机上"开关一开就卡"的观察是对的,而且会随启用的 scope 数增加而加重。**

## 四、给你的判断

**开关后这条同步链路"能跑",但跑的是一个"canonical 决策 + legacy 执行"的混合体,不是你要的"新内核接管"。** 用你的标准衡量:

- **真实**:半真(决策接管 3 个 scope,执行仍旧内核)。
- **有效**:读切换真接好了(赞),但漏传/卡顿这两个执行层病根开关消不掉。
- **高效**:反而更慢(inventory 仍主线程 + canonical 叠加)。

**所以在动那个 `canonicalFullSync` 之前,真正该让 Codex(额度回来后)补的不是"再加层",而是这三件硬骨头:**

1. **把 inventory builder 移出主线程**（去掉 `@MainActor`,扫描/元数据哈希放后台 actor,真测量并上报主线程阻塞数,别再硬编码 0)。→ 这是修卡顿的唯一正路,且独立、低风险、立刻可感。
2. **修 Mac 执行层的漏传**：让 `applySyncManifest` 真正消费 `manifest.recordings`。→ 否则 canonical 决策再对也白搭。
3. **想清楚"接管"的边界**：当前是"canonical 决策 + legacy 执行"。如果你要的是真·新内核执行,得让 canonical 拥有传输/落盘;如果你接受"决策叠加",那要明确**legacy 执行层的 bug(漏传)必须先修**,因为开关治不了它。

> 一句话:**别被"开关接好了"误导成"新内核能用了"。开关接的是决策,执行还是旧的;在 inventory 移出主线程 + Mac 漏传修掉之前,推 `canonicalFullSync` 只会得到一个"更卡、还漏传、但 UI 读 canonical"的混合态。**
