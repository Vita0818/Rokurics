# Rokurics 诊断 · 问题在内核,还是在接口外部?

- 时间：2026-06-18 (CST)
- 方式：**只读**审计,端到端追"你在设置里推到 fullSync → 真机实际跑什么"。未改代码。
- 你的问题:卡顿一点没改、收敛/UI 同步一点没做,两周像一事无成——**到底卡在内核,还是接口外部?**

---

## 0. 一句话结论
**问题在接口/集成层与架构,不在内核内部。** canonical 内核的类型/协议这两周写得又多又细(SyncCore 80+ 文件),甚至**过剩**;但真机没变化,是因为**真正决定"卡不卡、收不收敛"的那一层——@MainActor 的 legacy app 执行 + canonical 只做"叠加 overlay" + 开关的 readiness 门是"自证橡皮图章"——两周来基本没动。** 你不是没造内核,是把内核造在了一个没被改造的重壳上。

---

## 1. 证据 A：开关的"四域就绪"是自证的橡皮图章
你推到 fullSync 时,`resolve()` 会查 ~18 个 readiness 标志(`connectionRuntimeReady / transferRuntimeReady / audioUploadRuntimeReady / readRuntimeReady / 各域 readiness …`,`CanonicalKernelSwitch.swift:765-800`)。
但 app 实际用的 policy 是 `.debugInternal(ownerApproved:true, manualFullSyncConfirmation:…)`(`MacConnectionView.swift:96-98` → `runtimeConfigurationFromStoredDefaults`),而 `.debugInternal` **只设了 4 个标志,其余 readiness 全取 init 默认值——而默认值清一色 `= true`**(`:130-141`)。

→ **开关从不验证四域是否真就绪,它直接"声称"全部就绪。** 所以你以为切到了"四域 canonical",其实切到的是一个**自我盖章"我准备好了"的壳**。这本身就是接口层问题:门是装饰性的,不挡也不证。

## 2. 证据 B：canonical 是"叠加 overlay",真正干活、真正卡的是 @MainActor 的 legacy
- 这套架构是 Path B:canonical 只做**决策/读投影/状态事实**,**执行(传输、文件落盘、Mac 服务端建清单)仍是 legacy**。
- 而 legacy 执行层**整体挂在主线程**:`RokuricsMac/SecureLocalHTTPSServer.swift` 是 `@MainActor`(:52),每次心跳/同步在主线程做**同步** `write(to:options:.atomic)`(:3826/7855/7865)+ 清单/canonical 构建。
- 卡顿源就在这层。**canonical 不替换它,只在它上面再叠 decision/read/status-truth/exchange/projection** → 主线程活更多,不是更少。
- R1(诊断异步)、R2(读缓存)是**两个点修**,的确修对了两处;但它们抵不过"一切皆 @MainActor + canonical 叠加"的**聚合主线程过载**。这就是为什么"卡顿一点没改"——你修了两滴,水位没降。

→ **卡顿是接口/架构问题:重活在 app 的 @MainActor legacy 执行层,canonical 内核管不到。**

## 3. 证据 C：收敛也吊在同一层
- 收敛取决于"何时、由谁、走哪个通道传状态"——即**连接/传输/触发拓扑**,这层仍是 legacy(iPhone 拉、Mac 服务端 @MainActor、定时器为主)。
- canonical 的状态真相引擎(R4/R5)确实在 iPhone 侧产出 `EffectiveSyncStatus`、发 delta/ack;**但状态事实来自仍有问题的 legacy 执行**(漏传/单向/拓扑),"算出来的收敛"反映的是没修好的底层。
- 且 Mac 服务端侧的状态交换处理 grep 基本为空——交换很可能是**单边**的(iPhone 发、Mac 不对称消费)。

→ **收敛是接口问题:把"状态真相协议"叠在没改的 legacy 传输/触发上,事实再准也传不动、对不齐。**

---

## 4. 为什么"两周像一事无成"——力气花在了不影响体感的层
| 层 | 这两周 | 是否影响你的体感 |
|---|---|---|
| 内核类型/协议(SyncCore) | 大量新增、反复重构、80+ 文件 | ❌ 几乎不影响 |
| 内核运行时点修(R1/R2/R4/R5) | 真做了几处 | 🟡 局部,但被聚合过载淹没 |
| **接口/集成层**(@MainActor server/stores、执行接管、readiness 真验证、传输拓扑) | **基本没动** | ✅ **这才是决定卡顿/收敛的层** |

**结论很直接:不是缺内核(内核过剩了),是缺"把内核真正接进一个被改造过的、不在主线程上干重活的 app"。** Codex 一直在打磨内核内部,而体感由它没碰的集成层决定。

---

## 5. 方向选择(这是路线问题,得你定)
继续让 Codex 写内核**不会**改善体感。要破局,只有动接口/架构这一层,二选一:

**路线甲(改造集成层,渐进):**
1. 把 `SecureLocalHTTPSServer` 等从 `@MainActor` 重活里解放——清单/哈希/原子写/canonical 构建全部移到后台 actor,主线程只做 UI。
2. 把 readiness 门改成**真验证**(连不上/未就绪就如实 block,而不是默认 true)。
3. 让 canonical **真接管执行**(至少同步链路),而不是 overlay 在 legacy 之上叠加。
4. 收敛:确认 Mac 服务端**对称**消费/产出状态交换,而不是单边。

**路线乙(承认 overlay 架构的天花板):**
- Path B(canonical 决策 + legacy 执行)注定"叠加更重、收敛吊在 legacy 上"。如果目标是产品级不卡顿+秒级收敛,可能要放弃 overlay,做一次**真正的执行层替换**(canonical 拥有传输/落盘/服务端),代价更大但能根治。

**我的建议**:先走甲的第 1 步(把 Mac 服务端重活移出主线程)——这是唯一能让你**立刻**感到不卡的动作,且独立、可验证;同时**冻结内核类型的扩张**(别再加 FourDomain/evidence/gate)。验证不卡之后,再谈执行接管与对称收敛。

## 6. 怎么用真机一句话证实本报告
真机看诊断:若切 fullSync 后 `mainActorLongTaskDurationMs` 仍大、且大头在 Mac 服务端响应/构建阶段(而非诊断写)——就坐实"卡在 @MainActor legacy 执行层",与本报告一致。
