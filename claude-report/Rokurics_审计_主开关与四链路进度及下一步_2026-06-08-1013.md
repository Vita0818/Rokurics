## 4. 下一步该写什么（我的建议）

**别开新链路。先把"同步链路"真正写完并能切换——这是你"全部写好+开关"模式的第一块完整拼图。** 顺序：

1. **【最高优先】补齐同步链路的三大未完件**：
   - 把 `CanonicalReadRuntimeAdapter` **真接进 `StudyLibraryStore`/UI**（读切换 0/6 → 6/6），否则主开关 `canonicalFullSync` 形同虚设。
   - 给**音频上传补真实 commit 执行器**（目前只有 NoCommit）。
   - 在**真机真实库副本**上跑 `CanonicalLegacyCompatibility` 的 switch-back，证明"切到新内核写入→切回旧内核仍正确"。
   - 完成后：同步链路一条**端到端可由主开关切换**，且能安全切回——**这才证明了你整套模式可行**，再谈下一条。

2. **然后写"上传"链路**（不是连接）：理由——① 它已经写了一半（audio NoCommit + cutover 模型），补真实 commit 执行器即可接上；② 原来的上传层本就有真 bug（如失败重试队列没人 drain）；③ 录音音频同步这条最痛的就在上传。

3. **"连接"链路放最后、而且建议**只做"协议/信封契约"共享，**不要把 TLS/配对/HMAC/nonce 重写成新内核**：连接层早期审计就是**可靠且安全**的（pinning fail-closed、HMAC 常量时间比较、nonce 防重放），它**没有要修的 bug**；把安全边界重写成 canonical 是**高风险、低收益**，容易引入 TLS/HMAC 新漏洞。canonical 可以拥有"线格式/清单 schema"，但**鉴权/传输运行时保留 legacy**。

4. **文件**链路不必单独立项——它会随同步 apply 的 real apply port 自然成形（已在做）。

**一句话顺序**：**先把同步写完并验证可切换 → 再写上传 → 文件随附 → 连接最后且最小化（只共享协议、不动安全运行时）。**
