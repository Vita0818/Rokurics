## 0. 结论速览（四症状 → 根因）

| 症状 | 根因（一句话） | 关键证据 | 置信度 |
| --- | --- | --- | --- |
| ① 卡顿无改善 | `sha256HexOffMainActor` 用信号量在**主线程上同步等待**，"离开主线程"是假的；且整条 tick/inventory 管线都在 `@MainActor`，缓存仅内存、冷启动后必全量重算 | `StudyLibrarySyncCoordinator.swift:1329-1344`、`:1144`、`:1418`、`:1597/1701` | 高 |

**一句话总览：** 同步层存在一个**结构性裂缝**——「录音」在两端有两套互不打通的表示：iPhone 用 `RecordingMetadata`+本地音频；Mac 用「音频收件箱 `receive.json`」与「学习库 `StudyItemMetadata`」两套独立记录。同步的 metadata 通道只走「学习库 manifest」，而音频上传判定只看「音频收件箱」。两者不连通，导致：metadata 永远对不上（②④）、新录音音频永远不被触发（③）；Codex 这轮只在"算 hash 的快慢"上打补丁（①也没真正解决），没碰这条裂缝。

## 1. 症状①：卡顿没有改善——"离开主线程"是假的

### 1.1 信号量在主线程同步等待

`StudyLibrarySyncCoordinator.swift:1329-1344`：

```
private static func sha256HexOffMainActor(fileURL: URL) throws -> String {
    guard Thread.isMainThread else { return try SecureUploadUtilities.sha256Hex(fileURL: fileURL) }
    let semaphore = DispatchSemaphore(value: 0)
    var result: Result<String, Error>!
    DispatchQueue.global(qos: .utility).async {
        result = Result { try SecureUploadUtilities.sha256Hex(fileURL: fileURL) }
        semaphore.signal()
    }
    semaphore.wait()      // ← 在主线程上阻塞等待，直到哈希完成
    return try result.get()
}
```

- 名为 `OffMainActor`，但当处于主线程时，它把哈希派发到全局队列后**用 `semaphore.wait()` 在主线程同步阻塞**，直到整文件 SHA256 算完。主线程被占满的时长与"直接在主线程算"完全一样。
- 这是已知的反模式：主线程 `DispatchSemaphore.wait()` 还可能引发优先级反转/卡死。

### 1.2 整条 tick/inventory 管线在 @MainActor，且每 tick 构建两次

- `LocalNetworkSyncInventoryBuilder` 标注 `@MainActor`，`build()` 是同步函数：`:1144-1145`、`:1166`。
- 持有它的 `LocalNetworkSyncEngine` 也是 `@MainActor`：`:1418`；`performTick` 在其上运行。
- `performTick` 内**两次**调用 `inventoryBuilder.build(...)`：`:1597`（本地 inventory）与 `:1701`（refreshedInventory）。两次都在主 actor。
- `build()` 内对每条录音同步调用 `cachedChecksum → sha256HexOffMainActor`（`:1183-1192`），冷缓存时逐个阻塞主线程算哈希。

### 1.3 缓存只在内存，冷启动后必然全量重算

- `LocalNetworkChecksumCache` 是 `final class`，仅有内存字典 `entriesByKey`，键为 size+mtime：`StudyLibrarySyncModels.swift:580-671`。**无磁盘持久化**。
- 缓存实例随 `inventoryBuilder` 长存（`:1424/1464`），所以同一进程内热 tick 能命中。但**每次冷启动/进程重启后缓存为空**，激活后的第一次 tick（常在前台恢复时触发）会把**所有**音频在主线程逐个哈希一遍 → 列表/连接页明显卡。

> 净效果：Codex 的缓存只优化了"同一进程内的重复哈希"，但①主线程仍被信号量阻塞，②冷启动首 tick 仍全量哈希，③整条管线仍在主 actor，④每 tick 还构建两次。所以真机"卡顿无改善"符合预期。

**方向（不改代码、仅建议）：** 把 inventory 构建与哈希整体移出主 actor（真正的 `async`/后台执行，禁止主线程 `semaphore.wait()`）；缓存落盘（size+mtime+sha256）跨启动复用；每 tick 只构建一次 inventory，必要时增量更新。

## 2. 症状②：已有未改文件被重传——metadata 哈希两端算的是不同对象

### 2.1 两端 `metadataHash` 的输入类型不同，永不相等

`LocalNetworkSyncMetadataHash.hash<Value: Encodable>(_:)` 对传入对象做 JSON 编码再哈希（iPhone `StudyLibrarySyncModels.swift:2969-2970`，Mac `RokuricsMac/StudyLibrarySyncModels.swift:2815-2816`）。但两端喂进去的对象**不是同一种类型**：

- iPhone 录音条目：`metadataHash: LocalNetworkSyncMetadataHash.hash(metadata)`，其中 `metadata` 是 **`RecordingMetadata`**（`StudyLibrarySyncCoordinator.swift:1195`）。
- Mac 录音条目：`metadataHash: itemsByRecordingID[item.id].map(LocalNetworkSyncMetadataHash.hash)`，其中值是 **`StudyItemMetadata`**（`SecureLocalHTTPSServer.swift:3021`）。

两种结构字段完全不同 → JSON 不同 → 哈希**永远不相等**。

### 2.2 diff 因此每个 tick 都判"需要同步"

`compareRecordings`（`StudyLibrarySyncModels.swift:2605-2618`）：

```
if localRecording.metadataHash == peerRecording.metadataHash {
    plan.noOps...                     // ← 永远进不来
} else if ...updatedAt 比较... {
    plan.uploadMetadataActions / downloadMetadataActions ...   // ← 每个 tick 都命中
}
```

- 因为 2.1，第一行恒为 false，所以每个已存在的录音每个 tick 都会进入 upload/download metadata 分支。
- 执行时 `uploadLocalMetadataIfNeeded`（`StudyLibrarySyncCoordinator.swift:1969-1990`）把**整份 `studyManifest`** 经 `/sync/apply-metadata` 再发一遍；`applyPeerMetadataIfNeeded`（`:1955-1967`）同理再 apply 一遍。即**已有且未改动的录音，其 metadata/manifest 每个 tick 都被双向重传**。这正是用户看到的"已有文件仍被重新传输"。

### 2.3 关于音频字节是否也被重传

纯音频上传走另一条路（`uploadRecordingAudioActions`）。对已正确收妥、两端 checksum 一致的文件，运行期评估器会判 no-op（`StudyLibrarySyncModels.swift:591-601`、运行期 `StudyLibrarySyncCoordinator.swift:2688-2730`），**不应**重传音频字节。因此症状②最确定的成因是 **metadata/manifest 的恒定churn**；若真机抓包发现音频字节也在重发，则多半是冷缓存瞬间本地 checksum 暂缺（`localSignature` 为空导致 `matches()` 失败，见 `:307-316`）的时序问题，而非稳态。

**方向：** 录音 metadata 的同步哈希必须两端用**同一规范化输入**（同一字段集、同一编码顺序）计算，否则 diff 永不收敛。

## 3. 症状③：新文件不传——manifest 通道与音频收件箱通道互不连通

### 3.1 音频上传只由 `peer.recordings` 触发

新录音音频要被同步上传，必须命中以下之一，二者都依赖**对端已在 `peer.recordings` 里有这条录音**：

- `compareRecordings`：`if localRecording.audioAvailable, !peerRecording.audioAvailable`（`StudyLibrarySyncModels.swift:2620`）——要求 `(.some local, .some peer)`，即 peer 必须已有该录音条目。
- `appendRecordingReceiveStatusNoOps`：`for peerRecording in peer.recordings { ... }`（`:2407`）——**只遍历 peer.recordings**。

而对纯本地新录音，`compareRecordings` 命中 `(.some, .none)` 分支，**只产生 `uploadMetadataActions`，不产生任何音频上传动作**（`:2623-2624`）。

### 3.2 Mac 的 `peer.recordings` 来自「音频收件箱」，不是「学习库」

Mac inventory 的 recordings 由 `recordingFileStore.loadInboxItems()` 构建（`SecureLocalHTTPSServer.swift:3019-3020`），即读音频收件箱的 `receive.json`；`hasAudio` 取自**音频文件是否真实存在**（`MacRecordingFileStore.swift` loadInboxItems：`fileExists(.../audio.m4a)`）。收件箱只在**真实上传**（`RecordingUploadCoordinator` → `/upload-recording-metadata`+音频）时才会创建。

### 3.3 但同步只发学习库 manifest，且 Mac apply 不写收件箱

- iPhone 同步 metadata 时发的是 `localInventory.studyManifest`（`StudyLibrarySyncCoordinator.swift:1975-1981`）。
- Mac 接收后 `applySyncManifest` **只处理 folders / items / tombstones**，**完全忽略 `manifest.recordings`，也不创建任何音频收件箱 `receive.json`**（`RokuricsMac/StudyLibraryStore.swift:246-294`，循环仅 `manifest.folders` / `manifest.items` / `manifest.tombstones`）。

### 3.4 闭环断裂

于是新录音的链路是：

1. 新录音存在于 iPhone → 出现在 `localInventory.recordings` 与 manifest。
2. diff 命中 `(.some,.none)` → 仅 `uploadMetadataActions`（无音频动作）。
3. 同步发 manifest → Mac 学习库新增一个 StudyItem，但**音频收件箱仍没有这条录音**。
4. 下一个 tick：该录音在 recordings 比较里**仍是 `(.some,.none)`** → 回到第 2 步。音频触发（`:2620`/`:2407`）**永远不会满足**。

**结论：自动同步永远无法把"新录音的音频"送到 Mac。** 只有用户在列表/详情页**手动点上传**（`RecordingLibraryView`/`RecordingStudyDetailPage` → `uploadCoordinator.upload` → 走 `/upload-recording-metadata`+音频）才会在 Mac 收件箱建立 `receive.json`+音频。这与真机"新文件没有被传输"完全吻合。

**方向：** 要么让同步在检测到本地有、对端收件箱无的录音时，直接经 `RecordingUploadCoordinator` 走真实上传通道（metadata+音频）来 bootstrap 收件箱；要么让 Mac `applySyncManifest` 消费 `manifest.recordings` 并据此在收件箱建立 metadata-only 的 `receive.json`（hasAudio=false），从而下个 tick 的音频触发能命中。两端必须用同一条"录音存在性"真相源。

## 4. 症状④：双端状态显示不一致——永不收敛 + 时间语义错位 + 单向回写

三重叠加：

1. **metadata 永不收敛**（第 2 节）：两端 `metadataHash` 永不相等，diff 长期在 upload/download 间摆动，UI 状态随之抖动、互相覆盖。
2. **`updatedAt` 语义两端不同**：iPhone 录音条目 `updatedAt = metadata.deletedAt ?? metadata.createdAt`（`StudyLibrarySyncCoordinator.swift:1202`）；Mac 录音条目 `updatedAt = item.deletedAt ?? item.receivedAt`（`SecureLocalHTTPSServer.swift:3072`）。createdAt（创建时刻）通常早于 receivedAt（Mac 收到时刻），于是 `compareRecordings` 的 `localRecording.updatedAt > peerRecording.updatedAt`（`StudyLibrarySyncModels.swift:2614`）长期为假 → iPhone 总把"Mac 更新"判为更晚 → 倾向 download，"谁更新谁赢"被时间语义错位带偏。
3. **状态回写是单向、且口径窄**：`applyPeerRecordingStatuses`（`StudyLibrarySyncCoordinator.swift:1937-1953`）只在 `peerRecording.receiveStatus == "completed"` 且音频可用且本地存在时，把本地 `uploadStatus` 提升为 `.uploaded`；它**只升不降、不回写转写/笔记状态**。而 Mac 同一录音又分属两套记录——音频收件箱（`receiveStatus`/`transcriptionStatus`/`noteStatus`）与学习库 `StudyItemMetadata`（经 manifest 同步）——两套状态独立演化，UI 读哪一套就显示哪一套，于是两端/同端不同视图都可能不一致。

**方向：** 统一录音的"同步时间戳"口径（两端同义）；把状态机收敛为单一真相源并双向、全维度（upload/receive/transcription/note）协调；先解决第 2、3 节的结构裂缝，状态一致性才有可能稳定。

## 5. 对"Codex 本轮修复"的核对

| 本轮改动 | 意图 | 实际效果 | 结论 |
| --- | --- | --- | --- |
| `LocalNetworkChecksumCache`（两端） | 避免重复哈希、降卡顿 | 仅命中"同进程内重复"；冷启动/进程重启后失效；不解决主线程阻塞 | 对症状① **基本无效** |
| `sha256HexOffMainActor` | 把哈希移出主线程 | 主线程上 `semaphore.wait()` 同步阻塞，等价于在主线程算 | **伪异步**，症状①未解 |
| Mac `cachedChecksum` + inventory checksum 重算 | 让对端报告准确 hash | 对端 hash 即便准确，也救不了"metadataHash 用不同模型算"的 ②，与"音频根本进不了收件箱"的 ③ | 未触及 ②③ 根因 |
| 录音 diff（`compareRecordings` 等） | 计算同步动作 | 仍用两端不一致的 `metadataHash`/`updatedAt`；新录音仍只发 manifest | ②③④ 根因仍在 |

> 核心判断：本轮聚焦在"哈希算得快不快、对端报得准不准"，但四个症状的根因是**两端录音表示与同步通道的结构性不连通**（manifest 学习库通道 vs 音频收件箱通道）以及**metadataHash/updatedAt 的口径不一致**。不修这两点，缓存/异步层面的补丁无法改善真机表现。

## 6. 建议的最小修复方向（仅建议，本项目约束为只读，未改任何代码）

1. **统一录音同步真相源**：定义"录音在对端是否存在/是否有音频"的单一权威（建议以音频收件箱 `receive.json` 为准），并让 manifest 同步与音频上传共用它；`applySyncManifest` 消费 `manifest.recordings` 落地为 metadata-only 收件箱记录，或同步层对"本地有、收件箱无"的录音直接走 `RecordingUploadCoordinator` 真实上传。（解 ③，并缓解 ②④）
2. **统一 `metadataHash` 输入**：两端用同一规范化字段集与编码顺序计算录音 metadata 哈希，确保未改动文件能命中 `metadata_equal` no-op。（解 ②）
3. **统一 `updatedAt` 语义**：录音同步时间戳两端取同义值（如都用录音创建时刻或都用最后修改时刻），避免 createdAt/receivedAt 错位。（解 ④）
4. **真正移出主线程**：inventory 构建与文件哈希整体后台化，删除主线程 `semaphore.wait()`；缓存落盘跨启动复用；每 tick 只构建一次 inventory。（解 ①）
5. **状态机双向、全维度收敛**：upload/receive/transcription/note 状态统一协调，回写不只升不降。（解 ④）
