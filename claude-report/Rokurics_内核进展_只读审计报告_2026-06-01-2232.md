## 1. 本轮实际改了什么（实证）

新增共享文件：`RokuricsShared/SyncCore/CanonicalSyncPlanner.swift`（380 行）——端无关的同步**决策引擎**；并新增双端 canonical 单元测试（`RokuricsTests/`、`RokuricsMacTests/` 各 3 个 `Canonical*Tests.swift`）。

关键接线（iPhone `StudyLibrarySyncCoordinator.swift`）：

```
1820  let legacyPlan = diffPlanner.plan(...)                       // 旧 plan 仍全量计算
1825  let plan = canonicalSyncPlanIfAvailable(... legacyPlan ...)  // 新：canonical 接管
1832             ?? legacyPlan                                     // canonical 不可用才回退
```

`canonicalSyncPlanIfAvailable`（`:1949`）：当双端 `canonicalManifest` 都存在时，跑 `CanonicalSyncPlanner().plan(...)`（`:1969`）并返回 `bridgedCanonicalPlan(...)`（`:1976`）。

`bridgedCanonicalPlan`（`:2046-2082`）—— **这是"承重"的证据**：

```
2050  var plan = legacyPlan
2051-2055  plan.{uploadMetadata,downloadMetadata,uploadRecordingAudio,conflict,noOps}
           .removeAll { entityKind == "recording" }   // 先把 legacy 的"录音"决策全部删掉
```

即**对"录音"，canonical 决策已经是权威**，legacy 录音决策被丢弃；非录音（folder/studyItem/artifact）仍走 legacy。Mac 侧也同步生成 canonicalManifest（`SecureLocalHTTPSServer.swift:3130`，能力含 `recordingMetadata/audioArtifact/receiveRecord/objectProjection`）。

## 2. CanonicalSyncPlanner 的决策是否正确（端无关）

`CanonicalSyncPlanner.plan`（`CanonicalSyncPlanner.swift:142-308`）按 objectID 对齐双端 canonical 对象，逐项判：

- metadata：`sameHash` 相等→noOp；否则按 `metadata.modifiedAt` 做 LWW（newer 上传/下载，时间相等→冲突）。
- audio：本地无音频→defer；`viewRefresh`/`retryDrainer` 触发→defer（不建任务）；**对端对象缺失→上传**；对端音频 missing→上传；unknown/availableWithoutHash→defer；available 且 hash+size 一致→noOp；hash 或 size 不一致→**冲突**（不再无脑覆盖）。

这套逻辑是对的，且直接对症我前几轮指出的根因（统一哈希口径、统一时间语义、unknown 不再误传、冲突不再覆盖）。

## 3. 逐症状核对（含证据与残余风险）

### 3.1 ③ 新文件不传 —— 已真正打通（高置信）

链路（全部已读到源码）：

1. 新录音在 iPhone canonical manifest 中有对象+音频事实（`StudyLibrarySyncCoordinator.swift:1258-1265` 用 `canonicalAudioFact` 填 `audioFactsByRecordingID`）。
2. 对端无此对象 → planner 判 `peerObjectAbsent → uploadAudioArtifact`（`CanonicalSyncPlanner.swift:280-282`）；若已经过一次 metadata 同步、Mac 仅有学习项无收件箱 → `peerStudyItemOnlyWithoutReceiveRecord`（`:317-318`）。
3. 执行层 `uploadRecordingAudioActionsToRun`（`:3097`）用 `bridgedPeerAudioDecisionState`（`:3117/3297-3313`）把这些 canonical 原因映射为 `.missing`/`.metadataOnly`，喂给评估器 → `shouldCreateUploadJob = true`。
4. 走真实 `RecordingUploadCoordinator` 上传 metadata+音频 → 在 Mac 建立收件箱 `receive.json`+音频。

→ 这正好补上了我上轮指出的"manifest 通道与收件箱通道不连通"的闭环。**③ 在代码层面已被解决**（真机仍建议验证一次新录音端到端到达 Mac 收件箱）。

### 3.2 ② 已有文件重传 —— 大概率基本消除，但有残余风险（中高置信）

正面证据：canonical `metadataHash`（`CanonicalCore.swift:139-155`）**只哈希稳定业务字段**（objectID、title、createdAt、duration、filing、tags、isDeleted、deletedAt），**显式排除** modifiedAt、receivedAt、observedAt、upload 进度、receiveStatus、路径等。相等→`metadataHashEqual`→noOp。这直接消除了我上轮指出的"两端用不同模型算 hash → 永不相等 → 每 tick 重传"的根因。

**残余风险（需真机验证，勿当已彻底解决）**：哈希里**仍含 `createdAt` 与 title/tags/filing**，而双端适配器对这些字段取值口径不同：

- `createdAt`：iPhone=`metadata.createdAt`（`IPhoneCanonicalRecordingAdapter.swift:19`）；Mac=`studyItem?.createdAt ?? inboxItem?.receivedAt ?? 0`（`MacCanonicalRecordingAdapter.swift:69`）。若某录音在 Mac**只有收件箱、无学习项**，Mac 用 `receivedAt`（≠ iPhone createdAt）→ 哈希不等 → 仍会重传该条。
- **时间精度**：哈希用 `timeIntervalSince1970` 取 6 位小数（`CanonicalCore.swift:167-173`），而 manifest 跨端是 ISO8601 序列化；若 `createdAt` 经同步往返被截断到秒，iPhone 端内存值（含亚秒）与 Mac 端往返值会在小数位上不同 → 哈希不等。
- title/tags/filing：Mac 从 `studyItem ?? inboxItem ?? receiveRecord` 兜底，tags 还要从 `StudyTag.value` 映射；与 iPhone 的 `RecordingMetadata` 字段若有任何归一化差异 → 哈希不等。

→ 判断：**设计正确、主因已除**，但是否"一条不剩地不再重传"取决于双端这几个字段能否产出**逐字节一致**的 canonical 值。好在 Codex 的影子诊断会把这种情况记成 `canonicalMetadataHashMismatch`——**真机看 `canonical-shadow.jsonl` 是否还有该类条目即可定论**。

### 3.3 ④ 双端状态不一致 —— 改善但未根治（中置信）

改善：不再是哈希乒乓；当业务字段一致时直接 noOp；不一致时按 `modifiedAt` 做**确定性** LWW（`CanonicalSyncPlanner.swift:240-246`）。

未根治：

- Mac 的 `modifiedAt = studyItem?.updatedAt ?? …`（`MacCanonicalRecordingAdapter.swift:70`）。`studyItem.updatedAt` 会被**Mac 本机操作**（如转写/笔记状态写回、manifest 应用）推进，使 Mac 端 `modifiedAt` 长期晚于 iPhone 的 `createdAt` → 触发 `peerMetadataNewer` → iPhone 反复**下载** Mac 版本。这与 CanonicalCore 注释"local 时钟不应喂 modifiedAt"的意图相悖，是潜在的方向性抖动源。
- canonical 只统一了**同步决策**；双端各自的状态记录（iPhone `uploadStatus` vs Mac 收件箱 `receiveStatus`/`transcriptionStatus`/`noteStatus` vs 学习项）仍并存，processingState 是否被**双向回写**到两套记录、UI 读哪一套，本轮未见统一。故"显示一致"还不能保证。

### 3.4 ① 卡顿 —— 未改善，且大概率略变差（高置信）

- 每个 tick 仍 `diffPlanner.plan(...)` 全量算 legacy plan（`:1820`），而 legacy plan 依赖 legacy inventory 构建。
- 主线程阻塞哈希**原样保留**：`sha256HexOffMainActor` 仍在主线程 `DispatchSemaphore.wait()`（`:1526-1539`）；`LocalNetworkSyncInventoryBuilder` 仍是 `@MainActor` 同步构建。
- 本轮**新增**：双端 canonical manifest 构建 + 影子报告写 `canonical-shadow.jsonl`（iPhone `:1263/1344`、Mac `:3130/3152`）叠加在主 actor 路径上。
- 净效果：每 tick 的主线程工作量"legacy 全量 + canonical + 影子"，比上一轮更多。**① 未解，倾向更卡。**

## 5. 仍需完成的步骤（仅建议，未改任何代码）

1. **收敛 canonical 字段口径**（解 ② 残余）：双端 `createdAt`/title/tags/filing 必须产出逐字节一致的 canonical 值；建议 `createdAt` 在同步往返中保全精度，或把 `createdAt` 移出哈希、只用稳定 objectID + 业务字段。用 `canonical-shadow.jsonl` 的 `canonicalMetadataHashMismatch` 清零作为验收。
2. **修正 Mac `modifiedAt` 来源**（解 ④）：让 `modifiedAt` 只反映"业务元数据变更"，不被 Mac 本机处理（转写/笔记/manifest 应用）推进；并把 canonical processingState 作为**双向**状态真相源回写两端。
3. **inventory/执行也 canonical 化并下主线程**（解 ①）：用 canonical manifest 直接驱动，停止每 tick 再全量算 legacy plan；删除主线程 `semaphore.wait()`，inventory 构建后台化、checksum 落盘缓存。
4. **删除 legacy 录音内核**：canonical 稳定后移除两端重复的 diff/inventory 实现，真正"一套内核 + 接口适配器"。
5. **逐步把文件/连接/上传内核化**：共享 `FileStore` 协议核、共享"签名协议/状态机"核（client/server 仅作角色适配）、共享"分块/续传/账本"上传状态机核。
6. **监控静默回退**：把 `canonicalPlanFallback` 做成可见告警，避免长期回退到旧逻辑而无人知。
