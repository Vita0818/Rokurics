## 0. 结论（先回答你的两个问题）

**问题一：Codex 是否完成了"双端共用四内核"的描述？**
**没有完成。** Codex 新增的是一套**共享"规范数据模型"（CanonicalCore）+ 双端适配器 + 影子（shadow）诊断**，它**只覆盖"同步数据模型"这一层，且只以"影子/旁路诊断"方式运行**，不参与真实决策。同时：

- 双端同名内核文件**仍然各存一份且本轮还在变大**（不是合并，是又加了代码）。
- **连接内核、上传内核、文件内核完全没有共享化**，仍是两套实现。
- 真正跑的同步链路仍是旧的两套 legacy 代码，CanonicalCore 的结果被算出来后**丢弃不用**。

所以从"消除两套内核"的目标看，**本轮非但没有合并，反而引入了第三套表示（规范模型）**——尽管它的设计意图是将来替换 legacy 的垫脚石。

**问题二：这是否有利于解决前面的同步问题？**
**间接有利，但当前不解决任何症状。**

- 有利的一面：CanonicalCore 的**设计是对的**，它已在模型层修正了我上轮指出的两个根因（时间语义、metadata 哈希口径），且影子诊断**精准地把四个症状都做成了可观测的 mismatch 类别**（见第 3 节）。这是高质量的"地基 + 探针"。
- 不解决的一面：因为它是**影子旁路、不是真相源**，真实 diff/inventory/决策仍走旧的、口径不一致的 legacy 代码，所以**①卡顿 ②已有文件重传 ③新文件不传 ④双端状态不一致 这四个症状在本轮后依然全部存在**；①甚至可能因影子报告每个 tick 多做一遍而**略微变差**。

一句话：**Codex 搭好了"将来能共用内核"的地基和验证探针，但还没把地基接上承重墙，旧的两套内核仍在承重。你的诉求尚未达成。**

## 1. Codex 本轮实际做了什么

新增共享文件（`RokuricsShared/SyncCore/`，6/1 最新）：

- `CanonicalCore.swift`（654 行）：一套**与端无关的规范数据模型**——`CanonicalRecordingMetadata`、`CanonicalArtifact`、`CanonicalManifest`、`CanonicalHash`、`CanonicalTimestamp`、`CanonicalNode/Capability`、`CanonicalProcessingState` 等。
- `CanonicalShadowDiagnostics.swift`（533 行）：影子对比框架——`CanonicalShadowReportBuilder`、`CanonicalShadowMismatchCategory`、JSONL 写入器。

新增双端适配器：

- `Rokurics/IPhoneCanonicalRecordingAdapter.swift`：把 iPhone 的 `RecordingMetadata` → Canonical。
- `RokuricsMac/MacCanonicalRecordingAdapter.swift`：把 Mac 的收件箱/学习库 → Canonical。

**这套设计的方向是正确的**：一个共享 Core + 两个薄适配器，正是"内核共用、只有接口不同"的标准形态。`CanonicalRecordingMetadata` 里甚至写了针对性注释（`CanonicalCore.swift:107-110`）：

```
// createdAt is the recording creation time. It is not Mac receivedAt.
// modifiedAt is the business metadata clock for LWW. Local receivedAt/observedAt must not feed it.
```

`metadataHash` 也明确"只哈希规范业务字段，排除上传进度等"（`CanonicalCore.swift:139-140`）。**这正是我上轮报告指出的 ②④ 根因的正确修法**——但只存在于 Canonical 模型里。

## 2. 关键证据：CanonicalCore 是"影子旁路"，不是"真相源"

### 2.1 算出来即丢弃，`build()` 仍返回 legacy inventory

iPhone `StudyLibrarySyncCoordinator.swift`：

- `:1259-1266` 先用**旧的 `recordingEntries`** 构造 `inventory`（真实返回值）。
- `:1267-1278` 仅当 `shadowTrigger != nil` 时调用 `writeCanonicalShadowReport(...)`。
- `:1290` `return inventory` —— 返回的是 **legacy inventory**，与 Canonical 无关。
- `writeCanonicalShadowReport` 内部把对比结果写入诊断日志 `canonical-shadow.jsonl`（`:1344`），**不回灌**任何决策。

Mac `SecureLocalHTTPSServer.swift` 完全同构：`makeLocalNetworkSyncInventory`（`:3006`）在 `:3134-3158` 写影子报告后 `return inventory`（legacy）。

### 2.2 真实 diff 仍用 legacy `plan()` + 仍是类型不一致的 metadataHash

- 真实决策：`StudyLibrarySyncCoordinator.swift:1820 let plan = diffPlanner.plan(...)` —— 旧的 `LocalNetworkSyncDiffPlanner`，未改。
- legacy `metadataHash` **仍然两端算不同类型**（我上轮的 ② 根因，本轮未修）：
  - iPhone `:1197`：`metadataHash: LocalNetworkSyncMetadataHash.hash(metadata)`（`metadata` 是 `RecordingMetadata`）。
  - Mac `SecureLocalHTTPSServer.swift:3069` ← `:3021`：`LocalNetworkSyncMetadataHash.hash(StudyItemMetadata)`。
  - 二者类型不同 → 哈希永不相等 → 旧 diff 仍每 tick 判"需同步 metadata"。

### 2.3 症状③的闭环（manifest↔收件箱）本轮根本没碰

- `git show --stat v7.6` 中**不含** `RokuricsMac/StudyLibraryStore.swift`。
- 现源码 `applySyncManifest`（`RokuricsMac/StudyLibraryStore.swift:246-294`）仍只遍历 `manifest.folders/items/tombstones`（`:253/267/282`），**仍不消费 `manifest.recordings`、仍不写音频收件箱 `receive.json`**。
- Mac inventory 的 `peer.recordings` 仍来自 `loadInboxItems()`（音频收件箱）。→ 新录音音频仍无法经自动同步进入收件箱（③ 根因原样保留）。

## 3. 影子诊断：它精准地"看见"了四个症状（很有价值，但只是看见）

`CanonicalShadowMismatchCategory`（`CanonicalShadowDiagnostics.swift:15-27`）的类别几乎一一对应我上轮的根因：

| 诊断类别 | 对应症状 | 含义 |
| --- | --- | --- |
| `legacyMetadataHashMismatchButCanonicalHashMatch` | ② | 旧 metadataHash 不一致、但规范哈希一致 → 证明"已有文件重传"是旧口径的**假阳性** |
| `studyItemOnlyWithoutReceiveRecord` | ③ | 只有学习库条目、没有收件箱记录 → 正是"新录音进了 manifest 却进不了收件箱、音频不传" |
| `receiveRecordOnlyWithoutStudyItem` | ④ | 两套记录各有其一 → 双端/同端状态分叉 |
| `canonicalAudioSameHashSameSize` / `canonicalAudioMissing` / `canonicalAudioConflict` / `peerUnknown` | ②③④ | 规范化的音频决策真值 |

**结论**：Codex 显然读懂了问题——它把每个根因都做成了可观测探针，会往 `canonical-shadow.jsonl` 持续输出"旧逻辑在哪儿和规范逻辑分叉"。这是**排障地基**，对你后续定位极有用；但探针只负责"看见"，不负责"修"。真实链路依旧用会分叉的旧逻辑。

## 4. "四内核共用"诉求的逐项核对

| 内核 | 你的目标 | 现状 | 是否达成 |
| --- | --- | --- | --- |
| 同步内核 | 双端共用一套 | 有共享 Canonical **数据模型**，但**仅影子**；真实 diff/inventory/决策仍 legacy 双份 | ❌ 仅地基 |
| 文件内核 | 双端共用一套 | iPhone `AudioFileStore` 与 Mac `MacRecordingFileStore` 仍是两套独立实现；CanonicalCore 不含文件 IO | ❌ 未动 |
| 连接内核 | 双端共用一套 | iPhone `SecureMacUploadClient`（客户端）与 Mac `SecureLocalHTTPSServer`（服务端）仍两套；CanonicalCore 不含任何 HTTP/传输 | ❌ 未动 |
| 上传内核 | 双端共用一套 | iPhone `RecordingUploadCoordinator` 与 Mac 接收/收件箱仍两套；CanonicalCore 不含上传状态机 | ❌ 未动 |

`CanonicalCore` 的 capability 只有 `recordingMetadata/audioArtifact/receiveRecord/transcript/note/summary/objectProjection`（`CanonicalCore.swift:50-58`），即**纯同步数据模型**，不含文件 IO、连接传输、上传状态机。所以"四内核"里只有"同步内核的数据模型层"被触及，其余三个**未共享化**。

> 关于连接内核的一个公允说明：连接层确有 client/server 的天然角色差异，"完全一样"不现实；但正确形态是**一套协议/状态机内核 + 两个薄角色适配器**（正如 Codex 对数据模型用的 adapter 模式），而不是两套独立实现。你的架构判断是对的，只是连接层要落在"共享协议核 + 角色适配"上。

## 5. 这是否有利于解决同步问题——逐症状结论

| 症状 | 本轮后是否改善 | 原因 |
| --- | --- | --- |
| ① 卡顿 | ❌ 未改善，或**略变差** | 旧的主线程 `semaphore.wait()` 伪异步与 @MainActor 全量构建未动；影子报告每 tick 额外构建一遍 Canonical manifest + 写 JSONL（iPhone `:1267`、Mac `:3134`），在主 actor 上增加少量开销 |
| ② 已有文件重传 | ❌ 未改善 | 真实 diff 仍用类型不一致的 legacy `metadataHash`（`:1197` vs `:3069`）；Canonical 正确哈希只在影子里 |
| ③ 新文件不传 | ❌ 未改善 | `applySyncManifest` 仍不写收件箱、不消费 `manifest.recordings`（本轮未碰该文件）；音频触发仍依赖 `peer.recordings` |
| ④ 双端状态不一致 | ❌ 未改善 | ②的永不收敛 + `updatedAt` 语义错位 + 单向回写仍在；两套记录仍并存 |

**净判断**：本轮是"为正确的修复做准备"，不是"修复本身"。它把对的模型和对的探针放进了仓库，但没有把任何真实链路切换到共享内核，所以真机症状不会变。

## 6. 要真正达成你的诉求，缺的关键一步（仅建议，未改任何代码）

Codex 已经把"共享 Core + 双端适配器"的形状搭对了。要兑现"双端共用内核 + 解决症状"，还差**把 Canonical 从影子提升为真相源，并删掉 legacy**：

1. **让真实链路消费 Canonical**：inventory/diff/决策改为基于 `CanonicalManifest`/`CanonicalRecordingObject`（用 `CanonicalHash` 做 metadata 比较、用 `CanonicalTimestamp.modifiedAt` 做 LWW），替换 `diffPlanner.plan` 走的 legacy 口径。这一步直接消除 ②④。
2. **打通 manifest↔收件箱闭环**：让 Mac 接收侧依据 Canonical 的 `receiveRecord` capability 统一"录音存在性"真相源，使新录音能进入对端可见集合并触发音频上传。消除 ③。
3. **删除两套 legacy 内核**：Canonical 接管后，删去 iPhone/Mac 各自的 `StudyLibrarySyncModels`/diff/inventory 重复实现，真正做到"一套内核 + 两个接口适配器"。这是你"别再两套内核"的核心。
4. **把哈希/扫描移出主 actor**：Canonical 化的同时，inventory 构建与文件哈希后台化，去掉主线程 `semaphore.wait()`，缓存落盘跨启动。消除 ①。
5. **逐步把文件/连接/上传也内核化**：文件 IO 抽象为共享 `FileStore` 协议核 + 端适配器；连接抽象为共享"签名协议/状态机"核 + client/server 角色适配；上传抽象为共享"分块/续传/账本"状态机核 + 端适配器。
6. **影子留作回归闸门**：保留 `canonical-shadow.jsonl`，在切换期用"零 mismatch"作为可以删 legacy 的验收标准——这正是 Codex 这套诊断的最佳用途。

> 验收建议：先看真机产生的 `canonical-shadow.jsonl` 是否持续报告 `legacyMetadataHashMismatchButCanonicalHashMatch` 与 `studyItemOnlyWithoutReceiveRecord`——如果是（极可能），就直接印证"②③仍在、且 Canonical 已知正确答案"，可据此推动第 1、2 步。
