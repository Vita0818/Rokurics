- 你的验收标准(唯一尺子)：**① 双端均可用 ② 满足功能 ③ 高效不卡顿。**

## 0. 先对齐两点认知

**A. 脚手架的定位(认可你的判断,但说清边界)。**
脚手架(canary/landing/evidence/cutover/retirement)保证的是**"切换动作"的稳定**——不是内核本身"会跑、跑得快、跑得对"。所以它该留,但**只用现有的,别再加新类型**(已 2.6 万行,够了)。这是省 token 的关键:**把预算从"造更多闸门"转到"造发动机"。**

**B. 架构方向定调(本次最重要的决定)。**
当前是"**canonical 出决策 → 翻译回旧计划 → 旧内核执行(传输/落盘)**"。我建议**就走这条(决策内核 + 修好的旧执行 + 旧执行兜底)**,不要重写传输层。理由:
- 你要的是"可用/满足功能/不卡顿",**不要求** canonical 亲自做文件 IO;
- 旧的 TLS+HMAC+配对传输是可靠且安全的,重写它是高风险、最烧 token;
- "共享内核"在**决策+数据模型+投影+读**这一层共享就达标了(两端算同一份 manifest、同一套 diff、同一份投影)——这正是 `CanonicalCore/Planner/Apply/Projection` 已经做对的 7%。

> 即:**新内核 = 双端共享的"决策/模型/投影/读"层;旧内核 = 执行肌肉 + 兜底。** 把旧执行的 bug 修了,三条标准就能在不重写传输的前提下全部满足。
> (备选 Path A:让 canonical 亲自拥有传输/落盘=真·执行内核。更纯粹但翻倍工作量+动安全边界。除非你坚持,否则不建议。这是唯一需要你拍板的岔路。)

## 1. 路线图(5 个阶段,每段:Codex 写 → 你真机验)

```
P0 修卡顿 ──► P1 修执行层正确性 ──► P2 决策+读双端对齐(逐域,脚手架护航) ──► P3 收口主开关+真机切回 ──► P4 观察(legacy 常驻兜底)
  ③不卡顿        ②满足功能              ①双端可用 ②满足功能                    一个开关                  稳定
```

### P0 · 修卡顿(标准③;独立、最高优先、零切换风险)
**为什么先做**:它和 canonical 无关,是双端共享 inventory 的老问题;修完后"卡不卡"不再污染后面所有真机验证。
| Codex 窄任务 | 验收(你真机) |
| --- | --- |
| `LocalNetworkSyncInventoryBuilder` 去掉 `@MainActor`,把目录扫描 / `loadAllMetadata` / `loadJobs` / 逐条 `metadataHash` 放后台 actor(**真**后台,不是"主线程就 throw") | 开 `diagnosticsOnly`,连接/同步/学习库页**不再可见卡顿** |
| 落盘 checksum 缓存(size+mtime→hash)真正命中,避免每 tick 重算 | jsonl 里 `inventoryBuildDurationMs` 明显下降(给前后对照) |
| **删掉硬编码 `count=0` 的假遥测**,改真实测量主线程阻塞数 | `MainActorHashBlocked/ScanBlocked` 是**真**测出来的 0 |
| 让 canonical 每 tick 的规划/投影/seam 也不在主 actor 上(或在未启用时不跑) | 把开关逐档打开,卡顿**不随档位上升而加重** |

### P1 · 修执行层正确性(标准②;不依赖开关,旧内核也直接受益)
**为什么紧接**:执行肌肉是旧内核,决策再准,肌肉有洞也白搭(漏传就是这洞)。

| 用现有 NoCommit→Commit canary 给音频 commit 做安全着陆(脚手架在这里发挥作用) | canary 阶段全绿、可回滚 |

## 2. 节奏与纪律(防空转、控 token)

1. **一次一个窄任务**:每轮只交给 Codex 上表中的一格,**禁止**它"顺手再加一层脚手架/新 evidence 类型"。
2. **每轮交两样东西**:① 改了哪些代码;② **真机 jsonl 证据**(不是测试 fixture)。给不出真机证据=没真跑。
3. **真机验证是你的活**:Codex 跑不了真机,P0–P3 每段的"验收"都要你在设备上点一下、导出 jsonl。
4. **顺序不可乱**:P0(不卡顿)必须最先——否则后面每次真机验都被卡顿干扰,分不清是内核问题还是性能问题。
5. **token 预算**:冻结脚手架面(不加新类型),把预算压在 P0/P1 这两段"发动机"上——它们最小、最值、最直接命中你的标准。

## 3. 这条路线图怎么同时满足你三条标准
- **③ 不卡顿** → P0 直接修根因(inventory 移出主线程)。
- **② 满足功能** → P1 修漏传+音频 commit(执行肌肉变好)+ P2 决策内核修重传/状态不一致(决策变准)。
- **① 双端可用** → P2 两端跑同一套 canonical 决策+读;P3 一个开关双端切;legacy 双端兜底。

**一句话**:**P0 让它不卡,P1 让它能传对,P2 让两端算一致并能读,P3 一个开关切、能安全切回。脚手架在 P2/P3 当安全带——留着,但别再扩。**
