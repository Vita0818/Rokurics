## 第一部分 · 当前审查

### 1. 已证明的（可以肯定）
- **Codex 代码能力达标**：~60k 行 canonical、构建零 error；真机把开关推到最危险档，系统因 `peerSnapshotUnavailable` 前置不满足而 **`commitAttempted=false` + 保留 legacy**——护栏在最坏情况下守住了。这是实打实的好结果。
- **新内核的"决策模型"是对的**：canonical metadataHash 只哈希稳定业务字段、`modifiedAt` 做 LWW、投影契约带路径安全、apply 带原子+回滚、域矩阵带退役护栏。设计方向正确。
- **零生产风险**：全部默认关、读路径仍 legacy。

### 2. 必须清醒认识的（别误读"没 bug"）
- **"没出 bug"很大程度是因为它从没真正接管过运行时**。canonical 至今是**影子/旁路**：`StudyLibrarySyncCoordinator` 仍 `let legacyPlan = diffPlanner.plan(...)`（`:2026`）、`bridgedCanonicalPlan(...) ?? legacyPlan`（`:2149`），真实执行还是 legacy。**真正的正确性考验在 canonical 接管运行时那一刻才开始。**
- **你当初要解决的 4 个同步症状，根因在 legacy 运行时里一个都没消除**（因为 legacy 还在跑）：
  | 症状 | 根因（仍在 legacy 里） | 位置 |
  | --- | --- | --- |
  | 卡顿 | inventory builder `@MainActor` + `sha256HexOffMainActor` 用 `semaphore.wait()` 阻塞主线程 + 每 tick 构建两次 | `StudyLibrarySyncCoordinator.swift:1153/1677/1690/2000/2250` |
  | 已有文件重传 | legacy `metadataHash` 两端按**不同模型**算（iPhone `RecordingMetadata` vs Mac `StudyItemMetadata`） | iPhone `:1205` / Mac `SecureLocalHTTPSServer.swift:3316` |
  | 新文件不传 | `applySyncManifest` 仍只处理 folders/items/tombstones，不消费 `manifest.recordings`、不写音频收件箱 | `RokuricsMac/StudyLibraryStore.swift:253/267/282` |
  | 双端状态不一致 | `updatedAt` 语义错位（createdAt vs receivedAt）+ 单向状态回写 | 历史审计已记录 |
- **过度工程化倾向**：光"学习库"一个域已 163 个类型 / ~1.26 万行，却还没落地。**"让它继续写"必须配一条纪律：窄任务 + 每阶段先落地再写下一层**，否则会再堆出几座没跑过的脚手架。

### 3. 一句话现状
**地基和迁移机器件造得不错、护栏可靠，但新内核还没接管同步运行时，所以你建它的初衷（修同步）还没兑现。下一步的价值不在"再写更多"，而在"让新内核真正接管同步、并由构造消除那 4 个根因"。**

## 第二部分 · 同步链路新内核构建方向

### 0. 总目标
把 canonical 从"影子决策"升级为**真正的同步运行时**，并让 4 个症状**由架构消除**（不是靠影子比对一个坏 legacy）。仍走"默认关 / 一次一阶段 / 先落地再扩"。

### 1. 新同步内核应当"拥有"的五件事（现在都还在 legacy 手里）
1. **Inventory 投影**：移出主线程 + 落盘 checksum 缓存（size+mtime→hash），每 tick 只构一次。→ 直接消除**卡顿**。
2. **Diff / LWW**：以 canonical `metadataHash`（稳定业务字段）+ `modifiedAt` 为唯一真相源。→ 由构造消除**重传**与**状态不一致**（两端同口径哈希、同义时间）。CanonicalSyncPlanner 已具备，缺的是"升为权威、删 legacy diff"。
3. **统一"存在性"真相源**：干掉"学习库 manifest 通道 vs 音频收件箱通道"的割裂——apply 侧让 `manifest.recordings` 能落地为收件箱记录（或反之统一）。→ 由构造消除**新文件不传**。
4. **传输 + apply 执行**：canonical 拥有（真实端口/执行器已建，差"接管"）。
5. **读路径**：UI/Store 读 canonical 投影（带并行对照）。→ 让状态显示一致。

### 2. 推荐构建顺序（每阶段都能独立验收、先落地再下一阶段）

**阶段 0（先做、最高性价比、零写风险）：修卡顿。**
- 把 `LocalNetworkSyncInventoryBuilder` 的哈希/扫描移出主 actor（真后台，删 `semaphore.wait()`），加落盘 checksum 缓存，每 tick 只构一次 inventory。
- 验收：真机开 `diagnosticsOnly` 后连接/同步/学习库页**不再明显卡**（就是你刚观察到的卡顿消失）。
- 为什么先做：它独立于任何 cutover、低风险、立即可感知，而且**给后续所有影子/真机验证去掉"卡顿"这个干扰项**。

**阶段 1：把学习库域真正落地（把现有 90% 脚手架变成"已验证迁移"）。**
- 先解决真机 `peerSnapshotUnavailable`：两端前台 + 配对 + 手动同步，确保 Mac 同 tick 拿到本地+对端两份 canonical 清单。
- 一档一档爬：`diagnosticsOnly`（读侧等价=0）→ `armTestRootN1` → `executeTestRootN1`（测试根真写+回滚演练）→ `executeProductionRootN1`（真实根 N=1，先备份）。
- 然后做**读切换**（StudyLibraryStore/UI 读 canonical，先并行对照差异=0）→ 观察期 → 经域矩阵护栏退役该域 legacy。
- 验收：学习库这一个域**端到端由 canonical 读写**、legacy 退役、`canonical-shadow.jsonl` 零分歧。**这是把"会写代码"变成"会迁移"的关键一步。**

**阶段 2：录音 metadata + 录音/音频同步（你真正痛的那条）。**
- 用阶段 1 验证过的同一套模式（投影→NoCommit→Commit→读侧→退役），对录音域做。
- 重点在这里彻底落实第 1 节第 2、3 点：统一哈希口径、统一存在性真相源——**重传/漏传/状态不一致在这一阶段被根除**。
- 音频上传放最后（大文件/分块/网络，单独设计端口与金丝雀）。

**阶段 3：收口。**
- 删 legacy diff/inventory 重复实现；统一配置（现已 ≥9 个旋钮 → 收敛进域矩阵）；把 163 类型瘦身。

### 3. 给 Codex 的"第一个窄任务"（防止又空转）
> **只做阶段 0：把同步 inventory 的哈希与目录扫描移出主线程 + 落盘 checksum 缓存 + 每 tick 只构一次 inventory。不准动 cutover、不准加新域/新 pilot 类型、不准改默认开关。**
> 验收：① 构建零 error；② 现有测试全过；③ 真机开 `diagnosticsOnly` 后卡顿明显减轻（附"全关 vs 开启"对照）；④ 给出 `connection-diagnostics.jsonl` 里 inventory 构建耗时（`inventoryBuildDurationMs`）的真机数值，前后对比。

### 4. 红线（不变）
- 一次一个阶段/一个域；默认关；影子先于真写；写侧切换先于读侧切换；退役最后且过域矩阵护栏。
- 真实写必须 `rootEscape`+原子+可回滚+崩溃安全；`manifestHash` 不当鉴权（保 TLS pinning+HMAC）。
- **每轮要求 Codex 区分"写了什么代码"与"真机上验证了什么"，并交出真机 jsonl 证据**——不接受"又加了一层脚手架"当进展。

## 第三部分 · 给你的节奏建议
1. 先让 Codex 做**阶段 0（修卡顿）**——小、稳、立刻见效，也顺手验证 Codex 能不能按"窄任务+真机证据"交付。
2. 卡顿解决后，你自己按阶段 1 把**学习库域真机落地**（读侧切换 + 退役 legacy）——这是把整条流水线跑通的第一证据。
3. 再进阶段 2 去真正修同步。

**核心判断**：继续用新内核、从同步链路写起，方向对。但把"继续写"约束成"先把卡顿修了 + 把学习库一个域真正落地"，比"让它再开几个新域"价值高得多，也最能防它空转。
