## 0. 严重度图例与总览

| 等级 | 含义 |
| --- | --- |
| 🔴 高 | 影响功能正确性/数据收敛，正常使用即可能触发，建议优先处理 |
| 🟠 中 | 边界条件或特定场景触发，或安全纵深被弱化；威胁模型（可信局域网 + TLS + pinning + HMAC）缓解了部分风险 |
| 🟡 低 | 健壮性/可维护性/性能优化项，非阻塞 |

本轮共记录 **15 项问题 + 1 处文档/源码冲突 + 1 处死代码**，并在第 7 节列出已确认的良好设计。

**三个最关键的卡点（建议优先）：**

1. 🔴 **上传重试队列无人驱动**——`RecordingUploadQueue` 在生产代码中零调用，失败上传到期后不会被任何调度器自动重试（第 3.1 节）。
2. 🔴 **失败/冲突即永久"等待"**——重试驱动缺失叠加评估器把 `retryPending` 一律抑制为 waiting，且音频分歧被 Mac 拒收后无解决路径，形成僵局（第 3.2 / 3.3 节）。
3. 🟠 **peer 状态 unknown 即上传 + inventory 无哈希缓存**——inventory 缺失/过期时旧录音被重复上传，且每次 inventory 重建全量重算 SHA256，构成"既重复传又卡 UI"（第 4.1 / 4.2 节）。

## 1. 链路全景（实测梳理）

**连接层**（仅负责配对、presence、心跳、签名 HTTPS 请求，不决定某条录音是否上传）：

- iPhone：`SecureMacUploadClient`（pinning + HMAC 签名）、`SecureMacConnectionSettings/Store`（host/port→UserDefaults，deviceID/secret/fingerprint→Keychain）。
- Mac：`SecureReceiverService` → `SecureLocalHTTPSServer`（Network.framework TLS listener + HTTP 解析 + 路由）→ `RequestVerifier`（method/path/content-type/body-size/header/timestamp/nonce/bodyHash/HMAC）；`MacIdentityManager`（TLS 身份）、`PairingManager` + `PairedDeviceStore`。

**上传层**（实际 metadata/audio 传输、resumable session、ledger、进度、失败分类）：

- iPhone：`RecordingUploadCoordinator`（job ledger + 重试策略）→ `RecordingUploadClient`（单请求 vs resumable 分块决策）→ `SecureMacUploadClient`（签名传输）。
- Mac：`MacRecordingFileStore`（落盘、receive.json、resumable session、冲突检测、checksum 校验）。

**同步层**（inventory / diff / metadata·artifact apply / 把"对端缺音频"转成上传候选）：

- iPhone：`LocalNetworkSyncAppService`(入口)、`StudyLibrarySyncCoordinator`(performTick)、`StudyLibrarySyncModels`(`RecordingAudioUploadDecisionEvaluator` 决策核心、`LocalNetworkSyncDiffPlanner`)、`ConnectionSyncStateStores`。
- Mac：`SecureLocalHTTPSServer.makeLocalNetworkSyncInventory`、Mac 侧同名 `StudyLibrarySyncModels` / `ConnectionSyncStateStores`。

## 2. 连接层发现

### 2.1 🟠 TLS 私钥以明文 JSON 文件落盘（且与文档矛盾）

- 证据：`RokuricsMac/MacIdentityManager.swift:235-250`（`writeTLSPrivateKey` 将 `SecKeyCopyExternalRepresentation` → base64 → `tls-private-key.json` 明文写盘）、`:79-82`、`:188-208`、`:210-233`（从同一明文文件加载）。
- 文档冲突：`docs/DO_NOT_BREAK.md:55` 与 `docs/ARCHITECTURE.md:160` 均声称 "TLS private key 在 Data Protection Keychain 中，不是普通文件"。源码实为普通明文文件。
- 旁证：`RokuricsMac/MacAppStorageProfile.swift:64-80` 定义了 `tlsDataProtectionPrivateKeyTag/Label`，但 `MacIdentityManager` 从未引用；构造参数 `tlsKeyTagNamespace` 被显式丢弃（`:83 _ = tlsKeyTagNamespace`）。说明曾计划用 Keychain，实际未落地。
- 附带：签名私钥 `mac-identity.json` 同样明文（`:149-164`），但这一项与文档描述一致，风险更低。两个密钥文件均未见设置文件保护属性（`NSFileProtection*`）。
- 影响：Mac 私钥静态保护被弱化为"仅依赖 App Sandbox 容器隔离"。若容器被读取（备份、迁移、提权），TLS 私钥与签名私钥即泄露。
- 缓解：macOS App Sandbox 容器隔离 + 该密钥仅用于本机局域网自签 TLS。故评 🟠 而非 🔴。
- 方向：迁移到 Data Protection Keychain（`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` 等），或至少对密钥文件加文件保护属性；并同步修正文档。

### 2.2 🟠 配对码缺乏暴力破解防护

- 证据：`RokuricsMac/PairingManager.swift:53-61`（6 位十进制码，空间约 10^6 ≈ 20 bit，5 分钟有效）、`:85-122`（`completePairing`）。关键：`code` 错误时（`:101-105`）仅置 `state=.failed("bad_code")`，**不清除 `activeChallenge`、不计数失败、无锁定/退避**；只有过期（`:94-99`）和成功（`:118`）才清除挑战。
- 旁证：`/pair` 路由处理器 `RokuricsMac/SecureLocalHTTPSServer.swift:738-789` 同样无速率限制/尝试上限。
- 影响：同一配对码在 5 分钟窗口内可被局域网内攻击者持续枚举，直到命中或过期。（注：码本身由 `Int.random` = 系统 CSPRNG 生成，不可预测；风险来自空间小 + 无锁定，而非可预测。）
- 缓解：配对窗口短、需用户主动开启、且攻击者须在同一局域网。
- 方向：失败 N 次即作废当前挑战并退避；为 `/pair` 增加 per-IP 速率限制；可考虑加大码长或改用配对二维码内联随机 token。

### 2.3 🟠 Nonce 重放缓存仅存内存，Mac 重启后清空

- 证据：`RokuricsMac/RequestVerifier.swift:37`（`recentNoncesByDeviceID` 内存字典）、`:333-349`（仅按 `timestampWindow`=5 分钟剪枝）、`:39`（窗口 5 分钟）。
- 影响：Mac app 重启后 nonce 集合清空；在 5 分钟时间戳窗口内被截获的已签名请求，重启后可被重放一次。
- 缓解：TLS + pinning 使中间人截获在可信局域网下难度很高；窗口仅 5 分钟。
- 方向：nonce 缓存持久化（或缩短时间戳窗口 / 引入单调递增计数器）。

### 2.4 🟠→🟡 流式音频先落盘再验签

- 证据：`RokuricsMac/SecureLocalHTTPSServer.swift:1319-1376`（`/upload-recording-audio` 边收边写临时文件）、`:1438` 流式算 SHA256、`:1458-1464` **在整文件落盘后才** `requestVerifier.verify(...)`；拒绝分支 `:1507-1509` 会 `discardTemporaryUpload` 清理。
- 影响：未配对/重放请求可在被拒前迫使 Mac 写入至多 512MB（`audioMaxBytes`）临时文件并做一次全量哈希，构成局域网内的资源耗尽（磁盘/CPU）面。其余路由（chunk≤8MB、sync≤4–6MB）走内存缓冲后验签，量级较小但同样"先收满再验签"。
- 设计性说明：因签名 payload 含 body 哈希，必须读完 body 才能验签，这是协议固有约束。但 **device-id 是否为已配对设备、timestamp 是否在窗口** 属于不依赖 body 的廉价前置校验，当前未在收 body 前进行。
- 方向：在接收/落盘 body 前，先用 header 做 device 存在性 + 时间戳窗口预检，挡掉非配对/过期请求再决定是否接收大 body。

### 2.5 🟡 已验证请求的写放大（markSeen 全量落盘）

- 证据：`RokuricsMac/RequestVerifier.swift:311`（验签成功即 `markDeviceSeen`）→ `RokuricsMac/PairedDeviceStore.swift:112-119`（`markSeen` 调用 `save()`）→ `:174-186`（全量 `JSONEncoder` + `.atomic` 写盘），且 `PairedDeviceStore` 为 `@MainActor`。
- 影响：每个已验证请求（每次心跳、每个分块、每次 sync）都在主 actor 上全量重写 `paired-devices.json`。大文件分块上传时每块一次写放大，叠加 2.4 与 4.2 的主线程 IO，放大卡顿。
- 方向：`lastSeenAt` 节流落盘（如 ≥N 秒才持久化）或与请求处理解耦到后台。

### 2.6 🟡 证书再生会静默失效已 pin 的指纹

- 证据：`RokuricsMac/MacIdentityManager.swift:170-185`（当存储证书与当前 TLS key 不匹配或缺失时自动重建证书 → 指纹改变）；iPhone 端 pin 的是叶子证书整 DER 的 SHA256（`Rokurics/SecureMacUploadClient.swift:1629-1667`）。
- 影响：TLS key 文件（明文 `tls-private-key.json`）丢失/容器重置后，Mac 生成新 key+新证书 → 指纹变化 → iPhone 所有请求以 `fingerprint_mismatch` 失败，除通用失败外无显式"请重新配对"引导。
- 方向：证书轮换时提供面向用户的 re-pair 提示路径；或在 `/fingerprint`/health 流程中识别"指纹已变更"并引导。

### 2.7 🟡 `pairedCredentialState` 恒为 `.paired`（吊销态未接线）

- 证据：`RokuricsMac/PairedDeviceStore.swift:11-17`（枚举含 `.invalid/.revoked/.fingerprintMismatch`）但 `:54-56` 计算属性 **硬编码返回 `.paired`**。
- 影响：凭证失效/吊销/指纹不匹配等状态有定义但无写入路径，无法据此使某设备凭证失效。属未完成逻辑。
- 方向：若需要远程吊销/失效语义，补全状态机；否则删除误导性枚举值。

## 3. 上传层发现

### 3.1 🔴 重试队列无人驱动（auto-retry 形同死代码）

- 证据：`Rokurics/RecordingUploadCoordinator.swift:502-503`（`retryQueue()`）、`:1409`（`struct RecordingUploadQueue`）。**仓库范围内 `retryQueue()` 生产调用数 = 0**；`RecordingUploadQueue` 仅在 `RokuricsTests/RokuricsTests.swift:1054/1375/1407/1700` 被单测直接实例化。无任何 `Timer`/`asyncAfter`/scheduler 在 `nextRetryAfter` 到期后 drain。
- 配套：失败时 `:442-449` `markRetryableFailure` 设 `nextRetryAfter`（退避 `[5,30,120]`，上限 600s，见 `:943-965`）；`recoverStaleInProgressJobs`（`:1202-1228`）在启动时（`Rokurics/RecordingManager.swift:713`）把卡住的 in-progress 重置为 `retryableFailed(nextRetryAfter=now)` —— 但同样无人 drain。
- 影响：上传失败后，除非用户**手动再次点击上传**，或恰好有一次 sync tick 重新评估**且未被抑制**，否则失败任务不会自动恢复。退避重试在生产中实际不生效。
- 方向：引入一个到期驱动器（定时器或 ledger 变更触发）按 `nextRetryAfter` drain `retryQueue()`，并与 sync diff 去重避免重复建任务。

### 3.2 🔴 `retryPending` 被一律抑制为 "waiting"（与 3.1 叠加成僵局）

- 证据：`Rokurics/StudyLibrarySyncModels.swift:610-611`（`transfer_retry_pending` → suppress/waiting）、`:623-624`（`ledger_retry_pending` → suppress/waiting）。
- 影响：失败任务进入 `retryPending` 后，评估器既不创建新上传，UI 又显示"等待"，叠加 3.1 无 drainer，结果是**长期停在"等待上传"且无自动恢复、无可操作提示**。
- 方向：区分"退避等待中（到期可自动恢复）"与"无驱动的死等待"；UI 对 fatal vs retryable 提供不同操作（重试/查看原因）。

### 3.3 🟠 音频分歧 → Mac 拒收 → iPhone 死等（冲突无解决路径）

- 证据链：
  - 评估器对 peer `.different` / `.available` 但签名不匹配 → 判 `.upload`（`Rokurics/StudyLibrarySyncModels.swift:642-643`，reason `peer_audio_signature_mismatch`）。
  - Mac 收到时若该 recordingID 已有不同音频：`RokuricsMac/MacRecordingFileStore.swift:707-721` → `handleExistingAudioUpload` → `:1856-1877` 对 checksum/size 不一致 **throw `audioConflict`（拒收，不覆盖）**，并 `markUploadConflict`。
  - iPhone 收到失败 → `retryableFailed` → 回到 3.1/3.2 的死等。
- 影响：一旦同一 recordingID 的音频在两端分歧（re-encode、部分写、损坏等边界），iPhone 反复想传、Mac 反复拒、无 drainer、无冲突 UI，形成**永久僵局**。
- 缓解：正常流程下 recordingID 唯一且音频录完即不可变，分歧不常见。故评 🟠。
- 方向：定义明确冲突策略（保留双方/版本化/用户选择），而非"上传→必拒→死等"。

### 3.4 🟠 peer 状态 `unknown` 即上传（重复上传旧数据的根因之一）

- 证据：`Rokurics/StudyLibrarySyncModels.swift:640-641`（peer `.unknown` → `.upload`，reason `peer_audio_unknown`）。peer 状态来自对端 inventory；inventory 缺失/过期/只报 metadata 时即落为 unknown/metadataOnly/missing。
- 影响：app 激活 / 周期 / 手动 tick 在 inventory 不准时，把"Mac 其实已有的旧录音"判为需补传 → 重复上传。与团队 `docs/SYNC_STATE_AUDIT.md` 第 11 节记录一致，本轮已独立核实代码路径。
- 方向：手动/周期触发在建任务前先轻量获取一次 peer audio truth；取不到时标记为"强制/未知"，不要把它等价于"同步收敛"。

### 3.5 🟡 大文件上传前的全量预哈希造成首字节前延迟

- 证据：`Rokurics/RecordingUploadClient.swift:562-567`（resumable 路径上传前对整文件 `SecureUploadUtilities.sha256Hex(fileURL:)`，除非 resumeContext 已带哈希）；上限 16GB（`:223`）。
- 影响：哈希虽为 1MB 流式（不占内存，`SecureUploadUtilities.swift:27-44`），但超大文件在首个分块发出前需整文件读一遍，UI 上表现为长时间"无进度"。
- 方向：预哈希展示独立阶段进度，或与首块上传并行/边传边算。

## 4. 同步层发现

### 4.1 🟠 Inventory 无 checksum 缓存，每次重建全量重算 SHA256

- 证据：本轮 grep 确认 iPhone 侧 inventory 构建路径**无** mtime/size→hash 缓存（`Rokurics/StudyLibrarySyncModels.swift` / `StudyLibrarySyncCoordinator.swift` 未见 checksum cache）；Mac 侧 `RokuricsMac/SecureLocalHTTPSServer.swift:2995+`（`makeLocalNetworkSyncInventory`）对每个已存音频重算 checksum。
- 影响：每次 inventory 重建都对**每条**本地/收件箱音频整文件重算哈希；大库 + 高频 tick 时，是主 actor 上的 IO/CPU 热点，直接导致录音列表/连接页卡顿。与 `docs/SYNC_STATE_AUDIT.md` 第 17 节、`CURRENT_STATE.md` 风险项一致。
- 方向：引入 `(path, size, mtime) → sha256` 缓存，仅在文件变化时重算；inventory 改增量；把哈希/目录扫描移出主 actor。

### 4.2 🟠 Mac "立即同步" 为间接握手，易表现为 no-op

- 证据：Mac 端写 pending sync request 等待 iPhone 心跳消费 `syncStartSignal`（`docs/SYNC_STATE_AUDIT.md:103-107` 描述，代码侧入口 `SecureReceiverService.prepareManualStudyLibrarySync`）；iPhone 侧 tick 由 `isSyncing` 串行 gate 保护（`Rokurics/StudyLibrarySyncCoordinator.swift:267/278/411/1380/1483`）。
- 影响：iPhone 不活跃 / 心跳未运行 / presence 离线 / 已有 tick 在飞 / backoff 命中时，Mac 点"立即同步"无可见效果，且**无端到端回执**（pending→consumed→acked→started→completed/failed）。用户体感为 no-op。
- 方向：补端到端状态回执链并在 Mac UI 呈现；区分"已请求待 iPhone 执行"与"已执行/失败"。

### 4.3 🟡 双端同名模型内容不一致，改协议易单端遗漏

- 证据：iPhone 与 Mac 各有一份 `StudyLibrarySyncModels.swift`、`ConnectionSyncStateStores.swift`，内容不完全一致（`docs/ARCHITECTURE.md:166`、`PROJECT_MAP.md:239` 已记录）。
- 影响：修改同步协议/状态枚举/签名 payload 时若只改一端，易产生协议漂移，且测试覆盖偏单元级。
- 方向：把跨端协议模型收敛进 `RokuricsShared/`（如 `SyncCore.swift`），双端共用一份。

## 7. 已确认的良好设计（交叉复核，供平衡参考）

- **证书 pinning 正确且 fail-closed**：仅处理 `ServerTrust`，pin 叶子证书，缺 trust/缺证书/指纹不匹配均 `cancelAuthenticationChallenge`；调用方还二次校验"确实收到过 TLS challenge"（`SecureMacUploadClient.swift:169`、`:1601-1667`）。
- **HMAC 与哈希比较为常量时间**：`RequestVerifier.swift:284/303` 用 `constantTimeEquals`。
- **Resumable 完整性校验充分**：分块校验 offset 与 chunk-SHA256（`MacRecordingFileStore.swift:1077/1115/1136`），finalize 时对拼装文件整体 SHA256 与声明值常量时间比对（`:1229-1231`）。
- **Body 大小在缓冲前按路由预限**：`SecureLocalHTTPSServer.swift:1302` + `bodyLimit(for:)`（`:2968-2993`）与 `RequestVerifier` per-path 限额一致。
- **单请求音频流式落盘**：`/upload-recording-audio` 边收边写，避免 512MB 全量入内存（`:1319-1438`）。
- **明文上传被禁用**：`SecureMacUploadClient.isHTTPSUploadEnabled = true`，无明文回退活跃路径。
- **view refresh 不触发上传**：评估器 `triggerSource.isViewRefreshOnly → suppress`（`StudyLibrarySyncModels.swift:576-578`）落实了"展示状态不反向驱动业务"。
- **sync tick 串行 gate** 防并发重入（`isSyncing`）。

## 8. 上传决策真值表（本轮独立核实，源：`StudyLibrarySyncModels.swift:561-647`）
