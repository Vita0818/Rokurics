# Rokurics 诊断报告 · 新内核为何卡顿 · 为何状态仍不收敛

- 时间：2026-06-12 21:40 (CST)
- 方式：**只读**审计,未改任何代码。
- 前提：你两端都已选 `canonicalFullSync`(新内核完整同步),现象是"几乎点一下就卡",且状态收敛三症状仍在。

---

## 0. 一句话
**卡顿**的元凶是 canonical **读路径每次 UI 访问都在主线程重算投影+重建学习树**(无缓存),加上 **Mac 服务端每次同步都在主线程重建 manifest/canonical 对象**(T1 后台化没覆盖 Mac)。
**状态不收敛**的根因**根本不在 canonical 动过的层里**:你的"秒级同步"其实是 3 秒**心跳**(只探活、不传数据),真正同步是 **240 秒(4 分钟)定时器**;而 Mac"点同步"发出的唤醒提示,被运行中的那套心跳**忽略**了。canonical(Path B)只统一了数据模型/决策/读/写,**没碰触发拓扑与传输**,所以再完整也收敛不了。

---

## 重点 1 · 为什么新内核卡顿

### 1.1 读路径:每次 UI 访问都重算(这就是"点一下就卡")
`StudyLibraryStore`(双端)的 `effectiveStudyItems / effectiveStudyFolders / effectiveStudyTree` 是**计算属性**。`canonicalFullSync` 下 `canonicalReadServed == true`,于是每次被读到就:
- `effectiveStudyItems` → `canonicalEffectiveStudyItems(from: readSnapshot)` 重新变换整份快照;
- `effectiveStudyFolders` → 内部**再调一次** `canonicalEffectiveStudyItems`(重复算);
- `effectiveStudyTree` → `VirtualStudyTreeBuilder.build(items: effectiveStudyItems, folders: effectiveStudyFolders, …)`——**读一次就把上面全部重算一遍 + 整棵树重建**。

SwiftUI 每次渲染/交互会**反复读这些属性几十次**,每次都是 O(N) 重算 + 建树,全在 `@MainActor`。
对比 legacy 档:`effectiveStudyTree` 直接返回**缓存好的存储属性 `studyTree`**(在 `refresh()` 里只算一次,Mac :256/:824/:838),所以便宜。
→ **canonical 读路径把"算一次缓存"退化成了"每次访问重算",这是每次交互都卡的直接原因。** 位置:Mac `StudyLibraryStore.swift:186-214`、iPhone `:177-192`。

### 1.2 Mac 服务端:每次同步都在主线程重建一切(T1 没覆盖 Mac)
`RokuricsMac/SecureLocalHTTPSServer.swift` 整体 `@MainActor`(:52),每次建 inventory 都在主线程**同步**做:
- `studyLibraryStore.makeSyncManifest(...)`(:2518/2566/2725)——**没用后台版**(iPhone 已改 `makeSyncManifestInBackground`,Mac 没改,**T1 只做了一半**);
- **无条件**构建整套 canonical 对象 + canonical manifest(`MacCanonicalRecordingAdapter.makeObjects` + `CanonicalInventoryBuilderContract().build`,:3902-3923),**连档位都不判断**;
- `canonicalFullSync` 下其后十几个 `recordCanonical…Seam`(:3934-4030)以及 apply/audio commit **全部启用**,也在主线程。

→ **Mac 的卡顿根因(inventory 在主线程)从没被修过,fullSync 还把 canonical 的整套构建叠加上来。**

### 1.3 叠加架构:fullSync = 活最多,不是最少
canonical 始终是"在 legacy 之上叠加"——`legacyPlan` 每 tick 仍无条件计算,再算 canonical、再 bridge。所以**档位越往新内核推,每 tick 的主线程工作越多**,不是越少。这与"新内核更高效"的直觉相反,是当前实现的结构问题。

## 重点 2 · 为什么新内核没能解决状态收敛

### 2.0 核心误解:"秒级同步" = 心跳,不是同步
- `heartbeatInterval = 3` 秒(:93):这是**心跳**,只发 `sendDeviceStatus`(探活 + 状态摘要),**不交换清单、不传文件**。
- `syncInterval = 240` 秒(:94):这才是**真正的同步**(清单交换 + 传输 + apply),**4 分钟一次**(`syncLoop` :487-496)。
→ **你以为的"秒级同步系统"是 3 秒心跳;真正让状态/文件对齐的同步是 4 分钟一次。心跳 ≠ 同步。** 这是收敛慢的总背景。

### 2.1 症状①:Mac 点同步拉不起 iPhone
- **拓扑限制**:iPhone 是**客户端**、Mac 是 **HTTPS 服务端**。服务端**无法主动连客户端**——Mac 结构上没法"拨号"给 iPhone。
- **有提示通道,但被忽略**:协议里有 `syncRequested` 字段,Mac 的 `prepareManualStudyLibrarySync`(`SecureReceiverService.swift:941`)会置一个待同步信号、把状态标成"**等待 iPhone 执行同步**"(:976)。**但**运行中的 3 秒心跳循环 `heartbeatLoop → performHeartbeat()`(:482→:221)**只读 `response.ok`,根本不读 `syncRequested`、不触发同步**。真正会处理该提示的代码(:1097 `syncRequestedHintReceived` → :9688 `syncRequestedTickQueued`)在**另一套引擎心跳**里,而 live 循环调的不是它。
→ **结果:Mac 点了同步,只是在 Mac 侧挂了个"等待 iPhone"的状态;iPhone 那套在跑的心跳收不到、也不行动,只能等自己的 240 秒定时器。所以"Mac 点同步拉不起 iPhone"。** 这是 legacy 层的接线缺口(两套心跳,live 的那套没接 hint)。

### 2.2 症状②:iPhone 未同步文件不能及时到 Mac
- 周期同步 **240 秒**一次;新文件若没触发"视图刷新"类 trigger(`recordingListRefresh/studyLibraryRefresh` 等),就**静等最多 4 分钟**。
- 即便同步发生,Mac 侧消费录音的路径(`applySyncManifest` → `applyManifestRecordingsIfConfigured`)是**门控**的:要 `canonicalRecordingExistenceApplyPort != nil` 且 existence apply 配置非 disabled 才会落地(默认/非 fullSync 下不消费)。
→ **新文件到 Mac 的时效被"4 分钟定时器 + 门控 apply"双重拖住。**

### 2.3 症状③:两端对同一项目状态不同
- 状态字段(`uploadStatus / transcriptionStatus / receiveStatus / noteStatus`,`StudyLibrarySyncModels.swift:2155-2165`)是**两端各自计算**的;
- 只在每 240 秒同步时对账,且状态回写偏**单向**;
- `canonicalFullSync` 下一端走 canonical 读投影、另一端的某些视图可能走不同来源。
→ **在两次同步之间(可达 4 分钟),两端对同一项显示不同状态是必然的;若某个方向根本没传(见症状①②),就长期不一致。**

### 2.4 为什么 canonical 帮不上这件事
canonical(按你定的 Path B)统一的是 **数据模型 + diff 决策 + 读投影 + apply**;**刻意没有重写**触发拓扑与传输(TLS/心跳/定时器/客户端-服务端方向都保留 legacy)。
而状态收敛取决于 **何时、由谁、向哪个方向交换数据**——这整层是 legacy 的连接/触发逻辑,canonical 从设计上就不碰。
→ **所以无论 canonical 写得多完整,都不会让"Mac 唤醒 iPhone""4 分钟变秒级""双向状态回写"变好——瓶颈在 canonical 没拥有的那一层。** 这也解释了你"建了秒级同步却仍不收敛":你建的是 3 秒**心跳**,没建 3 秒**同步**,而 Mac→iPhone 的唤醒提示又在 live 心跳里断了线。

---

## 3. 结论与该修哪一层(不含改法,仅指方向)
- **卡顿**:属于"新内核**实现**问题",可修——(a) 读路径把 canonical 投影/树**缓存**成存储属性(像 legacy 的 `studyTree`),仅在 `canonicalReadRuntimeResult` 变化时重算一次;(b) 把 Mac 服务端的 manifest/canonical 构建**移出主线程**并在 `oldKernel` 档**完全跳过** canonical 构建。
- **状态收敛**:属于"**触发/传输拓扑**问题",在 canonical 之外——要让收敛变好,得修 legacy 连接层:(a) 让 live 心跳真正消费 `syncRequested`、把 Mac 的唤醒提示接到 iPhone 的同步触发;(b) 把"真正的同步"从 240 秒拉到事件驱动/秒级(新文件/状态变更即触发),而不是只把心跳设成 3 秒;(c) 状态双向回写。
- **次序提醒**:这两件都**不是把 canonical 写得更完整**能解决的。继续堆 canonical 域/执行器,卡顿和收敛都不会变好。
