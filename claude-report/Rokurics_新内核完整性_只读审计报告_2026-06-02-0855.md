## 0. 一句话结论

**新内核还不完整。** 它目前是一个**「只管录音、只管 metadata+音频、只做决策」**的纵向切片：把"录音元数据 LWW + 录音音频传输判定"做对了，但一个完整的共享同步内核还应覆盖的其余部分——**文件夹、独立学习项、转写/笔记/摘要等产物的同步、应用(写回)侧、冲突解决、删除墓碑生命周期、单一投影契约、传输/inventory 归属**——**要么没进内核、要么还压在旧逻辑上**。

并且：**本轮的新增量主要是"诊断与投影管线"，不是"覆盖面变宽"**——planner +81 行几乎都是诊断原因/发射点与 `audioArtifact` 能力校验；Mac 适配器 +105 行是多一个投影重载与辅助函数；影子诊断 +83 行。内核能管的**业务范围这轮基本没变大，只是更"看得清"了**。

## 2. 新内核已经做"对"且较完整的部分（值得肯定）

- **录音 canonical 数据模型**：`CanonicalRecordingObject` + `CanonicalRecordingMetadata`，`metadataHash` 只哈希稳定业务字段、排除 modifiedAt/receivedAt/processingState（`CanonicalCore.swift:139-155`）。
- **带完整性校验的清单**：`CanonicalManifest` 有 `schemaVersion` + `manifestHash`（自校验 `hasValidManifestHash`）+ 能力声明（`:405-449`），planner 入口 `validate` 会校 schema/hash/能力（`CanonicalSyncPlanner.swift:193-216`）。
- **录音 metadata LWW 决策**：相等→noOp，否则按 `metadata.modifiedAt` 上传/下载/并列冲突（`:225-308`）。
- **录音音频传输决策**：本地无音频/viewRefresh/retryDrainer→defer；对端对象缺失/音频缺失→上传；unknown→defer；同 hash 同 size→noOp；hash 或 size 不一致→冲突（`:311-363`）。
- **强诊断 + 双端单测**：`canonical-shadow.jsonl` + `Canonical*Tests.swift`（双端各 3 个）。

这块是同步里最难做对的"录音元数据 + 音频"一致性判定，已经基本闭合。

## 3. 新内核**缺失**的部分（按"缺什么"逐条）

### 3.1 对象域只有"录音"——缺文件夹与独立学习项

`CanonicalManifest.objects` 的类型是 **`[CanonicalRecordingObject]`**（`CanonicalCore.swift:411`），清单里**只有录音**。

- **文件夹**（`StudyFolderMetadata`：创建/重命名/移动/颜色/废纸篓）完全不在 canonical 模型里。
- **独立学习项/笔记**（没有 recordingID 的 item）也不在。
- 桥接层只剥离替换 `entityKind == "recording"`（`StudyLibrarySyncCoordinator.swift:2102-2106`），所以**文件夹与学习项的同步仍 100% 走旧逻辑**。

→ 缺口：内核还不是"学习库内核"，只是"录音内核"。

### 3.2 缺转写/笔记/摘要产物的同步决策（这是产品价值本身）

`CanonicalArtifact.Kind` 支持 `transcriptJSON/transcriptMarkdown/noteMarkdown/noteJSON/summaryJSON`，但：

- **投影只放音频**：iPhone 适配器只传 `audioFact`（`IPhoneCanonicalRecordingAdapter.swift:27`）；Mac inventory 喂给 canonical 的 `artifactFactsByRecordingID` 也只来自 `canonicalAudioFact(...)`（`SecureLocalHTTPSServer.swift:3125-3127`）。转写/笔记产物只出现在**旧** artifact 通道（`:3446-3459`、`StudyLibrarySyncCoordinator.swift:1571-1572`）。
- **planner 不决策产物**：除一个 `peerStudyItemOnlyWithoutReceiveRecord`（仍是给音频用的原因）外，planner 不含 transcript/note（`CanonicalSyncPlanner.swift` 全文）。
- 结果：iPhone 录音→Mac 转写+生成笔记→**笔记/转写回传 iPhone 这条"主价值链"完全不在新内核里**，仍由旧 `download/uploadArtifactActions`（`:2485/2719/2805`）处理。

→ 缺口：内核没覆盖"录音之外的产物流"，而这正是 app 的核心收益。

### 3.3 缺"应用/写回(apply)"侧——内核只会"规划"不会"落地"

`CanonicalSyncPlanner` 只产出 `CanonicalSyncPlan`（决策清单）。`RokuricsShared/SyncCore/` 内**没有任何 apply/executor/applier**（已 grep 确认）。落地仍是旧逻辑：

- canonical 判"下载某录音 metadata"→ 实际用旧的**整包** `applySyncManifest(manifest, …)`（`StudyLibrarySyncCoordinator.swift:2441-2450`），不是按对象精确写回。
- canonical 判"上传音频"→ 经桥接喂回旧评估器 + 旧 `RecordingUploadCoordinator`。

→ 缺口：一个完整内核应同时拥有"diff"和"apply"两半；现在只有 diff，apply 仍是旧整包逻辑。

### 3.4 冲突只检测、不解决

planner 会产出 `conflictRecordingMetadata` / `conflictAudioArtifact`（hash/size 不一致、modifiedAt 并列），但协调器对 `conflictActions` **只记录诊断**（`StudyLibrarySyncCoordinator.swift:1883-1884`），**无解决策略、无合并、无用户可见入口**。冲突对象既不上传也不下载，**静默停在 diverged**。

→ 缺口：缺冲突解决策略（谁赢/如何合并/如何提示用户）。

### 3.5 缺删除/墓碑生命周期

删除目前只靠 `isDeleted/deletedAt` 进入 metadata 哈希 + 走 LWW（`CanonicalCore.swift:152-153`）。没有专门的墓碑传播、墓碑回收(GC)、防"删除被对端旧数据复活"的保证；文件夹/学习项的删除更不在内核内。

→ 缺口：缺确定性的删除传播与墓碑生命周期。

### 3.6 缺传输/重试状态机的归属

`CanonicalTransferState`（queued/inFlight/retryPending/…）只是个枚举，**未被 planner 用于调度**；真正的上传/重试 ledger、`retryDrainer` 的实际 drain 仍在旧逻辑（planner 对 retryDrainer 只是 defer，`CanonicalSyncPlanner.swift:330-333`）。

→ 缺口：内核定义了传输状态词汇，但没拥有传输/重试的状态机。

### 3.7 投影是"两份适配器"，不是"单一契约"——这是新内核自身的一致性隐患

`createdAt` 仍进哈希（`CanonicalCore.swift:145`），而双端取值口径不同：iPhone=`metadata.createdAt`；Mac=`studyItem?.createdAt ?? inboxItem?.receivedAt ?? 0`（`MacCanonicalRecordingAdapter.swift:69`）。title/tags/filing 也各自兜底。两份适配器各写各的 → 仍可能产出不一致的 canonical 对象。Codex 已加诊断 `canonicalCreatedAtIgnoredForMetadataHash`（`CanonicalSyncPlanner.swift:239-249`）来观测这种偏差，但**还没有把"投影"收敛成一份双端共享的契约**。

→ 缺口：内核缺"单一投影定义"，目前靠两份手写适配器对齐，是新内核内部的脆弱点。

### 3.8 inventory 构建与传输线仍未归内核

canonical manifest 目前**寄生在旧 `LocalNetworkSyncInventory` 负载里**一起传（`SecureLocalHTTPSServer.swift:3130-3149`、iPhone 同构），inventory 仍由旧的 `@MainActor` builder 构建。内核没拥有 inventory 构建与传输端点。

→ 缺口：传输线/inventory 归属仍在旧层（这也是卡顿问题的来源，但按你要求本轮不展开）。

## 4. 把缺口排成"补全顺序"（仅建议，未改任何代码）

按"对产品价值/正确性影响"从高到低：

1. **投影收敛为单一契约**（解 3.7）：用一份共享投影定义产出 canonical 对象，双端只提供取数，不各自兜底；`createdAt` 要么保精度跨端、要么移出哈希。这是新内核**自身**能否信赖的前提。
2. **把转写/笔记/摘要产物纳入模型+决策+应用**（解 3.2）：这是 app 主价值链，目前完全在内核外。
3. **补 apply(写回)侧**（解 3.3）：内核同时拥有 diff 与按对象 apply，停止用旧整包 manifest 落地。
4. **把文件夹与独立学习项纳入对象域**（解 3.1）：让内核成为"学习库内核"。
5. **冲突解决策略**（解 3.4）与**删除/墓碑生命周期**（解 3.5）。
6. **传输/重试状态机归内核**（解 3.6）、**inventory/传输线归内核**（解 3.8）。

完成 1–3 后，新内核才算覆盖了"录音 + 其产物"的完整闭环；完成 4–6 才算覆盖整个学习库、可以开始删旧内核。
