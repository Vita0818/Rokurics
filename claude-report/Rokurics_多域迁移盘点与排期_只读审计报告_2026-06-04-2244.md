## 3. 没写/没接的怎么排

### 3.1 tombstone/冲突（执行器已写、未接线）
- **要么接、要么暂缓，别留半成品**。tombstone 是危险域（删除/防复活），接线时必须：app seam + canary + 闸门 + 防"对端旧 metadata 复活已删对象"。建议**排在 metadata 类域之后**，且接线前先把第一域真正跑通（见第 4 节）。

### 3.2 录音音频上传（只到 NoCommit）
- **commit 执行器最后做**。音频是大文件/分块/resumable/跨网络，回滚语义、原子性、爆炸半径、断点续传都与 metadata 完全不同——不能套 metadata 模板，要单独设计真实根端口（或复用现有 resumable 上传 + 检查点）与金丝雀。**放在所有 metadata/产物/库/tombstone 域之后。**

### 3.3 所有域共同欠下的"后半程"（统一排期）
对每个域，落地顺序固定为：**注入真执行器+真实根端口 → 开 canaryCommit(N=1) 真机金丝雀 → 等价=0 → 读侧迁移 → 观察期 → 退役 legacy**。这后半程目前 5 个域**全部为 0**。

## 4. 注意事项（重点）

1. **"广度已够、深度为零"是当前最大风险。** 已为 5 个域铺了 write 模板，但没有一个域走到真启用/读侧迁移/退役。建议**立刻转向把第一域（录音 metadata，最小最安全）一路打通到线上并退役其 legacy**，用它压过整条"注入→真机金丝雀→读侧→退役"流水线，再回头批量推其余域。否则会越堆越多"默认关、永不读、永不启用"的 write 路径，形成无人验证的脚手架。
2. **读侧迁移是每个域被系统性遗漏的另一半。** 现在 5 个域全是"canonical 能写、legacy 在读"。一旦哪天开了 commit 而没切读，会出现双真相，反而更易出 bug。**把"UI/同步读 canonical"列为每个域的硬性验收项。**
3. **配置旋钮在膨胀（已 6 个 gating 配置）。** 上轮我建议收敛成单一"域×阶段"矩阵，本轮不降反增（每域一套 AppSeamConfiguration）。**域越多越容易误配**（例如把 audio 误推到 commit）。建议**先收敛配置再加域**。
4. **跨设备协调未验证。** metadata/产物/库的 `send/apply` 跨设备；真 commit 走真实发送（影子里 transport 是抑制的），需单独验证 TLS pinning+HMAC + Mac 端 apply 幂等 + 双端 canary 预算协调。
5. **每域过门硬条件**：真机 NoCommit 等价=0 + 执行影子字节等价 + **故障注入回滚演练全绿**（写中断/部分提交/磁盘满/权限失败/回滚失败）+ 重试幂等 + 崩溃安全。
6. **一次一个域、一个档位**；保留 legacy 回退直到该域读侧迁移 + 观察期过。
7. **红线不变**：`manifestHash` 不当鉴权（保 TLS pinning+HMAC）；真实写必须 `rootEscape`+原子+可回滚+崩溃安全；保留 Commit 对 dryRun 端口 fail-closed；出厂默认关。
